# SEKB 文档体系审查报告

- **审查日期**：2026-09-15
- **审查人**：CodeBuddy
- **审查范围**：`README.md`、`AGENTS.md`、`docs/`（`tmp/` 与 `codeReview/` 除外）、`prompt/`
- **评估维度**：① 与功能一致 ② 编目合理、逻辑清晰 ③ 适用于多人群（拥有者/开发者/维护者/使用者）

---

## 一、总体结论

文档**总量充足、质量意识在线**（有 frontmatter、编号体系、漂移清单、CHANGELOG 碎片机制——后者在同类项目中罕见），但当前处于**"文档体系完成了一次大迁移，但旧文档没清干净"**的中间态：

1. **入口层（README）严重滞后于代码**——结构树、API 清单、命令、启动方式与现实不符；
2. **编目承诺与实际不符**——README 的目录清单漏掉实际存在的文件；
3. **四类受众中"使用者"几乎缺位**——技术文档 15 篇、运维 16 篇，用户手册 0 篇；
4. **已知漂移有台账（漂移清单）但无闭环**——清单记录了 12 项，多数仍开着。

## 二、A 类：一致性（文档 vs 实际，最高优先级）

**A1.（高）README.md 项目结构树整体过期**
`README.md:424-543` 的目录树仍是大迁移前的旧结构（`docs/01-architecture.md`、`docs/02-phase1-design.md` 等已迁入 `docs/tech/`）。新读者按图索骥第一步就失败。**建议**：用脚本从实际目录生成结构树（可挂 CI），并补 `docs/tech/`、`docs/ops/`、`prompt/`、`browser-service/`、`scripts/`、`AGENTS.md`。

**A2.（高）README 启动命令疑似指向非实际入口**
`README.md:273` 写 `uvicorn app.api.main:app`，而 `deploy/Dockerfile:177` 用 `app.api.server:app`。需核实 `main.py` 是否仍是入口；若否，README 教的启动方式直接报错。**建议**：以 `start_backend.sh`/Dockerfile 为唯一真相，README 引用而非复述。

**A3.（高）README API 清单缺失新功能全部端点**
README 仅列约 18 个端点，而系统实际有 65+（`docs/tech/05-API-REFERENCE.md` 统计 65 个），**招聘分析 20+ 端点、新闻、分享、会话分享、用量、监控端点全部缺失**。**建议**：README 只保留核心 10 个端点 + 链接到 05-API-REFERENCE，避免双份维护；或直接由 FastAPI `openapi.json` 自动生成。

**A4.（高）`README.md:365` `POST /api/v1/upload/` 带尾斜杠，实际路由无尾斜杠**
FastAPI 默认对尾斜杠做 307 重定向，POST 重定向可能丢 body。**建议**：核对并统一，或在 FastAPI 设 `redirect_slashes=False` 并在文档明确。

**A5.（高）docs/README.md 编目清单与实际不符**
`docs/README.md:11` 声称 ops 为"编号 00-10"，实际已有 00-15 共 16 篇；`docs/tech/00-README.md` 声称"完整版 12 篇"，实际还含 `12-三平台MCP接入调研.md`、`待确认项清单.md`、`漂移清单.md` 等未编目文件。**建议**：编目清单改为自动生成；或规定"新增/移动文档的 PR 必须同步更新 00-README"（写入 AGENTS.md）。

**A6.（高）根目录 README 与 docs/README 存在两套目录说法**
两处各自描述 docs 结构且互不一致。**建议**：确定 `docs/README.md` 为唯一目录真相，根 README 只保留一句"完整目录见 docs/README.md"。

**A7.（中）`config.yaml:7` 引用 `docs/04-config-reference.md`（漂移清单 D-07 已挂账未修）**
实际路径 `docs/tech/06-CONFIG-REFERENCE.md`。**建议**：漂移清单不能只记不修——给每项漂移加 owner 与目标版本。

**A8.（中）`06-CONFIG-REFERENCE.md` 与 config.yaml 多处脱节（D-03/D-06/D-12 相关）**
- eviction 四项（`config.yaml:143-146`）代码未使用；
- `cost_control` 只剩 pricing/usage，"预算 4 项未接线"；
- `tools.image_analysis` 整节被 Pydantic 丢弃（见代码报告 高-10）。
文档未标注这些是"死配置"。**建议**：06 文档给每个配置项加"✅ 已生效 / ⚠️ 规划中未接线"状态标记。

**A9.（中）`05-API-REFERENCE.md` 应标注每个端点的权限级别**
`preview` vs `full` 是本系统核心概念，但 API 文档未标注哪些端点需 full。**建议**：每行加 `🔒full` / `👁preview` 标记。

**A10.（低）根 README 未提多用户/权限模型**
README 通篇未提白名单、preview/full 权限、分享功能——这是部署者与使用者最需要知道的概念。**建议**：在"快速开始"后加一节"权限模型速览"。

## 三、B 类：编目与结构

**B1.（高）建立 `docs/user/` 用户手册目录——使用者受众完全缺位**
目前 tech 15 篇 + ops 16 篇 + prompt 18 篇，面向最终用户的操作手册 0 篇。
"如何上传知识""招聘分析怎么用""分享链接怎么创建和撤销"只散落在技术文档里。
**建议**：新增 `docs/user/01-快速上手.md`、`02-知识库管理.md`、`03-招聘分析.md`、`04-分享与权限.md`、`05-常见问题.md`；前端帮助中心直接渲染这些 md，一次编写两处复用。

**B2.（高）文档命名语言与风格不统一**
`漂移清单.md`、`待确认项清单.md`（中文无编号）与 `01-xxx.md`（编号英文风格）混用，不利于排序与机器处理。**建议**：非编号文件统一入子目录或加编号前缀。

**B3.（中）`docs/tech/.facts/`、`.validation/` 隐藏目录无说明**
两个点开头目录用途未在任何文档说明。**建议**：在 00-README 说明用途与生命周期，或加入 .gitignore 不入库。

**B4.（中）`prompt/` 目录 18 个提示词文件无索引**
文件名已较自明（`1-1-…` 至 `5-2-…`），但没有 README 说明各提示词的用途、适用阶段、输入输出契约。**建议**：加 `prompt/README.md` 索引表：文件名 / 用途 / 对应工程环节 / 维护状态。

**B5.（中）`docs/CHANGELOG.md` 体量会持续膨胀**
碎片机制（`changelog_add.py`）设计得很好，但 CHANGELOG 本体只增不减。**建议**：按季度切分（`CHANGELOG-2026Q3.md`），主文件保留最近一个季度 + 链接。

**B6.（中）`BACKLOG.md` 与 `tech/11-EVOLUTION.md` 职责重叠**
两者都承载"未来要做的事"。**建议**：BACKLOG 放"排期/状态"，11-EVOLUTION 只保留架构演进方向，互相引用。

**B7.（低）`RAG常见问题汇总.md` 孤悬根目录**
从文件名看是面向使用/维护的 FAQ，但未入任何目录体系（README 与 docs/README 均未提及）。**建议**：迁入 `docs/user/05-常见问题.md` 或 `docs/faq/`。

**B8.（低）`AGENTS.md` 建议补充"文档协作"章节**
现有协作约定已覆盖代码与 CHANGELOG，但文档协作（谁负责 00-README 编目同步）没有约定——这正是 A5 编目过期的根因。**建议**：在 AGENTS.md 第 1 条认领表附近，加"新增/移动文档必须同步 00-README"的硬约定。

## 四、C 类：逻辑与内容质量

**C1.（高）漂移清单（12 项）无闭环机制**
`docs/tech/漂移清单.md` 是很好的实践，但 12 项中多数长期未修。**建议**：给漂移清单加两列——`责任人`、`目标修复版本`；把"漂移清零"纳入发版 checklist。

**C2.（高）问题台账分散在三个地方**
问题记录分散在 `docs/tech/未修复问题跟踪.md`、`docs/tech/漂移清单.md`、`docs/codeReview/*/`，无统一视图，容易"记录了但没人再看"。**建议**：以 GitHub Issues（或单一 TODO 文件）为唯一 issue 台账，其他文档只引用编号。

**C3.（中）技术文档缺少"请求-响应"级端到端时序图**
`01-ARCHITECTURE.md` 有组件图，但新增的招聘分析链路（收集 → 缓存 → MCP 内核 → 分析 → 报告，涉及 4 层缓存）复杂且无一张完整时序图，新协作者要读 5 个文件才能拼出全貌。**建议**：补 `01b-招聘分析数据流时序图`（mermaid）。

**C4.（中）运维文档缺"故障排查决策树"**
ops 目录 16 篇覆盖部署/监控/备份，但缺"症状 → 原因 → 处置"式排障手册（例如"分享页 404 → 检查 expires_at 字段"）。**建议**：新增 `ops/16-故障排查手册.md`，按症状而不是按模块组织。

**C5.（中）`docs/README.md` 缺"按人群导航"**
当前导航按目录组织，四类受众各自需要不同入口。**建议**：在 docs/README 顶部加"我是…→ 我该读…"路由表：

| 角色 | 首选 | 次选 |
|---|---|---|
| 使用者 | `docs/user/01-快速上手` | FAQ |
| 开发者 | `docs/tech/00-README` | `AGENTS.md`、`05-API-REFERENCE` |
| 维护者 | `docs/ops/00-README` | `CHANGELOG`、`漂移清单` |
| 拥有者 | `README.md` | `BACKLOG`、`11-EVOLUTION` |

**C6.（中）CHANGELOG 碎片流程缺使用时机说明**
`changelog_add.py` / `changelog_merge.py` 机制很好，但文档只在 AGENTS.md 提到"写变更记录"，未说明何时合并、谁合并。**建议**：明确"合并时机=发版时，合并人=发版人"，写进 AGENTS.md 第 2 条。

**C7.（低）`02-DATA-MODELS.md` 应补充 job_cache / analysis_cache / 分享存储的模型**
新增的缓存与分享数据结构未入数据模型文档。**建议**：补充，并标注每个存储的持久化方式与并发安全性（与代码审查报告 S2 呼应）。

**C8.（低）`docs/COORDINATION.md` 认领表无超时清理机制**
认领后忘记删除行是常见问题。**建议**：要求开始时间用 ISO 格式，超过 48h 未收工的行由下次例会清理（写进 AGENTS.md 即可）。

## 五、D 类：可发现性与维护机制

**D1.（高）建立"文档新鲜度"自动化检查**
`docs/tech/00-README.md` 头部 `last-updated: 2026-09-09`、`based-on-commit: 010d83e`，而仓库已领先 208 个提交——文档陈旧却无任何告警。**建议**：写脚本比对"代码高频变更文件（如 `job/market.py`）所对应文档的 last-updated"，超阈值在 CI 与漂移清单标红。

**D2.（中）API 文档自动生成**
FastAPI 自带 OpenAPI schema，05-API-REFERENCE 却是手写的。**建议**：核心端点用 `openapi.json` 生成再人工补"业务说明"，至少保证路径/参数永不漂移。

**D3.（中）文档引用断链检查**
`docs/README.md` 引用的文件（如 A 类所示多处）无存在性检查。**建议**：并入 D1 脚本，检查所有 md 内部相对链接的存在性，防止 A 类断链复现。

**D4.（低）给 docs 目录加 markdownlint 规范**
标题层级、frontmatter 必填字段（`last-updated`/`based-on-commit`）目前靠自觉。**建议**：加 lint 规则 + pre-commit hook，frontmatter 缺失直接拦截。
