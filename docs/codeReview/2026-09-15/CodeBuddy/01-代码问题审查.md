## 二、严重问题（7 条，建议立即修复）

### 严重-1 `--forwarded-allow-ips "*"` 使全站限流可被一键绕过

`deploy/Dockerfile:177-178`：

```dockerfile
CMD ["uvicorn", "app.api.server:app", "--host", "0.0.0.0", "--port", "8000",
     "--forwarded-allow-ips", "*"]
```

无条件信任任意 `X-Forwarded-For`。攻击者每个请求换一个 XFF 值即可重置 `api/middleware.py:79` 的滑动窗口限流（key=`user:ip`），绕过 `/auth/reset-password` IP 限流与 LLM 接口配额，实现暴力破解/刷量。
**修复**：只信任真实代理网段（如 `--forwarded-allow-ips "172.16.0.0/12"`），或改由 nginx 写 `X-Real-IP`、后端只读该头。

### 严重-2 异常原文回传客户端（系统性 S1）

`job.py:105,149,177,190,253`、`upload.py:259,294,325,357,386,443,499,563,588,613`、`share.py:499`：

```python
raise HTTPException(status_code=500, detail=f"职位分析失败: {e}")   # job.py:105
inner_err = json.dumps({"type": "error", "detail": f"内部错误: {e}"})  # share.py:499 SSE
```

`server.py` 注释与 `core/exceptions.py` 的 `include_details=False` 明确了 SEC-04 规范，但业务路由整体绕过。泄露内部路径、表名、Chroma/MCP 内部错误、LLM Provider 信息。
**修复**：注册 `@app.exception_handler(Exception)` 全局处理器，统一返回通用信息 + trace_id；CI 门禁禁止 `detail=f"...{e}"`。

### 严重-3 消息追加 read-modify-write 竞态，并发下丢消息

`storage/share_storage.py:168-185`（`BaseStorage.append_list_item`）：

```python
exists, entries = self._load()   # ① 读全量
entries.append(entry)            # ② 内存改
self._save(entries)              # ③ 整体覆盖写
```

三步间无任何锁。`share.py:475-483` 连续 append user/assistant 两条消息即可交错覆盖；`chat_share_storage.py:157` 复制了同一不安全实现；多 worker 部署 100% 触发。
**修复**：短期加 `asyncio.Lock`；中期改 append-only JSONL（`aiofiles` 追加写）；长期迁移 SQLite/PG（11-EVOLUTION 已规划）。

### 严重-4 `user_storage` 非原子写，崩溃即丢全部用户

`storage/user_storage.py:32-34` 直接 `open(path, "w")` 覆盖写。`json_storage.py:80-90` 已有 tmp+`os.replace` 原子实现却未复用。写一半被 kill/OOM → 用户表截断 → **全站无法登录**。
**修复**：复用 JsonStorage 的原子写（抽 `atomic_write_json()` 工具），并保留最近 3 份 `.bak`。

### 严重-5 分享链接无过期、无访问审计，SSE 问答无限流

`storage/share_storage.py:135-145`：

```python
if not isinstance(share.get("expires_at"), str) or not share["expires_at"]:
    return True          # 无 expires_at → 永久有效
```

- 创建分享未强制 `expires_at` → 永久有效；`is_active` 从未被置 False（死字段），`delete`/`deactivate` 语义重复；
- 无 `view_count`/`last_accessed_at`，所有者对滥用毫无感知；
- `share.py:380` 的分享问答 SSE 接口未挂 RateLimiter，可刷爆 token 成本。
**修复**：创建时强制默认 7 天过期（上限 30 天）；记录访问数并展示；SSE 挂 IP/分享维度限流；提供"一键全部失效"。

### 严重-6 JWT 黑名单纯内存 + token 90 天，登出形同虚设

`core/auth.py:27` `_jti_blacklist: set[str] = set()` 单 worker 内存实现；`config.yaml:322` token 有效期 2160h=90 天，前端 `Settings.tsx:157` 还声称"到期自动续租"。重启/多 worker/容器重建 → 黑名单清空 → 登出后的 token 依然长期可用。
**修复**：黑名单外置 Redis；改 access(2h)+refresh(7d) 双 token；有效期降为 7 天并提供"活跃会话管理/强制下线"。

### 严重-7 `/auth/reset-password` 仅需邮箱即可重置任意账号

`api/routes/auth.py:290-302`：重置只要求"已登录 + 知道目标邮箱"，**无邮件验证码、无旧密码确认**。结合严重-1 的限流绕过，构成账号接管链路。
**修复**：重置走邮箱验证码（Redis 存 5 分钟一次性）；对未知邮箱返回与已知邮箱完全相同的响应（防枚举）；成功后吊销该用户全部 token。

## 三、高优先级问题（17 条）

### 高-1 `job.py:398` 默认关键词硬编码 `"Agent"`，与配置不同源 → 职位串档/丢失

```python
keyword = (body.keyword or "").strip() or "Agent"    # job.py:398
```

同文件 `fetch` 分支读 `cfg.job.default_keyword`（config.yaml:437），`cache/save` 分支却硬编码。改配置后 fetch 用新值、save 用旧值 → `search_id` 算成另一个搜索的 ID，**职位存错搜索**或**凭空消失**，极难复现定位。
**修复**：抽 `_resolve_job_params()` 统一三条分支；或 keyword 为空直接返回 422。

### 高-2 三套 job 缓存：无锁 + 非原子写 + 无容量上限（S2）

`job_cache.py:28 _save` 用 `write_text` 直接覆盖（非原子）；`cleanup_expired` 只清空 `jobs` 列表，**条目本身永不删除** → `data/job_cache.json` 无限膨胀；并发搜索互相覆盖。
**修复**：统一抽 `AtomicJsonStore`（`asyncio.Lock` + tmp+`os.replace` + 按 `created_at` LRU 淘汰到 N 条）。

### 高-3 `market.py:263-290` 传入 jobs 时跳过缓存读取并强制覆盖 → 重复烧 LLM

"职位收集→批量分析"主流程永远不读缓存直接调 LLM，然后 `save_report_cache` 无脑覆盖。用户重复点分析 = 每次都付全额 LLM 费用，且没有 `force` 参数让用户选择刷新。
**修复**：提供 jobs 时也先查缓存，命中即返回（除非 `force=true`）；前端暴露"重新分析"按钮并展示 `analyzed_at`。

### 高-4 `analysis_cache.py:21` key 不含用户画像 → 画像更新后返回旧分析

```python
key_src = f"{user_id}|{jd_text[:3000]}"
```

key 只有 user_id + JD。用户更新简历/求职方向后，14 天内同一 JD 仍返回**基于旧画像**的匹配度与建议，且无任何提示——静默错误结果。
**修复**：把 profile 版本（`updated_at` 或内容 hash）纳入 key；profile 更新时主动失效该用户分析缓存。

### 高-5 `market.py:267` search_id 为空时回退"最新一份报告" → 跨搜索串数据

`get_cached_report(user_id, sid if search_id else None)`：`None` 语义为"该用户最新报告"。search_id 缺失时会把**上一次完全不同搜索**的报告返回，跨搜索数据串档。
**修复**：search_id 为空视为无缓存直接重算，或强制必填。

### 高-6 `llm_factory.py:81-90` `LLMCallStats.records` 无界增长 → OOM

每次 LLM 调用 append 一条记录，从不清理、无上限（`metrics_collector.py` 的 `LLM_HISTOGRAM.observe` 同样无界）。长期运行内存持续上涨，OOM 时若正写 `user_storage` 会连锁触发严重-4。
**修复**：改 `collections.deque(maxlen=1000)` 或聚合 P50/P95/P99 后丢弃原始记录。

### 高-7 流式 LLM token 统计恒为 0 + 内核调用只打日志 → 成本统计系统性失真

流式路径未累积 `usage_metadata`；`market.py` 的 MCP 内核调用 `_log_kernel_usage()` 只打日志不进成本统计。而招聘分析主流程恰恰大量用流式+内核 → 用量页/配额/成本归集全部偏低甚至为零。
**修复**：优先切 LangChain `usage_metadata`；不可用时按输出字符估算（中文约 1.5 字符/token）并标注 `estimated=True`。

### 高-8 `upload.py:169` 先全量 `read()` 再判大小 → 50MB 限制形同虚设

```python
content = await file.read()
if len(content) > settings.max_upload_size: ...
```

攻击者发 2GB 请求体，服务端在判断前就已分配 2GB 内存，单请求即可 DoS。
**修复**：先读 `content-length` 预判 413；或分块读累计超限即断；nginx 层 `client_max_body_size` 兜底。

### 高-9 async 路由中大范围同步阻塞 IO，阻塞事件循环

`job_cache`/`analysis_cache`/`market`/`upload_service` 的 `read_text`/`write_text`/`shutil.copy2`（`upload_service.py:113` 最大 50MB）/`os.walk` 全部在 `async def` 路由里直接调用。缓存文件越大，所有并发请求（包括其他用户的 SSE 流）一起卡住。
**修复**：包 `asyncio.to_thread()` 或改 `aiofiles`；高频小文件可考虑进程启动时加载一次 + 写时落盘。

### 高-10 `tools.image_analysis` 整节配置被 Pydantic 静默丢弃

`config.yaml:244-251` 定义了 `image_analysis`（max_images、vision_model、cache_ttl、prompt），但 `core/config.py` 的 `ToolsConfig` **没有该字段** → Pydantic 默认忽略额外字段，配置完全不生效，且无任何告警。
**修复**：`ToolsConfig` 加 `model_config = ConfigDict(extra="forbid")`（全局对所有 Config 生效），缺字段直接启动失败——所有"配置改名后悄悄失效"问题一并根治。

### 高-11 `config.yaml:301` 弱密钥默认值 + `AuthConfig.jwt_secret` 死字段

```yaml
jwt_secret: "${JWT_SECRET:-sekb-dev-secret-change-in-production}"
```

代码实际走 `auth.py:45` 直读环境变量并做强度校验（该默认值会被 `sekb-dev` 弱密钥标记拒绝），配置文件里的 `jwt_secret` 是**死字段**，且字面量弱密钥提交在仓库里误导部署者。
**修复**：删除该行，或注释"此字段已废弃，实际读取 JWT_SECRET 环境变量"。

### 高-12 `access.py` 裸 except 降级为 preview + async 依赖中做同步 IO

`core/access.py` 的 `access_level()` 用裸 `except Exception` 吞掉所有错误并降级为 `preview`——用户存储 IO 故障时**正式用户被静默降权**且无日志。同时该 async 依赖内部调用同步 `user_storage.get()`。
**修复**：except 里加 `logger.exception`；IO 失败应显式报错而非静默降权。

### 高-13 `browser_client.py` 每次调用新建 `httpx.AsyncClient`，无连接复用、无关闭保证

`services/browser_client.py` 每个请求 `async with httpx.AsyncClient(...)` 新建连接（含 TLS 握手），未复用连接池；超时配置靠调用方自觉。
**修复**：模块级单例 client + `lifespan` 关闭；统一默认超时（连接 5s / 读取 30s）。

### 高-14 `job.py:305-317` 列表接口 O(N) 次全量 JSON 读写

`list_searches` 对每个 search 依次调 `get_cached_report`（内部 `_load()` 读全文件）、`_report_matched`（又 `get_by_search_id` 再读一次），加上 `expired_search_ids` 与 `list_searches` 本身——**一次列表请求 = 2N+3 次全量文件读取与解析**。搜索积累 50 个后该接口明显变慢。
**修复**：一次 `_load()` 后在内存中完成全部关联查询。

### 高-15 `job.py:126-128` 命中缓存时为刷新时间戳全量重写文件

```python
cached = jc.get_cached_jobs(key)
if cached:
    jc.save_cached_jobs(key, cached)   # 仅为刷新 ts，重写整个缓存文件
```

用户每次点搜索都触发一次全量序列化+写盘，放大高-2 的竞态窗口。
**修复**：时间戳刷新改为惰性（读时不写，仅过期判断用），或节流到 1 小时一次。

### 高-16 `cache_key` 不含 page/limit/source → 翻页结果互相覆盖

`job_cache.py:15` 的 key 只含 keyword/city/days，不含分页与来源。第 2 页结果会**覆盖第 1 页**的同 key 缓存，用户回看时数据错乱。
**修复**：key 加入 `page/limit/source`；或缓存改为"key→按页聚合"的结构。

### 高-17 前端 `api.ts:74` 401 硬编码跳 `/login`，生产子路径下 404

生产部署在 `/sekb/` 子路径（`API_BASE=/sekb/api/v1`），`window.location.href = '/login'` 会跳到不存在的路径。应使用 `window.location.assign(import.meta.env.BASE_URL + 'login')` 或经 react-router 跳转。

## 四、中优先级问题（18 条）

### 中-1 `middleware.py:79` 限流窗口 dict 无界增长

滑动窗口按 `user:ip` 存 dict，恶意伪造大量不同 user_id（配合严重-1 的 XFF 伪造）后窗口永不清理 → 内存泄漏。**修复**：定期清理过期窗口（如每 60s），或用 Redis ZSET。

### 中-2 Prometheus 指标以 `user_id` 为标签 → 高基数

`metrics.py` 给请求/LLM 指标打 `user_id` 标签，用户量增长后时序基数爆炸，Prometheus 内存与查询性能劣化；`daily_cost_usd` Gauge 从不重置，跨天累加语义错误。**修复**：标签改为 user 分桶或去掉；daily 指标加定时重置或用 Counter 按天标签。

### 中-3 审计日志同步阻塞 IO + 全局 `threading.Lock`

`core/audit.py` 在 async 请求路径中同步写文件且持全局锁，高并发下成为串行化点。**修复**：改异步队列（`asyncio.Queue` + 后台消费者）。

### 中-4 `upload_service` MD5 索引非原子写；且函数名 `compute_md5` 实为 SHA-256

`upload_service.py:87` 实现是 SHA-256，但函数名、常量 `MD5_FILE`、字段名 `md5`、前端契约全部叫 md5——命名与实现不一致是严重隐患（第三方按 MD5 对账永远对不上）。**修复**：统一改名 `sha256` 并在前端契约同步。

### 中-5 `upload.py:480 /reclassify` 串行逐文件调 LLM

对每个文件 `await classify_document(...)`，100 个文件 = 100 次串行 LLM 往返，极易请求超时。**修复**：`asyncio.gather` 并发（限并发数 5-10）或改后台任务 + 进度查询接口。

### 中-6 `upload.py:114-131 / 428 /files` 全量加载无分页

`/upload/files` 与 `/upload/series` 都 `list_entries(limit=5000)` 全量返回，`/files` 路由无分页参数。知识库到几千条后前端一次拉全量。**修复**：加 `page/page_size` 与游标分页。

### 中-7 `upload.py:507-528 / 570-578` 返回值计数撒谎

`reclassified += 1` 不管更新是否成功都计数；`updated_files += 1` 对未变更文件也加；`entries_updated: len(entries)` 返回的是**总条目数**而非实际更新数。前端展示的"成功 N 条"是错的。**修复**：只在实际变更时计数。

### 中-8 `upload.py:205-222` 异步上传立即返回 `status="success"`，失败无感知

`async_process=true` 时直接返回 success，无任务 ID、无状态查询接口，后台 LLM 失败用户毫不知情。**修复**：返回 `task_id`，提供 `GET /upload/tasks/{id}` 查询进度/失败原因。

### 中-9 `job_cache.parse_key` 用 `|` 分割，keyword/city 含 `|` 即解析错乱

用户输入 `AI|ML` 作为关键词时 `parse_key` 按 `|` 切分，`keyword`/`city` 展示错位、search_id 错乱。**修复**：改用 `json.dumps([keyword, city])` 做 key，或对输入先校验剔除 `|`。

### 中-10 `job.py:347` count 字段语义混乱

`len(entry.get("jobs") or []) or entry.get("count", 0)`：过期时 jobs 为空回退 count——三个来源（缓存、实时、报告）的 count 含义不一致，前端无法区分"0 条职位"与"已过期"。**修复**：明确 `job_count`/`expired` 两个字段。

### 中-11 `_report_matched` 严格集合相等过严 → "报告已过期"长期误报

`job.py:314-315` 判断报告与当前职位集合是否匹配用严格集合比较，只要少一条/多一条就判不匹配。职位列表天然动态，用户几乎永远看到"报告已过期"。**修复**：改为覆盖率阈值（如 ≥80% 即有效）并显示具体覆盖比例。

### 中-12 `chat_share` 无 `set_active`、`expires_at` 永不过期，`is_active` 死字段

`chat_share_storage.py` 的 `is_active` 字段无任何代码置 False；会话分享永久有效。**修复**：同严重-5，统一分享过期策略。

### 中-13 `guard.py` 解析回退 `"true" in s` 误伤正常输入

`core/guard.py` LLM 返回解析失败时回退用 `"true" in s` 判断——用户问"这段代码 if true 会怎样"即被误拦。**修复**：解析失败按"未拦截"处理并告警，而非字符串包含。

### 中-14 `feedback_service` 3 次踩永久物理删除知识条目，无回收站

用户手滑反馈 3 次即物理删除知识库条目，不可恢复、无确认、无管理员审核。**修复**：改为软删除（标记 `disabled`），管理员可恢复；触发阈值前二次确认。

### 中-15 `user_id` 用时间戳生成，碰撞时返回 500 而非 409

`user_storage.py` 的 `create` 捕获唯一约束冲突后 `raise HTTPException(500)`——同一毫秒注册两个用户时客户端看到服务器错误而非"请重试"。**修复**：冲突重试生成新 ID 或返回 409。

### 中-16 `bootstrap.py` L3 加载只捕获 ImportError

LangChain 各集成包版本组合复杂，`RuntimeError`/`AttributeError` 同样会炸启动流程。**修复**：捕获更宽并打详细日志（哪些包缺失/版本不兼容）。

### 中-17 `job_service.parse_job_files` 无文件大小/类型校验

解析用户上传的职位文件未限制大小与行数，恶意大文件直接拖垮解析。**修复**：复用 upload 的 size 上限并限制行数。

### 中-18 `json_storage` 临时文件固定名，跨进程不安全

`json_storage.py` 写 `xxx.tmp` 固定名，两个进程同时写同一 tmp 再 replace 会互相踩。**修复**：tmp 名加 `uuid/pid` 后缀（`NamedTemporaryFile` 同目录）。

## 五、低优先级问题（8 条）

### 低-1 `usage_service` 10 次串行 Redis 往返

聚合统计逐 key 串行 GET，可 pipeline/MGET 一次完成，减少 P95 延迟。

### 低-2 `EmbeddingFactory`/`LLMFactory` 懒加载无锁

`core/embedding.py` 首次并发请求会重复初始化多个实例。**修复**：加锁或 lifespan 预热。

### 低-3 `core/audit.py` 审计时间戳秒级 + `%z` 非标准格式

跨时区审计对齐困难。**修复**：统一 `datetime.now(timezone.utc).isoformat()`。

### 低-4 前端 `stores/chat.ts:186` `streamControllers` Map 泄漏

流结束后 controller 从不 `delete`（仅删会话/取消时清理），长会话累积泄漏。**修复**：`finally` 中 `streamControllers.delete(displayConvId)`。

### 低-5 前端消息 id 用 `msg_${Date.now()}`，同毫秒重复

`stores/chat.ts:103` 连续发送/接收在 同一毫秒时 key 冲突导致 React 渲染异常。**修复**：加自增序列或 `crypto.randomUUID()`。

### 低-6 前端 `render.tsx` 34 处 `any`

`features/job/render.tsx` 与后端返回结构强耦合又无类型定义，后端字段变更编译期无感知。**修复**：按 `docs/tech/05-API-REFERENCE.md` 生成 TS 类型（可用 openapi-typescript 从 FastAPI schema 自动生成）。

### 低-7 前端 `Chat.tsx` 等组件 console.log 遗留

生产构建未剥离调试日志，`logger.ts` 亦无生产级别控制。**修复**：vite 配置 `esbuild.drop` 或按 `import.meta.env.PROD` 过滤。

### 低-8 `job_cache.py:37` 使用 `hashlib.md5`

虽然仅用于 ID 派生非安全用途，但 FIPS 环境会直接报错。**修复**：改 `hashlib.sha256(..., usedforsecurity=False)` 或直接用 `uuid5`。
