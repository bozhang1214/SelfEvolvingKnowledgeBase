# 使用者视角功能优化建议（破除"知识的诅咒"）

- **审查日期**：2026-09-15
- **审查人**：CodeBuddy
- **立场声明**：本报告的出发点是**设计者对系统了如指掌，因此看不见新用户看不见的坑**——即"知识的诅咒"。所有建议均按"**一个第一次打开这个系统的用户**会遇到什么"来组织，而非"代码该怎么改"。
- **配套阅读**：`01-代码问题审查.md`（技术根因）、`02-文档优化建议.md`（文档补缺）

---

## 一、核心发现

系统在**能力密度**上很强（多 Agent、RAG、招聘分析、分享、反馈闭环），但存在三类典型的"设计者盲区"：

1. **错误信息对设计者有意义、对用户是噪音**：后端把 `str(e)` 原文回传，用户看到 `ConnectionError: Could not connect to Chroma at localhost:8000` 完全不知道该做什么；而前端 `stores/chat.ts` 里大量 `catch {}` 静默处理走向另一个极端——**出了错界面毫无变化**，用户以为自己操作失败。
2. **系统状态对用户不可见**：后台任务无进度、异步上传无感知、缓存刷新无提示、用量限制到达前无预警。用户分不清"系统在忙"还是"系统挂了"。
3. **首次使用无引导**：功能说明页对**预览账号**也显示全部 6 个功能卡片，点击后无提示地弹回首页；新用户不知道自己受限、更不知道为什么。

---

## 二、A 类：首次使用与引导

**建议-1（高）新增"新人向导"：注册后 3 步走完核心价值**
现状：注册完进系统，看到功能说明页和一排菜单，不知道第一步做什么。**建议**：注册/首次登录后走 3 步——① 上传一份简历或文档 ② 试着问一个问题 ③ 跑一次职位分析。每步可跳过，完成后再进主页，用 localStorage 记录完成状态。

**建议-2（高）每个页面首次打开时有空态引导（Empty State）**
现状：文件页、知识库页、职位页空的时候一片空白，用户不知道该点哪。**建议**：空态放一句说明 + 一个主操作按钮 + 一行"为什么需要它"。例：文件页空态"还没有知识文件 → [上传第一个文件]，上传后 AI 对话就能引用你的资料了"。

**建议-3（高）"预览账号"权限限制必须显式告知**
现状：`AppLayout.tsx` 对预览用户直接静默跳回首页；Home 页 6 个功能卡片对预览用户照样全部可点，点了原地弹回——用户只会认为"这个功能坏了"。**建议**：① 受限菜单项加"预览"角标并保留可点击，点击后弹出说明"你的账号为预览权限，此功能需正式权限，可在设置中查看/申请"；② 欢迎页顶部常驻一条权限提示条；③ 403 响应在前端统一转为用户可读文案（目前 `api.ts` 只处理 401）。

**建议-4（中）菜单与页面名需要"这是什么"的一句话解释**
"文件管理"和"知识库"对设计者是两个概念（原始文件 vs 向量条目），新用户完全分不清。**建议**：菜单项加副标题或 hover 提示——"文件管理（原始文档）""知识库（已索引内容，可直接被 AI 引用）"。

## 三、B 类：错误信息与可理解性

**建议-5（高）错误提示统一改为"发生了什么 + 我能怎么办"两段式**
现状：后端 `detail=f"...{e}"` 把异常原文抛给前端直接 toast。用户看到 `ConnectionError: ...` 只会干瞪眼。**建议**：建立错误码字典（`E_UPLOAD_TOO_LARGE` / `E_QUOTA_EXCEEDED` / `E_SERVICE_BUSY` 等），前端按码映射成"文件超过 50MB，建议拆分后重传"这类人话；原文只进日志，每条错误附可复制的 trace_id。

**建议-6（高）消灭"静默失败"**
`stores/chat.ts` 中 `loadConversations` / `selectConversation` / `createConversation` / `deleteConversation` / `renameConversation` / `togglePin` 全部 `catch {}` 后不做任何事。用户点"删除会话"界面毫无反应，会反复点。**建议**：所有 catch 至少给一次 toast；写操作失败时保留原状态，避免用户误以为成功。

**建议-7（中）区分"网络 / 服务 / 操作"三类反馈**
现在一律一个 toast。**建议**：网络断开给可重试气泡并自动重试；服务异常给"稍后重试 + 联系管理员（trace_id）"；操作类（重名、超限额）给出即时可修正的指引。

**建议-8（中）长耗时操作要有进度，不能只有转圈**
招聘分析（多轮抓取 + 多次 LLM）、批量重分类、大文件上传动辄数十秒到数分钟，目前只有 loading。**建议**：返回任务进度（阶段 + 百分比 + 已耗时），前端显示进度条与阶段文案（"正在抓取第 3/10 个来源…"），并支持中途取消。

## 四、C 类：系统状态可见性

**建议-9（高）用量与额度必须可见，并在到达前预警**
设置页目前无用量展示，而系统已有 `usage_service` 与 Redis 计数。用户不知道还差多少额度，直到被拒绝。**建议**：设置页加"本月用量"卡片（对话次数/token/上传量/分析次数），80% 黄色预警，100% 明确告知何时重置。

**建议-10（高）配额超限要给出可操作的下一步**
被限流时（429）提示不明。**建议**：明确写"今日分析已达上限（10 次），明天 00:00 重置"或"如需提升额度请联系管理员"，而不是"请求过于频繁"。

**建议-11（中）上传结果要能追溯，异步处理不能"假成功"**
`upload.py` 在 `async_process=true` 时立即返回 `status="success"` 但 `chunks=0`，无任何任务 ID；后台解析失败用户永远不知道。**建议**：返回 task_id，文件列表显示"处理中 / 已就绪 / 失败（原因）"三态，失败项提供"重试"按钮。

**建议-12（中）提供"我的会话与设备"管理**
JWT 有效期 90 天且前端声称"到期自动续租"，用户无法知道自己在哪些设备登录过，也无法主动踢出。**建议**：设置页加"活跃会话"（设备 / IP / 最近活跃时间）列表与"全部下线"按钮。

## 五、D 类：信任与控制（分享与账号资产）

**建议-13（高）分享链接要有安全感与控制感**
分享无过期、无访问统计（见代码报告 严重-5），用户不敢分享也不知道分享后发生了什么。**建议**：创建时强制选有效期（7 / 14 / 30 天），列表显示访问次数与最近访问时间，提供"复制链接 / 提前失效 / 全部失效"。

**建议-14（中）提供数据导出与账号注销入口**
用户投入大量知识后关心"能不能带走 / 能不能删干净"。**建议**：设置页提供"导出我的全部数据"（文件 + 知识条目 + 对话记录，JSON/Markdown 打包）与"注销账号（连带删除全部数据）"并二次确认。

## 六、E 类：招聘分析核心流程

**建议-15（高）分析结果的"新鲜度"必须对用户显式说明**
`analysis_cache` key 不含用户画像（代码报告 高-4）、`_report_matched` 用严格集合比较导致几乎永远显示"已过期"（中-11）。用户看到的结果可能基于旧画像，或看到莫名其妙的"报告已过期"。**建议**：① 报告头部显示"生成于 X 月 X 日，基于当时职位列表（N 条，当前覆盖 85%）"；② 画像更新后提示"你的求职方向已更新，建议重新分析"；③ 覆盖率 ≥80% 即视为有效，不显示"过期"。

**建议-16（高）"重新分析"要成为用户可主动触发的按钮，并提示会消耗额度**
目前传入 jobs 时跳过缓存直接重算（代码报告 高-3），用户重复点会重复花钱却毫无提示。**建议**：明确区分"查看报告（缓存）"与"重新分析（消耗额度）"，后者二次确认显示预计消耗。

**建议-17（中）搜索历史需要可命名、可删除、可对比**
搜索历史只按关键词展示，用户多次搜索"Java 后端 / 上海 / 30 天"后无法区分。**建议**：支持重命名搜索、删除历史、以及"对比两个搜索的职位差异"。

**建议-18（中）抓取失败要有"部分成功"的明确表达**
多来源抓取时部分平台失败（反爬/超时）目前语义不清。**建议**：显示"10 个来源中 8 个成功，2 个失败（平台 A 超时、平台 B 需登录）"，并允许只对失败来源重试。

## 七、F 类：日常交互细节

**建议-19（中）移动端与响应式适配**
`AppLayout` 侧边栏固定 220px 且无折叠，移动设备上会挤爆内容区。**建议**：Sider 支持折叠 + 窄屏切换为抽屉式；长列表（职位、文件）改用卡片流。

**建议-20（中）关键操作需要撤销与二次确认**
反馈"踩"3 次会永久物理删除知识条目（代码报告 中-14），无回收站、无确认；删除会话/知识同样直接消失。**建议**：删除一律走软删除 + "撤销（10 秒内）"提示；知识条目的自动下线改为标记禁用，由用户在回收站确认删除。

## 八、落地优先级建议

| 优先级 | 建议编号 | 理由 |
|---|---|---|
| P0 | 3、5、6、9 | 直接决定用户"能不能用明白"，成本小收益最大 |
| P0 | 15、16 | 招聘分析是核心卖点，结果可信度出问题会直接摧毁信任 |
| P1 | 1、2、10、11、13 | 首用转化与信任感 |
| P2 | 4、7、8、12、14、17、18 | 体验完整性 |
| P3 | 19、20 | 覆盖面与容错 |

> 一句话总结：**这个系统不缺能力，缺的是"把能力解释给用户听"的那层。** 建议把"用户可读性"作为每次功能上线的验收项之一：新功能上线时自查三件事——出错时用户看到什么？系统在忙时用户看到什么？这个功能为什么存在用户看得懂吗？
