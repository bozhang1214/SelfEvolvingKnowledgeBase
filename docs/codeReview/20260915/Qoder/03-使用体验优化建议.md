# SEKB 使用体验优化建议（使用者视角）

> 审查日期：2026-09-15　审查角色：Qoder（任务 #9）
> 审查立场：**站在"第一次接触本系统的用户"角度**，克服"知识的诅咒"——设计者因为懂 RAG / Agent / L1-L3 记忆 / MCP / 白名单，会默认用户也懂，从而忽略对新用户显而易见的问题。
> 审查方式：只读审查（未修改任何代码/配置），逐页面、逐模块阅读前端 `pages/`、后端 `api/routes/`、`cli/`、`config.yaml`、`.env.example`、`README.md`、`start_*.sh`，从代码/配置推断真实使用流程与体验断点。
> 约束遵循：每条建议均附**代码/配置证据（文件:行号）**，问题描述使用**用户语言**（非技术语言）。

## 用户画像（本报告代入的三类使用者）

- **新手用户**：刚注册，不懂 RAG / 知识库 / Agent，只想"传点资料、问几个问题"。
- **日常用户**：已上手，每天用对话 / 文件 / 知识 / 资讯 / 职位功能。
- **高级用户 / 管理员**：需要自己部署、配置白名单、管理知识、分享、跑 CLI。

---

## 一、优化建议清单（按优先级 P0 → P3 排列）

### UX-01　注册后"功能凭空消失"，且无任何解释（预览账号静默锁定）
- **优先级**：P0（对新手等同于阻断使用）
- **场景**：首次使用 / 注册上手
- **目标用户**：新手
- **问题描述**：新用户高高兴兴注册、登录，却发现左侧菜单只剩「功能说明」和「科技资讯」两项，对话、文件、知识库、职位全都不见了；就算手动在地址栏输入 `/chat`，页面也会**不声不响地跳回首页**，没有一句提示告诉他"你没有权限"或"该怎么开通"。用户会以为系统坏了、注册失败，直接流失。
- **证据**：
  - 预览账号只能看到 2 个菜单：`frontend/src/components/Layout/AppLayout.tsx:37-38`、`:44-45`
  - 访问受限路由时静默 `Navigate to="/"`，无 toast、无提示：`AppLayout.tsx:93-98`
  - 权限判定来自环境变量白名单 `ALLOWED_EMAILS`，注册接口对新用户完全不提示会被降级：`backend/app/core/access.py:41-47`、`backend/app/api/routes/auth.py:46-93`
  - 后端 403 文案"预览账号无权限执行此操作，仅可浏览科技资讯"只在直接调 API 时才出现，前端页面并不展示：`access.py:62-65`
- **优化建议**：
  1. 注册/登录成功后，若判定为预览账号，**立刻用一条醒目横幅说明**："当前为预览账号，仅开放科技资讯浏览；如需完整功能请联系管理员将你的邮箱加入白名单"，并给出可复制的管理员邮箱/申请入口。
  2. 被限制的菜单项不要直接隐藏，而是**置灰 + 加锁图标 + 悬浮说明"预览账号不可用"**，让用户知道"功能存在，只是我没权限"，而不是"功能不存在"。
  3. 手动访问受限路由时，跳转到一个**明确的"无权限"页面**（带原因与开通指引），而非静默弹回首页。

### UX-02　首页"快速上手"是死的装饰，不反映用户真实进度
- **优先级**：P1
- **场景**：首次使用 / 上手引导
- **目标用户**：新手
- **问题描述**：首页有一块"快速上手"五步引导（登录→上传→提问→采集→资讯），但它永远是灰色未激活状态，无论用户做到哪一步都不会点亮、不会打勾、不能点击跳转，纯粹是摆着看的文字。新手无法用它获得"我下一步该做什么"的指引。
- **证据**：`frontend/src/pages/Home.tsx:70-76`（步骤定义）、`:130-137`（`current={-1}` 写死，永不高亮；步骤项不含跳转/完成态）。
- **优化建议**：把静态 Steps 改成**任务清单式引导**：根据后端真实状态（是否已上传过文件、是否已发起过对话）自动打勾，每一步配"去完成"按钮直接跳到对应页面；全部完成后收起或显示"你已上手 🎉"。

### UX-03　分享链接对"没有账号的朋友"完全打不开
- **优先级**：P1
- **场景**：分享
- **目标用户**：日常 / 高级（分享者）+ 被分享者（外部人）
- **问题描述**：用户生成知识库/对话分享链接，兴冲冲发给同事或朋友，对方点开却被**强制要求登录/注册**才能看。分享的初衷是"给别人看"，但被分享者若无账号就寸步难行，分享价值大打折扣。分享者也不清楚"原来对方必须先注册"。
- **证据**：
  - 知识库分享页未登录即跳登录：`frontend/src/pages/SharedKnowledge.tsx:64-67`
  - 对话分享页未登录即跳登录：`frontend/src/pages/SharedChat.tsx:33-36`
  - 分享弹窗文案"其他**已注册用户**可通过链接……"藏在表单底部小字，创建时不显眼：`frontend/src/pages/Knowledge.tsx:508`
- **优化建议**：
  1. 提供**"公开只读分享"选项**（无需登录、带链接有效期/访问口令），默认关闭由分享者勾选，满足"发给外部人看看"的真实诉求。
  2. 若维持登录墙，则在**生成链接时就明确告知**"对方需注册登录后才能查看"，并在链接落地页对未登录用户展示友好的"你需要先登录/注册才能查看 XXX 的分享"引导页，而非直接甩到通用登录框。

### UX-04　对话页没有"点赞/点踩"，用户无法反馈答案好坏
- **优先级**：P1
- **场景**：对话 / 反馈闭环
- **目标用户**：日常
- **问题描述**：系统主打"越用越聪明、知识自迭代"，但对话界面上每条 AI 回复只有"复制/重生成/转发"，**没有点赞/点踩**。用户想告诉系统"这条答得好/答得差"却无处可点，也就无法驱动所谓的自迭代，"反馈"这件事对用户不可见、不可用。
- **证据**：
  - 前端消息操作区仅有复制/编辑/重生成/转发，无评分按钮：`frontend/src/pages/Chat.tsx:653-706`
  - 后端其实**已提供**消息反馈接口 `POST /conversations/{id}/rate`（thumbs_up/down + comment）却未被前端使用：`backend/app/api/routes/conversations.py:11`、`:46-51`
- **优化建议**：在每条 AI 回复的操作区加"👍/👎"按钮，点踩时弹出可选的原因/补充框，直接对接已有的 rate 接口；并在某处（如设置或对话顶部）让用户感知"你的反馈已被用于改进"。

### UX-05　对话太多时找不到历史会话，且无法跨会话搜索
- **优先级**：P1
- **场景**：对话 / 历史检索
- **目标用户**：日常
- **问题描述**：左侧会话列表随使用时间越来越长，但**没有搜索框**，用户想找回"上周问过的那个问题"只能一条条翻。右侧"历史提问"抽屉只能搜**当前这一个会话内**的提问，帮不上跨会话查找。
- **证据**：
  - 会话侧栏只有列表 + 新建按钮，无搜索：`frontend/src/pages/Chat.tsx:387-460`
  - "历史提问"抽屉数据源仅取 `currentMessages` 里的用户消息（限当前会话）：`Chat.tsx:228-231`、`:821-856`
- **优化建议**：在会话列表顶部加**搜索框**（按标题/消息内容检索所有会话），后端补充跨会话搜索接口；搜索结果高亮命中片段并可直接跳转定位。

### UX-06　README 里的 API 试用示例缺少登录令牌，照抄必 401
- **优先级**：P1
- **场景**：配置部署 / API 试用
- **目标用户**：高级 / 管理员 / 开发者
- **问题描述**：想通过 curl 试接口的人，照着 README 的示例发请求会**直接被拒（401）**——因为示例里既没有 `Authorization: Bearer <token>`，请求体里还写着早已废弃的 `user_id`/`conversation_id` 字段。文档给人"能直接跑"的错觉，实际第一步就卡住。
- **证据**：`README.md:270-328`（curl / Python 示例均无鉴权头；`:277-281` 请求体含 `conversation_id`，`:313-315` 仍演示旧字段）。实际所有业务路由都依赖 JWT 与 `require_full_access`：`backend/app/api/routes/chat.py:45-49`。
- **优化建议**：更新 API 示例，先演示"注册/登录拿 token"，再在后续请求带上 `Authorization` 头；或直接引导用户用 FastAPI 自带的 `/docs` Swagger UI 在线试用（并在 README 显著位置给出 `/docs` 地址）。

### UX-07　自部署者不知道 `ALLOWED_EMAILS` 的存在，一不小心把自己锁成预览
- **优先级**：P1
- **场景**：配置部署
- **目标用户**：管理员
- **问题描述**：`.env.example` 只列了 4 个变量，**没有 `ALLOWED_EMAILS`**。管理员若从别处听说或误设了这个变量，就会发现所有非白名单用户（包括自己新注册的号）都被降级成预览账号，却怎么也想不到是这个没写进模板的变量在作怪。
- **证据**：
  - `.env.example` 仅含 DEEPSEEK/BOCHA/LANGSMITH/JWT/DATABASE：`backend/.env.example:1-30`
  - 而白名单开关恰恰读的是未在模板出现的 `ALLOWED_EMAILS`：`backend/app/core/access.py:19-24`
  - `config.yaml` 还引用了 `VISION_LLM_API_KEY` 等同样未在 `.env.example` 说明的变量：`backend/config.yaml:243-246`
- **优化建议**：在 `.env.example` 补齐 `ALLOWED_EMAILS`（含"留空=所有人完整功能；填写=仅名单内邮箱可用完整功能"的注释）与 `VISION_LLM_*` 等变量说明；启动日志里明确打印"当前白名单是否启用、命中邮箱数"，避免管理员踩坑。

### UX-08　满屏专业黑话，新手看不懂"这系统能帮我干嘛"
- **优先级**：P1
- **场景**：首次使用
- **目标用户**：新手
- **问题描述**：首页和功能卡片大量使用 RAG、PDCA、L1/L2/L3 记忆、MCP、向量检索、多智能体、锚定度等术语。一个只想"存资料 + 问问题"的新手，读完仍不明白**具体能替他做什么**，术语反而制造距离感。
- **证据**：`frontend/src/pages/Home.tsx:24`（"RAG 检索增强"）、`:40`（"向量检索""三级分类"）、`:88-91`（"多智能体（PDCA）""检索增强"）；`README.md:33-49` 同类术语密集。
- **优化建议**：面向用户的界面改用**结果导向的大白话**（如"你上传的资料，问问题时会自动帮你翻出来作答"），把 RAG/PDCA/L3 等术语收进"了解更多"折叠区或帮助文档；功能卡片首句先讲"能帮你做什么"，再讲"怎么做到的"。

### UX-09　对话冷启动没有示例问题，新手对着空白框发懵
- **优先级**：P2
- **场景**：对话 / 首次使用
- **目标用户**：新手
- **问题描述**：新建对话后中间只有一句"开始一个新对话 / 在下方输入消息"，没有任何示例提问或引导卡片。不懂系统能做什么的新手，面对空白输入框常常不知道第一句该问什么。
- **证据**：`frontend/src/pages/Chat.tsx:528-534`（空状态仅两行文字，无建议 prompt）。
- **优化建议**：空状态放 3-5 个**可点击的示例问题卡片**（如"帮我总结我上传的 XX 文档""根据我的知识库回答……"），点击即填入输入框，降低第一步门槛。

### UX-10　知识库条目看不到全文，内容被截断到 200 字
- **优先级**：P2
- **场景**：知识管理
- **目标用户**：日常 / 高级
- **问题描述**：知识库列表里每条内容都被省略号截断，用户想完整阅读某条知识（确认入库对不对、复习一下）却**没有"点开看全文"的入口**，只能看到前一小段。
- **证据**：
  - 后端把内容硬截断到 200 字返回：`backend/app/api/routes/knowledge.py:37`
  - 前端表格该列 `ellipsis: true`，且无行点击/详情抽屉：`frontend/src/pages/Knowledge.tsx:300-306`、`:409-423`
- **优化建议**：为知识条目增加**详情查看**（点击行弹出抽屉显示完整内容、来源、分类、入库时间）；列表可仍截断，但要提供"查看全文"的明确入口。

### UX-11　知识库无法手动新增一条知识，只能靠上传文件
- **优先级**：P2
- **场景**：知识管理
- **目标用户**：日常
- **问题描述**：用户突然想到一条要记住的内容，想直接"手写一条"存进知识库，却发现整个页面只有搜索/分享/刷新，**没有"新增条目"按钮**，唯一入库途径是去"文件管理"上传文档。心智模型上"知识库应该能手动记一条"落空。
- **证据**：`frontend/src/pages/Knowledge.tsx:392-423`（工具栏仅搜索/分享/我的分享/刷新，无新增）；空状态引导也只指向上传文档：`:422`。
- **优化建议**：增加"手动新增知识"按钮（弹窗填写内容 + 选择分类），复用后端入库能力；空状态同时给出"上传文档"和"手动记一条"两个入口。

### UX-12　分类目录树默认全折叠，用户以为"没有分类"
- **优先级**：P2
- **场景**：知识管理
- **目标用户**：新手 / 日常
- **问题描述**：进入知识库，左侧"分类目录"默认只展开一个"全部 (N)"，三级分类全被折叠起来。新手第一眼看到的是近乎空的侧栏，感知不到系统"自动三级分类"的卖点，也不会主动去点开。
- **证据**：`frontend/src/pages/Knowledge.tsx:377`（`defaultExpandedKeys={['__all__']}`，仅展开"全部"）。
- **优化建议**：默认展开到一级分类（甚至二级），让用户一眼看到分类结构；或提供"展开/折叠全部"按钮。

### UX-13　文件页把后端环境变量名甩给普通用户
- **优先级**：P2
- **场景**：文件上传 / 错误提示
- **目标用户**：新手 / 日常（非技术）
- **问题描述**：当知识库未启用时，文件页弹出红色错误"请检查后端配置（KNOWLEDGE_BASE_ENABLED / ChromaDB 连接）"。普通用户根本不知道这是什么、也改不了，只会更慌。这类信息只对管理员有意义。
- **证据**：`frontend/src/pages/Files.tsx:463-471`（尤其 `:468` 直接暴露环境变量与组件名）。
- **优化建议**：面向普通用户改为"知识存储暂未就绪，暂时无法上传，请稍后再试或联系管理员"，把技术细节收进"查看详情/给管理员看"的折叠区。

### UX-14　"上传历史"与"已上传文件"两个列表含义混淆
- **优先级**：P2
- **场景**：文件上传
- **目标用户**：日常
- **问题描述**：文件页同时存在"上传历史（刷新即清空）"和"已上传文件（跨会话持久）"两块列表，名字相近、内容重叠，用户分不清该看哪个、为什么一个会消失一个不会。
- **证据**：`frontend/src/pages/Files.tsx:636-687`（上传历史，`:647` 注明"仅当前会话有效，刷新页面会清空"）与 `:735-776`（已上传文件，跨会话持久）。
- **优化建议**：合并为**一个"我的文件"列表**（持久），把"本次上传"作为临时高亮/筛选态；或明确改名"本次上传（临时）"与"全部文件（永久）"并加说明图标。

### UX-15　生成周报/月报要等约 10 分钟，却没有进度与预期提示
- **优先级**：P2
- **场景**：科技资讯
- **目标用户**：日常
- **问题描述**：点"生成周报/月报"后，实际要等约 10 分钟（前端最长轮询 30 分钟），但界面只有按钮转圈 + 一句 toast，没有进度条、没有预计耗时、没有"可离开页面稍后回来看"的说明。用户会以为卡死或反复点击。
- **证据**：`frontend/src/pages/News.tsx:162-176`（`pollTask` 每 15s × 120 ≈ 30 分钟）、`:291-302`（生成按钮，无耗时预告）、`:156-161`（注释自述"实测约 10 分钟"）。
- **优化建议**：点击前用确认框告知"生成约需 10 分钟，可先去忙别的，完成后回来刷新即可"；生成中显示带阶段文案的进度提示；完成/失败通过站内通知或页面横幅明确告知，而不是只靠一闪而过的 toast。

### UX-16　职位分析默认关键词/城市/薪资是"设计者自己的求职条件"
- **优先级**：P2
- **场景**：职位分析
- **目标用户**：新手 / 日常
- **问题描述**：不输入关键词直接点"收集职位"，系统会用默认「Agent / 北京 / 月薪 50K」去搜——这是**开发者本人的求职画像**，对其他用户毫无意义甚至误导（"为什么全是 Agent 岗？"）。典型的"知识的诅咒"：把自己的上下文当成了默认值。
- **证据**：`backend/config.yaml:436-440`（`default_keyword: Agent`、`default_city: 北京`、`default_min_salary_k: 50`）；前端提示"空则用默认「Agent」"：`frontend/src/pages/Job.tsx:719-721`。
- **优化建议**：默认关键词/城市/薪资应**留空或中性**，未填时引导用户"请先输入你想找的岗位关键词"，而不是替他假设；若要保留默认，也应在 UI 上明确"当前使用的是默认条件，可修改"。

### UX-17　职位分析一页塞了 5 个大 Tab，信息架构过重
- **优先级**：P2
- **场景**：职位分析 / 导航
- **目标用户**：新手
- **问题描述**：「职位分析」单页内含"职位收集 / 批量分析 / 单职位分析 / 历史报告 / 投递计划"5 个模式，还叠加"搜索历史=当前搜索上下文"这类抽象概念。新手一进来就要理解一堆相互依赖的模式与状态，认知负荷很高。
- **证据**：`frontend/src/pages/Job.tsx:83-84`（5 种 analysisMode）、`:588-592`（Tabs）、`:606-608`（"选中即切换「当前搜索」……"抽象说明）。
- **优化建议**：按用户目标重新组织为**引导式流程**（收集 → 分析 → 投递），用向导/步骤条串起来；把"搜索历史/当前搜索"这类内部状态用更直观的方式表达（如顶部一个"当前正在看：XX 关键词"的下拉切换器 + 一句人话说明）。

### UX-18　投递计划的日期要手打 `YYYY-MM-DD`，没有日期选择器
- **优先级**：P2
- **场景**：职位分析 / 投递计划
- **目标用户**：日常
- **问题描述**：新增/编辑投递记录时，"投递日期""出结果日期"是纯文本框，要用户手动敲 `YYYY-MM-DD`，格式错了还影响冷却期计算。这是本可一键选择的常见交互。
- **证据**：`frontend/src/pages/Job.tsx:1358-1367`（两个日期均为 `Input` + placeholder `YYYY-MM-DD`）。
- **优化建议**：改用日期选择器（DatePicker），并对"出结果日期晚于投递日期"等做基本校验，避免手打错误。

### UX-19　设置页把"BOSS 直聘扫码登录"这类小众功能放在显眼位置且解释很技术
- **优先级**：P3
- **场景**：设置
- **目标用户**：日常 / 新手
- **问题描述**：设置页里赫然出现"BOSS 直聘登录"卡片，说明文字是"获取 Cookie……当前 BOSS 采集受反爬限制，登录作为备用"。绝大多数用户用不到，也不理解 Cookie/反爬，放在通用设置里造成干扰与困惑。
- **证据**：`frontend/src/pages/Settings.tsx:229-239`（卡片与文案）、`:63-120`（扫码流程实现）。
- **优化建议**：把这类高级/实验性集成收进"高级设置"折叠区，或用大白话说明"仅在需要采集 BOSS 直聘职位时才用得到"，避免干扰主线设置（账号/密码/偏好）。

### UX-20　对话分享无法集中管理与撤销，和知识库分享是两套割裂的机制
- **优先级**：P3
- **场景**：分享 / 一致性
- **目标用户**：日常 / 高级
- **问题描述**：知识库分享有"我的分享"列表可管理/撤销，但**对话分享没有集中列表**——想撤销某条对话分享，只能重新打开那条分享链接、且恰好自己是所有者时才看得到撤销按钮。两套分享入口与管理方式不一致，用户难以形成统一心智。
- **证据**：
  - 知识库"我的分享"列表 + 撤销：`frontend/src/pages/Knowledge.tsx:514-553`
  - 对话分享仅在生成时复制链接，无管理列表：`frontend/src/pages/Chat.tsx:361-380`
  - 对话分享的撤销入口只存在于打开后的分享页且限所有者：`frontend/src/pages/SharedChat.tsx:94-98`
- **优化建议**：做一个统一的"我的分享"中心（知识库分享 + 对话分享合并列出，均可复制/撤销/看状态），交互模式保持一致。

### UX-21　分享创建时无法设置有效期，但分享却会"过期"
- **优先级**：P3
- **场景**：分享
- **目标用户**：日常 / 高级
- **问题描述**：创建分享时只能填标题和范围，**没有有效期选项**；但分享列表里却会出现"已过期"状态。用户无法控制分享活多久，也不知道它什么时候、为什么会失效。
- **证据**：创建分享表单仅 title + category：`frontend/src/pages/Knowledge.tsx:490-510`；列表却有 `has_expired`/"已过期"状态：`:536-539`、`ShareItem` 定义 `:37-49`。
- **优化建议**：创建分享时提供有效期选择（如 7 天/30 天/永久），并在列表清晰展示到期时间；到期前给出提醒。

### UX-22　后端把原始异常字符串直接当错误信息返回给用户
- **优先级**：P3
- **场景**：知识管理 / 错误提示
- **目标用户**：日常（非技术）
- **问题描述**：删除/查询知识条目失败时，返回的是"删除失败: {底层异常原文}"这类信息，可能包含堆栈/内部术语，用户看不懂也帮不上忙，还有信息泄露风险。
- **证据**：`backend/app/api/routes/knowledge.py:193`（`f"查询条目失败: {e}"`）、`:208`（`f"删除失败: {e}"`）、`:274`（`f"更新分类失败: {e}"`）。
- **优化建议**：对外返回稳定的用户友好文案（如"删除失败，请稍后重试"），把异常详情只写进服务端日志（附 trace_id 供排查）。

### UX-23　CLI 用固定的 `default` 用户，和网页端数据是两个世界
- **优先级**：P3
- **场景**：CLI / 配置部署
- **目标用户**：高级 / 开发者
- **问题描述**：命令行 `sekb chat` 把用户 ID 写死成 `default`，意味着**在 CLI 里产生的对话/知识，登录后在网页端看不到**（网页端按真实 user_id 隔离）。开发者用 CLI 调试完，切到网页却"数据不见了"，非常困惑。CLI 也没有上传文件、管理知识等命令，能力与网页端不对等。
- **证据**：`backend/app/cli/chat.py:68-69`（`USER_ID = "default"`）、`backend/app/cli/main.py:52-87`（子命令仅 chat/eval/rag-eval/health，无上传/知识管理，也无登录/指定用户）。
- **优化建议**：CLI 支持 `--user`/登录态，让数据落到与网页端一致的用户空间；在 CLI 帮助与 README 中**明确说明**默认 `default` 用户与网页账号数据相互独立，避免误解；补齐上传/知识查询等常用命令。

### UX-24　多栏固定侧边布局，窄屏/手机上无法使用
- **优先级**：P3
- **场景**：响应式 / 可访问性
- **目标用户**：全体（移动端）
- **问题描述**：对话、文件、知识、资讯、分享等页面普遍使用固定像素宽的左侧栏（220/280/300/360px）+ `100vh` 布局。在手机或窄窗口下，侧栏会挤占甚至压垮主内容区，没有"抽屉式收起"的响应式处理，移动端基本没法用。
- **证据**：`frontend/src/pages/Chat.tsx:387`（Sider 280）、`Knowledge.tsx:370`（Sider 280）、`News.tsx:273-277`（Sider 300）、`SharedKnowledge.tsx:234`（Sider 360）、`AppLayout.tsx:68-69`（Sider 220 + `minHeight:100vh`）。
- **优化建议**：小屏下把侧栏改为可收起的抽屉（Drawer）+ 顶部汉堡按钮；对 `100vh`、固定宽度做媒体查询适配，保证移动端可用。

### UX-25　删除会话/撤销分享等破坏性操作，确认提示过于简略
- **优先级**：P3
- **场景**：对话 / 一致性
- **目标用户**：日常
- **问题描述**：删除对话只弹"确定删除？"，没有说明"删除后消息不可恢复"；用户可能低估后果误删重要对话。破坏性操作的提示应统一说明影响范围与不可逆性。
- **证据**：`frontend/src/pages/Chat.tsx:417`（`title="确定删除？"`）；知识条目删除同样简略：`frontend/src/pages/Knowledge.tsx:359`。
- **优化建议**：破坏性确认统一文案，明确后果（如"删除后该对话及其消息将无法恢复，确定删除？"），危险按钮用红色并二次确认。

### UX-26　缺乏统一的"任务/通知中心"，异步结果只能靠手动刷新
- **优先级**：P3
- **场景**：通知 / 反馈
- **目标用户**：日常
- **问题描述**：资讯生成、批量职位分析、知识入库等都是异步/耗时任务，但系统没有一个统一的"我的任务/通知"入口。用户离开页面后，任务完成与否只能回来手动点"刷新列表"才知道，容易错过结果或被 toast 一闪而过忽略。
- **证据**：资讯靠轮询 + toast（`frontend/src/pages/News.tsx:178-192`）；职位报告靠手动"刷新"按钮（`frontend/src/pages/Job.tsx:1131`）；无全局通知组件（`AppLayout.tsx` 顶栏仅用户下拉，无通知铃铛：`:56-87`）。
- **优化建议**：在顶栏增加"通知/任务"铃铛，聚合异步任务的进行中/已完成/失败状态，点击可直达结果；关键完成事件（日报生成好、分析报告就绪）主动推送。

## 二、按用户旅程归纳的"体验断点地图"

```
注册 ──────────► 上手 ──────────► 日常使用 ──────────► 高级 / 管理
  │                │                   │                     │
  │                │                   │                     │
[断点A]         [断点B]             [断点C]               [断点E]
预览账号静默     快速上手是死的      对话找不到历史         API 示例缺 token→401
锁定，菜单凭空   装饰，不引导；      无法反馈答案好坏；     ALLOWED_EMAILS 未写进
消失+静默弹回    满屏黑话看不懂；    知识条目看不到全文、   .env.example，误设即
首页，零解释     对话冷启动无示例    不能手动新增；分类树   自锁；CLI 用 default
(UX-01)         问题(UX-02/08/09)   默认折叠(UX-05/04/     用户，与网页数据割裂
                                    10/11/12)              (UX-06/07/23)
                                       │
                                    [断点D]
                                    分享对无账号者打不开(UX-03)；
                                    对话分享无法集中管理、无有效期
                                    (UX-20/21)；异步任务无通知中心、
                                    只能手动刷新(UX-15/26)
                                       │
                                    [贯穿全程] 窄屏/移动端不可用(UX-24)；
                                    破坏性操作提示过简(UX-25)；
                                    错误信息暴露技术细节(UX-13/22)
```

**旅程解读**：
- **注册→上手**是断点最密集、最致命的阶段：新手可能连"为什么功能没了"都不知道（UX-01），加上术语墙（UX-08）和死引导（UX-02），首次体验极易劝退。
- **日常使用**的核心痛点是"反馈闭环缺失"（UX-04）与"知识管理不符合心智"（看不到全文、不能手动记、分类默认折叠）。
- **分享**是被低估的断点：对外分享给无账号者直接失败（UX-03），对内管理割裂（UX-20/21）。
- **高级/管理**主要是**文档与配置的可发现性**问题：README 示例跑不通、关键环境变量没写进模板、CLI 与网页数据不通。

## 三、最值得优先改善的 Top 5

| 排名 | 编号 | 建议 | 为什么最该先做 |
|---|---|---|---|
| 1 | **UX-01** | 预览账号给出明确提示 + 受限菜单置灰说明 + 无权限页 | 直接决定新用户"留不留得下来"，当前是静默劝退，等同阻断使用 |
| 2 | **UX-03** | 分享支持无账号只读访问（或至少落地页友好引导） | 分享是核心传播动作，现在发给外部人直接打不开，功能价值被腰斩 |
| 3 | **UX-04** | 对话加点赞/点踩，接通已有 rate 接口 | 后端能力已就绪、改造成本低，且直接支撑产品"自迭代"的核心卖点 |
| 4 | **UX-08 + UX-02** | 首页去黑话 + 把"快速上手"改成可交互的任务引导 | 低成本、高感知，显著改善新手第一屏的理解与下一步行动 |
| 5 | **UX-06 + UX-07** | 修正 README 的 API 试用示例 + 在 `.env.example` 补齐 `ALLOWED_EMAILS` 等变量 | 让自部署者/开发者第一步就能跑通，避免"照文档做却处处碰壁" |
