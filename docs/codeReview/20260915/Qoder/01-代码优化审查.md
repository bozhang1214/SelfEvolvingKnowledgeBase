### CODE-01 · P0 · 安全编码 · browser-service

**证据**：`browser-service/app.py:52-99`

```python
def _read_cookies() -> dict[str, dict[str, Any]]:
    if not COOKIES_FILE.exists():
        return {}
    try:
        return json.loads(COOKIES_FILE.read_text(encoding="utf-8"))
    except (json.JSONDecodeError, OSError):
        return {}

@app.post("/cookies")
async def import_cookie(req: ImportCookieReq) -> dict[str, Any]:
    """导入某站点的登录 Cookie（持久化）。"""
    if not req.cookie_header.strip():
        raise HTTPException(400, "cookie_header 不能为空")
    data = _read_cookies()
    data[req.site] = {"cookie_header": req.cookie_header.strip(), "updated_at": _now()}
    _write_cookies(data)
    return {"site": req.site, "ok": True}
```

**问题分析**：`/cookies`（POST 写入、GET 列出）以及 `/login/qr/*`、`/scrape` 等端点**完全没有任何鉴权中间件**。BOSS 直聘等站点的登录 Cookie 明文存储在 `/data/cookies.json`。虽然 docker-compose 未把 browser 服务端口映射到公网（仅内网 `sekb_net`），但**同一 Docker 网络内的任意容器**（含被攻破的 rsshub、第三方镜像）都能读取/篡改其他用户的招聘站点登录态，等于账号劫持。`_write_cookies` 还是同步 IO + 无锁读-改-写（见 CODE-08）。影响面：登录凭据泄露、越权采集。

**优化建议**：
1. 为 browser-service 增加共享密钥鉴权（如 `X-Internal-Token` 头，backend 与 browser 通过环境变量约定同一 token），在所有写/敏感端点校验。
2. Cookie 落盘加密（`cryptography.Fernet` + 密钥来自环境变量），或至少限制文件权限 `chmod 600`。
3. 用 FastAPI `Depends` 统一注入鉴权，避免逐端点遗漏。
```python
async def require_internal_token(x_internal_token: str = Header(...)):
    if x_internal_token != os.getenv("BROWSER_INTERNAL_TOKEN"):
        raise HTTPException(403, "invalid internal token")
```

### CODE-02 · P1 · 性能/安全 · api/routes/upload

**证据**：`backend/app/api/routes/upload.py:169-174`

```python
content = await file.read()
if len(content) > upload_service.MAX_FILE_SIZE_BYTES:
    raise HTTPException(
        status_code=413,
        detail=f"文件过大：{len(content)} bytes，上限 {upload_service.MAX_FILE_SIZE_BYTES} bytes",
    )
md5 = upload_service.compute_md5(content)
```

**问题分析**：先把**整个上传文件读进内存**（`await file.read()`），再判断是否超过 50MB 上限。攻击者上传一个 2GB 文件，在大小校验生效前进程已把 2GB 载入内存 → 直接 OOM，构成拒绝服务（DoS）。`MAX_FILE_SIZE_BYTES` 的守卫形同虚设。并发几个大上传即可打挂单 worker 后端。

**优化建议**：分块流式读取，边读边累计大小，超限立即中断；或依赖前置 nginx `client_max_body_size` 做第一道拦截，应用层用流式写盘 + 累计计数：
```python
size = 0
with open(tmp_path, "wb") as f:
    while chunk := await file.read(1024 * 1024):
        size += len(chunk)
        if size > MAX_FILE_SIZE_BYTES:
            raise HTTPException(413, "文件过大")
        f.write(chunk)
```
同时在 `deploy/nginx.conf` 显式设置 `client_max_body_size`。

**证据 B**：`backend/app/api/middleware.py:108-116`

```python
# 获取客户端 IP
client = scope.get("client")
client_ip = client[0] if client else "unknown"

group, limit = self._match_group(path, method)
```

**证据 C**：`backend/app/core/audit.py:134-146`（对照——审计模块正确处理了 XFF）

```python
# 优先使用 X-Forwarded-For（经 Nginx 反代），回退到 direct client IP。
forwarded = request.headers.get("x-forwarded-for")
if forwarded:
    return forwarded.split(",")[0].strip()
```

**问题分析**：三处共同暴露两类缺陷：
1. **限流按 `scope["client"]` 取 IP**，而生产部署下 backend 只经 nginx 反代（compose 里 `127.0.0.1:8000`），`scope.client` 恒为 nginx 容器 IP。于是**所有真实用户共用同一个限流桶**——一个用户刷接口会让全站 429，限流按 IP 隔离的设计目标完全失效。审计模块 `audit.py` 已经正确解析 XFF，说明团队知道该问题，但限流中间件未同步修复，属于一致性缺陷。
2. **`--forwarded-allow-ips "*"` 信任任意来源的 X-Forwarded-\* 头**。若 backend 端口被意外暴露（或内网其他容器直连），攻击者可伪造 XFF 头绕过基于 IP 的审计/限流、污染审计日志。应仅信任反代网段。

**优化建议**：
1. 限流中间件复用 `audit.py` 的真实 IP 提取逻辑（解析 XFF 首个 IP），抽成公共 `get_client_ip(scope)` 工具函数，避免两处行为分叉。
2. `--forwarded-allow-ips` 收窄为 nginx 容器所在网段（如 `172.16.0.0/12` 或具体反代 IP），而非 `*`。

### CODE-04 · P1 · 配置治理/安全 · config.yaml

**证据**：`backend/config.yaml:299-303`

```yaml
  auth:
    token_expire_hours: 2160           # 90 天（配合前端滑动续租，实际接近免登录）
    jwt_secret: "${JWT_SECRET:-sekb-dev-secret-change-in-production}"
    password_min_length: 8
    rate_limit_login_per_minute: 5
```

**问题分析**：`jwt_secret` 提供了一个**已知的弱默认值** `sekb-dev-secret-...`。一旦生产环境忘记设置 `JWT_SECRET` 环境变量（compose 里 `JWT_SECRET: ${JWT_SECRET:-}` 允许为空），系统会静默回退到这个写在公开配置文件里的默认密钥 → 任何人都能用它签发合法 JWT，完全绕过鉴权。同时 `token_expire_hours: 2160`（90 天）过长，令牌泄露后风险窗口极大。

**优化建议**：
1. 去掉弱默认值，改为**缺失即启动失败**（fail-fast）：`jwt_secret: "${JWT_SECRET}"`，并在 `AppConfig` 校验阶段断言非空、长度 ≥ 32。
2. 生产环境启动时若检测到使用默认/弱密钥则拒绝启动或打 ERROR 级告警。
3. 令牌有效期缩短至合理值（如 2h access + refresh token 滑动续租）。

### CODE-05 · P1 · 性能 · core/llm_factory

**证据**：`backend/app/core/llm_factory.py:86-104`

```python
records: list[LLMCallRecord] = field(default_factory=list)
...
@property
def retry_rate(self) -> float:
    retried_calls = sum(1 for r in self.records if r.retried)
    return retried_calls / self.total_calls if self.total_calls > 0 else 0.0
```

以及 `llm_factory.py:465`：

```python
delta_records = self.stats.records[snapshot.records_len:]
```

**问题分析**：`LLMStats.records` 是**无界列表**，每次 LLM 调用都 append 一条记录且**永不裁剪**。后端是常驻单 worker 进程（Dockerfile `--workers 1`），运行数天/数周后 records 会累积到数十万条，内存单调增长直至 OOM——这是典型的慢速内存泄漏。此外 `retry_rate` 每次访问都 O(n) 全量遍历，随 records 增长越来越慢；`delta_records = records[snapshot_len:]` 依赖「记录只增且顺序稳定」，但并发请求下切片会包含其他请求的记录，跨请求统计污染（见 CODE-24 关联）。

**优化建议**：
1. records 改为**有界环形缓冲**（`collections.deque(maxlen=N)`，N 如 1000），或仅保留聚合计数器（total/retried/failed/token/cost 累加），明细写入外部时序存储（已有 Prometheus）。
2. `retry_rate` 等比率用累加计数器 O(1) 计算，不遍历列表。
3. 单次请求的成本统计用 contextvar 隔离，不依赖全局列表切片。

### CODE-06 · P1 · 性能 · memory/short_term

**证据**：`backend/app/memory/short_term.py:79-86`

```python
self._messages: dict[str, list[BaseMessage]] = {}
self._summaries: dict[str, list[str]] = {}
self._conv_users: dict[str, str] = {}
self._locks: dict[str, asyncio.Lock] = {}
```

**问题分析**：L1 短期记忆用四个**进程内无界字典**，key 为 conv_id，只有显式 `clear()` 才移除。随着会话不断累积，`_messages`（含完整消息历史）、`_locks`（每会话一个 `asyncio.Lock` 对象）永不回收 → 常驻进程内存持续增长。尤其 `_locks` 每新建会话就插入一个 Lock 且从不清理，长时间运行会积累成千上万个僵尸 Lock 对象。叠加纯内存实现本身的问题：进程重启丢失全部 L1、多 worker 下各进程记忆不一致。

**优化建议**：
1. 引入 LRU + TTL 淘汰（如 `cachetools.TTLCache`），对 `_messages/_summaries/_locks` 设定最大会话数上限，超限淘汰最久未活跃会话。
2. 会话结束/删除时联动清理对应 key（`_locks` 尤其要在会话归档时 pop）。
3. 中期看，L1 也应具备可选的 Redis 落地（项目已有 L2 Redis），解决多 worker 一致性与重启丢失。

### CODE-07 · P1 · 性能/错误处理 · browser-service

**证据**：`browser-service/app.py:113-170`

```python
# 进行中的扫码会话：qr_id -> 会话状态（含持有登录 Cookie 的 APIRequestContext）
_QR_SESSIONS: dict[str, dict[str, Any]] = {}
...
_QR_SESSIONS[qr_id] = {
    "ctx": ctx,          # Playwright APIRequestContext，持有登录态
    "qr_id": qr_id,
    "second_uuid": "",
    "phase": "waiting_scan",
    "created": time.time(),
}
```

过期仅在 `_boss_qr_status` 轮询时检查（`app.py:190-193`）：

```python
if phase == "waiting_scan":
    if time.time() - sess["created"] > _QR_TTL:
        _log(f"{qr_id} 第一张码过期")
        return {"phase": "expired"}     # 注意：只返回 expired，未 ctx.dispose() 也未 pop
```

**问题分析**：扫码会话字典 `_QR_SESSIONS` 里每个条目持有一个 Playwright `APIRequestContext`（`ctx`）。清理只在客户端**主动轮询** `/login/qr/status` 时触发；若客户端调用 `/login/qr/start` 后**不再轮询**（用户关闭页面、网络中断），该会话永不过期检查，`ctx` 永不 `dispose()`，`_QR_SESSIONS` 条目永不 `pop` → Playwright 上下文与内存双重泄漏。更严重的是即便命中过期分支（L191-193），代码只返回 `expired` 却**没有 `await ctx.dispose()` 也没有从字典移除**，泄漏依旧。长期运行会耗尽 Playwright 资源。

**优化建议**：
1. 增加后台清理任务（`asyncio.create_task` 定期扫描 `_QR_SESSIONS`，对 `created` 超时的会话 `await ctx.dispose()` 并 `pop`）。
2. 过期分支必须 `await ctx.dispose(); _QR_SESSIONS.pop(qr_id, None)` 后再返回。
3. 用带 TTL 的结构（如 `cachetools.TTLCache`）承载会话，并在淘汰回调里 dispose 上下文。

```python
from app.agents.job.job_cache import cache_key, make_search_id, save_cached_jobs
```

**问题分析**：大量 import 散布在函数体内。部分确为破循环依赖（合理），但很多只是习惯性或为「延迟加载」，导致：依赖关系不透明（无法从文件头看出模块依赖）、IDE 静态分析/重构困难、同一模块多处重复 import。尤其 `job.py` 几乎每个端点都重复 import `job_cache`。

**优化建议**：区分真实循环依赖（保留延迟 import 并加注释说明原因）与习惯性延迟 import（上提到模块顶部）；重复 import 合并；循环依赖优先通过重构模块边界/`TYPE_CHECKING` 解决，而非到处延迟 import。

### CODE-39 · P3 · 可维护性 · memory/short_term

**证据**：`backend/app/memory/short_term.py:310-314, 350-354`

**问题分析**：L1 压缩的摘要/合并提示词与「不超过 200 字」/「不超过 300 字」等字数上限**硬编码在方法内**。项目已有 `PromptRegistry`（`AppContext.prompt_registry`）统一管理提示词（且 compose 把 `./prompt` 目录只读挂载以便免重建镜像改提示词），但 short_term 的提示词未走该体系，造成提示词管理割裂、无法热更新。

### CODE-40 · P3 · 错误处理/可读性 · browser-service

**证据**：`browser-service/app.py:178-179, 272-275`

```python
def _log(msg: str) -> None:
    print(f"[boss-qr] {msg}", flush=True)      # print 而非 logging
...
except Exception as e:  # noqa: BLE001
    import traceback
    traceback.print_exc()                       # 三处重复（L272/297/383）
    raise HTTPException(500, f"扫码登录启动失败: {e}")
```

**问题分析**：①用 `print` 而非结构化 `logging`，无级别/无时间戳/无结构化字段，与后端 structlog 体系不一致，难以被 Loki/Promtail 采集过滤。②`traceback.print_exc()` 在三处（L272/297/383）重复，且与 `raise HTTPException` 同时存在，堆栈打到 stdout 而非日志。③HTTPException 同样把 `f"...: {e}"` 内部异常回传（同 CODE-22）。

**优化建议**：用 `logging.getLogger(__name__)` 替换 `_log`/`print`；`traceback.print_exc()` 改为 `logger.exception(...)` 并抽为统一异常处理装饰器；对外错误脱敏。

### 3.2 共性根因

1. **“单 worker 内存态”假设遗留下的一致性/泄漏隐患**：大量无界字典/列表（CODE-05,06,10）、进程内限流与缓存（CODE-08,10,29）都依赖“单进程且会手动清理”的隐含前提。一旦扩容或长期运行，内存泄漏与状态不一致集中爆发。

2. **“能跑就行”的降级/吞错文化**：静默降级为 warning（bootstrap/registry）、`except: return []`（sources）、`catch {}`（前端）、恒 True 的 health_check（registry）——故障被层层掩盖，可观测性失真（尤其 CODE-24 流式成本恒 0、CODE-25 假 retry 计数）。

3. **配置与代码双写**：`config.yaml` 已定义的项（default_keyword/城市码/image_analysis/jwt）在代码里又硬编码一份（CODE-04,26,31），造成“改配置不生效”与魔法值散布。

4. **God function/component 普遍**：`_run_chat`(270)、`ingest_conversation`(340)、`initialize_app`(220)、`Job.tsx`(1512/30+ state) 都是职责过载的巨块（CODE-12~15），直接导致不可测试、难维护。

5. **同一正确范式未全面推广**：`json_storage` 已用 `asyncio.Lock`+`to_thread`+原子重命名、`audit.py` 已正确解析 XFF、`server.py` 全局 handler 已脱敏错误、`update_metadata_batch` 已存在——但这些正确做法未在同类场景全面复用（CODE-03,08,17,22），一致性缺失。
