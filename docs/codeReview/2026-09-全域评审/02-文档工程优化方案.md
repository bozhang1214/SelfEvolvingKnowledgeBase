## 2. 目标架构：五层文档模型 + 目录重组

### 2.1 五层模型（每层职责单一、读者明确）

```
L1 宪法层  Constitution  ── 不可随意改，改需 ADR：架构、术语、设计原则、目录规范
L2 设计层  Design        ── 随功能演进：各模块详设（历史设计标注为"设计快照"）
L3 操作层  Operations    ── 可执行 SOP：部署、运维、排障、检查清单
L4 参考层  Reference     ── 自动生成优先：配置参考、API、错误码、术语表
L5 记录层  Records       ── 只增不改的历史：CHANGELOG、评审、事故、决策记录
```

关键约束：**L5 只增不改；L3/L4 与代码强绑定（可自动校验）；L1/L2 变更需 ADR**。

## 3. SSOT：四份"记录类"文档的边界定义

当前 `CHANGELOG.md` / `BACKLOG.md` / `ISSUES-FIXES-2026-08.md` / `codeReview/未修复问题跟踪.md` 边界重叠（如 D1 明文 PAT 问题在 BACKLOG 与未修复问题跟踪中都有记录）。

| 文档 | 唯一职责 | 写入时机 | 生命周期 |
|---|---|---|---|
| `CHANGELOG.md` | **已发生**的变更（功能/修复/破坏性变更） | 每次合并 | 只增不改，按时间倒序 |
| `BACKLOG.md` | **未发生**的需求（待办/进行中/暂缓） | 需求产生或状态变更 | 条目可移动，完成后移入 CHANGELOG |
| `records/incidents/YYYY-MM.md` | **事故与故障**的时间线（现象→定位→修复→复盘） | 故障处理完 48h 内 | 归档，不改 |
| `records/reviews/` | **评审快照** | 每次评审 | 归档，不改 |

**判定规则（写进 CONTRIBUTING-DOCS.md）**：
- "我们要做什么" → BACKLOG
- "我们做了什么" → CHANGELOG
- "它坏了，我们怎么修的" → incidents
- "别人/工具怎么看我们的代码" → reviews
- 同一事实只允许出现在一处，其余位置用链接引用。

### 4.2 配置文档与 `config.yaml` 自动对账

现状：`04-config-reference.md` 617 行手工维护，而代码中存在**死配置**（`security.*`、`cost_control`、`api.auth.jwt_secret`、`rate_limit.*`、`tracing.sample_rate`、`l2_session`、`eviction.*`、`storage.postgres`、`tools.vector_store.enabled` 等）与**未文档化的硬编码**（`file_processor.py:81` chunk 500/50、`rag/retriever.py:107` min_score 0.3、`knowledge_ingestor.py:556/582` 冲突阈值、`upload.py:97-110` 直读环境变量）。

落地方案：新增脚本 `backend/scripts/check_config_doc.py`：

```
输入：config.yaml（解析为键路径集合） + 04-reference/config-reference.md（抽取 `yaml` 代码块中的键）
输出：
  - MISSING_IN_DOC：config.yaml 有、文档没有 → 报警
  - MISSING_IN_CONFIG：文档有、config.yaml 没有 → 报警
  - DEAD_CONFIG：config.py 定义但代码中零引用（用 ast 扫描属性访问） → 报警
退出码：非 0 阻断 CI
```

配套动作：把死配置**从 config.yaml 移除或标注 `# unused (planned)`**，避免"改了没用"的陷阱（对应 ARCH-06、AGENT-15）。

### 4.3 API 文档自动生成

现状：根 `README.md:326-372` 手工维护 API 表，已缺 `/news`、`/job`、`/share`、`/chat_share`、`/monitoring` 五组路由。

方案：
1. `backend/scripts/export_openapi.py` 启动时导出 `docs/04-reference/openapi.json`（CI 中运行 `python -c "from app.api.server import create_app; ..."` 即可，无需起服务）；
2. `04-reference/api.md` 只写"鉴权方式/统一响应格式/错误码/版本策略"，路由表用 `<!-- AUTO-GENERATED -->` 区块由脚本注入；
3. 前端 `services/*.ts` 的类型可由 openapi 生成（顺带治理 FE-03 的 `any` 密度）。

### 4.4 检查清单由脚本生成

`PRE-DEPLOY-CHECKLIST.md`（10 节）与 `pre-deploy-check.sh`（8 节）同名同序双份。方案：脚本增加 `--emit-markdown` 输出，文档顶部注明「本文件由 `deploy/pre-deploy-check.sh --emit-markdown` 生成，请勿手改」，并在 CI 校验两者一致。

## 6. 元信息头规范与术语表

### 6.1 统一元信息头（每个 md 文件顶部）

```markdown
---
title: 资讯子系统设计与运维
layer: design          # constitution | design | operations | reference | records
owner: @zhangbo
status: active         # active | draft | deprecated | archived
version: 1.0.0
last-updated: 2026-09-08
related: [02-design/memory-rag.md, 03-operations/runbooks/job-sources.md]
---
```

`status` 取值中的 **`archived`** 是关键：给所有"设计快照"打上时间戳归档（如 `02-phase1-design.md`），读者一眼知道"这是当时怎么想的"，而不是"现在是这样"。

### 6.2 术语表（`docs/GLOSSARY.md`，首版内容见 01 号文档附录 C）

要求：**先统一 7 个高混淆术语**（知识条目 / 会话 / 反思 / 降级 / 意图 / 报告 / L1-L3），再逐步扩展。同时定义：
- `degraded`（降级）必须是可观测状态而非形容词 —— 代码、日志、指标、文档、UI 五处统一用词（与 AGENT-09 联动）。

### 6.3 图统一为 Mermaid

现状架构图为 ASCII（`根 README.md:112-193`、`graph/builder.py:369-391`）。建议：
- 文档中的图全部改 Mermaid（可渲染、可 diff）；
- 代码里的 `get_graph_diagram()` 保留为文字版，但在文档里维护 Mermaid 版并注明"以文档为准"。
