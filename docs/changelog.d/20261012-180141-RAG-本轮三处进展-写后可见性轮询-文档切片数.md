## 2026-10-26（RAG 三处进展 + 仍未解释的"跨轮摆动"）

### ✅ 进展一：写后可见性 —— 有界轮询（已实测生效）
同一次调用里出现过 `size()`=0 而紧接着 `all()`=1：两个读法对**同一张表**给出不同答案，
唯一自洽的解释是**写入在提交后还需要一点时间才可见**。改成有界轮询（最多 4 次 × 40ms，
期望值是**本次应当写入的条数** `rep.chunks`）后：
```
dbChunks=1 allRows=1 轮询=1        ← 一次就读到（此前是 0/1 或 0/0）
tx=[begin=0 before=0 inTx=0 commit=0 after=1]
```
**注意**：这不是"把失败掩盖成成功"——期望值来自本次写入量，达不到仍然会带出真实数字（`轮询=4` 就是四次都没读到）。

### ✅ 进展二：文档列表的切片数改为**按 `chunks` 表算**（真正的根因之一）
设备实测：文档登记成功（列表里能看到这一篇），但其 `chunks` 列**恒为 0，轮询 4 次仍是 0**
（`docs=1篇/0段(轮4)`），而同一时刻 `chunks` 表里确实有切片。
⇒ `documents.chunks` 这个**冗余缓存列不可信**；切片表才是事实来源（检索/删除都按它走）。
`RdbVectorStore.list()` 改为 `LEFT JOIN chunks ... COUNT(c.id)`（`LEFT JOIN` 保证"没有切片的文档"
仍出现且计数 0，不会因 INNER JOIN 丢行）。修完：`docs=1篇/1段(轮1)`、`rag_ingest` 转 PASS（列表里 2 篇、总片段 2 段）。

### ✅ 进展三：自检开头先清理上一轮的 `__selftest` 文档
自检库与用户库共用 `sekb_docs.db`，上一轮的测试文档**可能没删干净**（实测 `rag_delete` 有时删 0 段），
于是下一轮 `rag_retrieve` 命中的是**残留行**、`rag_ingest` 的篇数也随残留变化——
这正是同一份代码出现 `PASS=26 / 22 / 23` 不同汇总的直接原因。
现在自检**开头就按前缀清理**（只删 `__selftest` 前缀，绝不碰用户文档），并打一行"RAG 预清理：N 篇"。

### ⚠️ 仍未解释：`rag_retrieve` 的分数在 0.696 / 0.214 / 0.000 之间摆动
同一份代码、同一句中文查询（"端侧 RAG 为什么隐私更好"），三次运行的**最高分**分别是
`0.696`、`0.214`、`0.000`，且 `嵌入` 耗时一次是 `0ms`、一次 `1000ms`。
- `0.000` + `嵌入=1000ms` 那次：库是干净的（预清理 0 篇）、`rag_ingest` 也 PASS（2 篇/2 段），
  说明**写入与登记都对了，但检索算不出分**；
- 而 `0.696` 那次能给出合理分。⇒ 问题在**查询侧嵌入**（同一模型会话的两次调用结果不一致），
  不在存储链路（存储链路本轮已被三处修复钉住）。

**下一轮的第一步（明确）**：把 `rag_embed_sanity` 那种"同一文本嵌入两次、比对余弦"的判据
**搬到检索路径上**——在 `rag_retrieve` 的报告里带上"查询向量是否为零向量 / 前后两次嵌入是否一致"。
一次运行就能区分"嵌入不稳定"与"检索打分/阈值"两类原因。**不再做存储层的实验**（那层本轮已收敛）。
