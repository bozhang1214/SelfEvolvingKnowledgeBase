### 鸿蒙 RAG 本轮的**关键取证结论**：嵌入与打分链路是**正确**的
三处判定（都绕开可能出问题的中间层）：
```
查询向量：dim=512 norm=1.000000 全零=false 两次自洽余弦=1.000000 头=-0.040517,-0.042803,0.074009
入库向量：dim=512 norm=1.0000
直接余弦=0.696412（自己算，不经 topK、不经阈值）——**与检索给出的最高分完全一致**
```
⇒ 嵌入、向量编解码、余弦打分**全都对**。
先前把"检索 0 条"当成 RAG 没通是**误判**：该断言用的是自检短文语料 + 0.40 阈值，
而这条查询与语料的相似度**天然在 0.21~0.70 之间摆动**（摆动来自下面那条 RDB 问题，不是语义）。

### 仍未收敛（本轮**不再**在此层加时间的那个问题）
同一份代码、同一台模拟器，RDB 的**写后可见性/读一致性随轮次摆动**。最尖锐的一次证据：
**同一次 `rag_retrieve` 调用里**，检索给出 `最高分=0.214`，而紧随其后的取证件读到 **`库里 0 行`**。
已排除：事务（`begin/commit` 返回值全 0、`after=1` 那次可见）、游标长度语义（已修）、
列名/索引（自省确认）、库名/目录（正确）、嵌入与打分（本轮已证正确）。
已做的缓解（都有实测效果）：写入侧回读**有界轮询**、检索候选读取**有界轮询**、
文档列表切片数**改按 `chunks` 表算**（不再信 `documents.chunks` 冗余列）、自检开头**预清理**残留文档。

**下一轮的建议（换战场，不再和这个 RDB 绑定纠缠）**：
1. 把 `VectorStore`/`DocumentRegistry` 换到 **ArkTS `relationalStore`**（RFC C3 原意；
   接口不变、共享层零改动、NDK C 路径留作对照）——它由平台托管连接/事务，最可能绕开这个摆动；
2. 同时把自检的 `rag_retrieve` 断言改成"**直接余弦**必须 ≥ 某值 且 **topK 结果与直接余弦一致**"
   （用本轮已验证正确的量做判据），这样阈值/语料不再干扰"链路是否通"的判断。
