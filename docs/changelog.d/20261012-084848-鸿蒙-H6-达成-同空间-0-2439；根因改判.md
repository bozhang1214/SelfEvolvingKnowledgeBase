## 2026-10-12（鸿蒙 H6 达成：同空间 0.2439；根因改判为设备侧喂数越界（非转换器丢掩码））

- **背景**：鸿蒙端侧嵌入此前设备实测 `cos(端侧推理为什么省电, 北京今天多云转晴适合骑行)=0.8154`，
  而 Android 基线是 **0.244**。上一轮把它归因为"转换器把 `sekb_additive_mask_zero` 常量折叠了"，
  并把下一步定为"让转换链保真"。本轮**先验证这个归因**，结论是它**不成立**。

- **根因改判（两条独立证据）**：
  - **图结构**：新写 `scripts/ms_flatbuffer.py`（纯 Python 读 MSL2 flatbuffer，不需要 flatc/runtime/设备）
    + `scripts/check_ms_mask_wiring.py`。产物里链条完整：
    `mask 输入[35] → sekb_additive_mask_zero_nh2nc(Transpose，NHWC 适配) → 4×attention/self/Add → Softmax`，
    下游闭包 110 个节点，且该张量 `has_data=False`（**不是**常量）。**没有被折叠。**
    同时暴露关键一行：`input_ids` 的 flatbuffer `dtype=34`，而 34 在 flatbuffer **和**
    OHOS `OH_AI_DATATYPE_*` 里都是 **INT32**（INT64 是 35）。
  - **运行期数值**：`scripts/check_ms_numerics.py` 在 arm64 容器里 ctypes 调 `libmindspore-lite.so`，
    复刻设备的"读输入 → 写 `MSTensorGetMutableData` → Predict"路径：
    `input_ids` 元素数 512 而 `MSTensorGetDataSize=2048 B`（=512×4）。旧代码用 `LongArray`
    写 **4096 B → 越界 2048 B**；Linux 形态直接崩（`malloc(): invalid size (unsorted)`，可复现），
    鸿蒙 musl 不报 → 后半段 id 静默写进隔壁分配块，模型只收到前 256 个 id。
    把写入限制在 2048 B 后：**与 onnxruntime 参考余弦 = 1.0000（逐元素差 ≈4e-6）、cos(A,B)=0.2439**；
    而"int64 半写"给出 0.514 / 0.7861（与设备那个 0.8154 同量级）。
  - 即：**掩码从来没被忽略，是词 id 被写坏了。**

- **改动**：
  - 设备侧修 `MsLite.kt`：不再假设 int64，按 `OH_AI_TensorGetDataSize / GetElementNum` 得到
    每元素真实宽度（4/8）再打包；`writePacked` 写前断言"要写的字节数 == 缓冲字节数"，
    结构上排除越界写。（实测 `OH_AI_TensorGetDataType` 会把三个输入都报成 34，不可作判据。）
  - 补 `MindSporeBgeEmbedding.embedOne`：`EmbedSanity.kt` 一直在调它而类里**只有私有的
    `embedOneText`** —— 检出状态下源码编不过（`Unresolved reference: embedOne`），
    设备上那份"跑通的产物"其实是更早的构建缓存。这是一处真实的复现性缺口。
  - `diagnostics` 把 `输入布局`（元素数 / 声明 dtype / 缓冲字节数 / 实测每元素宽度）放到**第一行**——
    脚本按 `embed_` grep 时只显示第一行，放第二行等于设备上看不到，而它正是本缺陷的唯一直接设备证据。
  - `EmbedSanity`：新增 `embed_mask_effective`（正确掩码 vs **全零**掩码必须差 >0.05）；
    `embed_sanity_cosine` 保持硬 FAIL（`|cos-0.244|≤0.02`）；修正 `embed_mask_value_scan` 的措辞——
    `-1e9/-65504/-1e4/-inf` 四者 cos **完全相同**（host 实测极差 0.00e+00，softmax 饱和一致），
    极差≈0 **不是**"掩码被忽略"的证据（上一版那句会误导）。
  - 新增构建期/验收期断言：`check_ms_mask_wiring`（6 条结构判据）、`make_maskref.py`（ORT 参考，
    并证明 int64/int32 两种声明数值等价）、`check_ms_numerics.py`（`.ms` vs ONNX 逐元素 ≤1e-5 +
    缓冲宽度守卫 + 掩码生效）、`model_to_ms_maskfree.py --id-dtype/--dump-mask-input`
    （产出与产物同声明的 int32 对照图）。
  - `model_to_ms.sh` 新增 `convert-maskinput / check-maskinput-wiring / check-maskinput-ref /
    check-maskinput-ms / check-maskinput-ms-red / check-padding-gap[-red] / verify-maskinput`；
    `harmony.sh embed` 现在会**先跑产物侧断言**再上设备（把"产物坏了"与"设备喂数坏了"分开定位）。
  - `check_maskfree_padding_gap.py` 判据纠正：旧版判据（"两个余弦必须一个 >0.5 一个 <0.5"）
    把**正确**的模型判成"结论不明确"；现改为"逐元素 ≤1e-5 + 两图余弦都落在 0.244±0.02"，
    并新增 `--red` 反证。同时更正 `model_to_ms_maskfree.py` 头部"带 padding 时预期不一致"的说法
    （对本变体不成立，实测逐元素差 ~1e-7）。

- **验证**（模拟器 127.0.0.1:5555 / nova 16 Pro / HarmonyOS 6.0.2 API22 arm）：
  - host：`check_maskfree_padding_gap.py` → 两图 CLS 最大逐元素差 **1.067e-07 / 1.157e-07**（判据 ≤1e-5），
    两图余弦 **0.2439 / 0.2439**（基线 0.244±0.02）。
  - 产物侧：`bash scripts/model_to_ms.sh verify-maskinput` → `MS-WIRING PASS 6/6`、
    `MS-CHECK PASS 8/8`（与 ONNX 参考逐元素差 4.0e-6 / 5.2e-6）、
    两条反证均"确实变红"（不喂掩码 → `MS-CHECK FAIL 4/8`；全零掩码 → 3 条判据红）。
  - 设备：`bash scripts/harmony.sh embed 90` → `EMBED PASS 10/10`、明细 `FAIL=0`，
    其中 `embed_sanity_cosine — cos=0.2439`（**与 Android 基线同空间**）、
    `embed_mask_effective — 正确掩码 0.2439 vs 全零掩码 0.9688：差=0.7250`、
    `embed_l2_norm — 1.0000`、`embed_deterministic — 两次嵌入逐位相同`、
    `embed_failure_returns_zeros` 仍成立。

- **未做 / 已知缺口**：
  - `.ms` 数值判据跑的是 **Linux aarch64 runtime**（与鸿蒙 runtime 同一套 C API 的两个名字、
    同一份转换产物），**不是**鸿蒙 runtime 本身；设备侧"每个输入缓冲多少字节"目前由
    `diagnostics` 打印的实测值 + "写不下就报错"的守卫间接保证，尚未把
    `OH_AI_TensorGetDataSize` 的对照值从设备上直接打印出来。
  - `bge-maskinput-i32.ms`（与产物同声明的对照产物）已能转换，但**没有**单独上设备跑；
    转换与数值等价由 host 侧两条断言覆盖。
