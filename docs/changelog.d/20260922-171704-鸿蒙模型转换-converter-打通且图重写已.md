## 2026-09-22（鸿蒙模型转换：converter 打通且图重写已证明等价，但 .ms 运行时 build 失败）

- **背景**：上一轮确认鸿蒙端侧嵌入改用系统 MindSpore Lite，剩下两个前置条件之一就是
  "把 bge-small-zh 从 ONNX 转成 `.ms`"（`OH_AI_MODELTYPE` 只有 MINDIR，没有 ONNX），
  而当时本机与 DevEco 里都找不到 `converter_lite`。本轮把它打通到"只差运行时"，
  并**如实记录一个更深的新问题**。

- **改动**：
  - 新增 `scripts/model_to_ms.sh`（`fetch|rewrite|convert|check|all`）与 `scripts/model_to_ms.py`。
  - 关键决策：**用 Linux-aarch64 版 MindSpore Lite 包**。官方**没有 macOS 版 converter**
    （只有 Linux-x86_64 / aarch64 / Windows）；而 aarch64 包与 Apple Silicon 宿主同为 arm64，
    可以在本地已有的 arm64 容器里**原生执行，不需要 Rosetta**。
    （试过 `--platform linux/amd64`：Docker 会去拉不存在的镜像并 403——因为本地镜像是 arm64-only。）
  - 关键修复：converter_lite **不认 `IsNaN`** 算子。HF 导出的 BERT 每层注意力都带
    `Where(IsNaN(softmax), 0, softmax)`（即 `nan_to_num`）。本模型的掩码是**加性大负数**（不是 `-inf`），
    softmax 不可能出 NaN → 这段是**死代码**，可安全短路。`model_to_ms.py` 做这个重写，
    并**用 onnxruntime 证明改写前后逐位相同**（不是"余弦接近 1"）。
  - `scripts/model_to_ms.sh` 注释里记下了一条复发过的 shell 坑：`$VAR（` 这种"变量紧挨全角括号"
    的写法会让 bash 把全角括号首字节并入变量名，报 `VAR\xef: unbound variable`（本脚本与
    `scripts/ios_app.sh` 都踩过）→ **一律写 `${VAR}`**。

- **验证**（实测）：
  - ✅ 包 sha256 `3db8ce8a…456a02` **与官方公布值完全一致**；`fetch` 幂等（复跑不重下）。
  - ✅ 图重写：4 处 `Where(IsNaN(softmax), 0, softmax)` 短路；onnxruntime 在 4 种输入形状
    （1×16 / 1×64 / 2×33 / 1×128）下**全量最大差均为 0.000e+00**（逐位相同）。
  - ✅ `converter_lite` → `CONVERT RESULT SUCCESS:0`，产出 `.ms` 94.8MB，头部魔数 **`MSL2`**。
  - ❌ **`benchmark` 实际加载运行失败**，且两条路径失败点不同：
    · 动态 shape：加载时 `FindBackendKernel return nullptr, name: /m/Flatten, type: Flatten`
      （上游动态形状未解析 → 下游算子形状未知 → 拿不到 kernel）；
    · 固定 shape（`--inputShape`）：**转换阶段**即 `SaveGraph] Convert to meta graph failed`。
  - **结论：鸿蒙端侧嵌入的"模型依赖"目前未打通**。三条候选路径已写入 `apps/harmony/README.md`：
    ① 静态化 ONNX 的动态掩码展开子图后再转；② 回到社区版 OHOS ONNX Runtime；
    ③ 按 RFC §4 D2 退路线 B（ArkTS 重写 + 契约夹具）。这需要 owner 拍板。
  - 口径提醒：第 3 条(运行时)/第 4 条本来还要等设备与签名，所以这个模型问题**不是当前唯一卡点**，
    但它决定 M7 的技术路线。
