## 2026-10-26（自检库跨轮带脏数据 → 加"干净性"判据；写入不可见已钉到具体形状）

### ① 发现：自检库**跨轮带脏数据**，所以"检索能命中"有水分
给探针加了 `fresh_db_is_empty`（`delete` + `open` 之后条数必须为 0）之后，两条事实同时出现：
- **有干净库那一次**：`fresh_db_is_empty PASS — 条数=0 内容=[]`（说明 `delete` 本身是有效的）；
- **上一轮那次**：同一个探针库（名字每轮唯一！）的 `all()` 读到 **3 条上一轮的 `__selftest__` 行**（`dim=512`）。
两轮之间唯一的变化是我在探针里加了断言——所以"库不干净"不是稳定复现的现象，而是**状态相关**的。
**后果必须说清**：`rag_retrieve` 报的那个 `PASS（首条=__selftest__@0.696）`，
命中的**可能是上一轮的残留行**，不能当成"本轮写入→检索"闭环的证据。
新增的 `fresh_db_is_empty` 把这件事变成机械可判（不干净就整批断言都不可信）。

### ② 写入不可见的现象，已钉到具体形状（但根因仍未定）
同一份代码、同一个探针，在**干净库**上立刻表现为：
```
fresh_db_is_empty PASS 条数=0
write_size         FAIL size=0（期望 1）      ← 刚 upsert 完，size() 还是 0
read_single_column FAIL source_id='<null>'
read_multi_column  PASS 列名/索引/取值全正常（id='doc-probe#0'）
read_all_path      FAIL 条数=0
size_after_delete  PASS size=0
```
而**另一次**运行（库里有残留时）则是 `dbChunks=1 allRows=1`、`read_all_path PASS`。
⇒ 形状是：**`upsert()` 报成功，但同一句柄随后 `size()`/`all()` 看不到那一行（有时又看得到）**。
已经排除的：事务（`begin/commit` 返回值全 0，且提交后 `after=1` 那次确实可见）、
游标长度语义（`cursorText` 两种长度都试）、列名/索引（自省确认）、库名/目录（都正确）。

### ③ 决策（不再往 NDK C 路径加时间）
按 RFC 里 C3 的原意，**下一轮把这套实现换到 ArkTS `relationalStore`**：
- 它由平台托管连接/事务/账号簿记，`ValueBucket` 与 `RdbStore` 都是官方主推路径；
- `VectorStore`/`DocumentRegistry` 两个接口**不变**（端口的意义就在这里），
  共享层 `KnowledgeIndex`/`Retriever`/评测集**一行都不用改**；
- NDK C 路径保留在仓库里作为对照（其现象与探针都已留档）。
若 `relationalStore` 路线也出现"写后读不到"，那才说明是平台缺陷，而不是绑定用法问题。

### ④ 本轮已确凿修好的两处（都以断言钉住）
1. `cursorText` 长度语义 → `all()` 不再整行跳过（`read_multi_column` 从 FAIL 转 PASS）；
2. 命中字段名 `source`/`sourceId` 不一致 → **`rag_retrieve` 转 PASS**（首条带上了来源名）。
