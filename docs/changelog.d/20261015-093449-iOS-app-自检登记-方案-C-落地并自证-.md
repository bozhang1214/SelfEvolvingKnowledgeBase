## 2026-10-15（iOS app 自检的**登记机制**（方案 C）落地，并用它自证）

### 你问的"加进 CI 门禁"具体是什么 —— 先说清仓库现状
仓库**已有 CI**（GitHub Actions，Linux）三道门：`ci.yml`（后端 ruff/mypy、**doc guard**、gitleaks、
npm audit、tsc、ESLint）、`android.yml`（Android 单测 + assembleDebug）、`doc-review.yml`（季度文档时效）。
**iOS / Mac / 鸿蒙 三个端侧门在 CI 里一项都没有** —— 它们需要 Xcode / 模拟器 / 鸿蒙模拟器，
Linux runner 上跑不了，所以只能靠人跑；而"靠人记"会漏（本项目真漏过，见下）。

于是"加进 CI 门禁"有三种可选做法，**本轮按你的选择执行方案 C**：

| 方案 | 是什么 | 代价 | 本轮 |
|---|---|---|---|
| A 真 CI job | `macos-*` runner 上跑 `ios_app.sh run`，红了挡合并 | macOS runner 计费是 Linux 的 **10 倍**；模型 91M 未入库需缓存；约十几分钟/次 | 未做 |
| B pre-push hook | 本地推送前跑（不花钱、即时） | 只对装了 pre-commit 的人有效 | 未做 |
| **C 登记式** | **记录 + 校验 + PR 可见性**，不挡提交 | 零成本；靠"陈旧会被报出来"来防漏 | ✅ **本轮** |

### 方案 C 实现（三件）
1. **记录** `apps/ios/docs/验收记录.json`：每条含 **commit SHA**、PASS/FAIL/SKIP、**SKIP 项**、时间、命令、设备。
   **SHA 是必需字段**——没有它就无法判断记录是否还新鲜。
2. **工具** `scripts/ios_record.py`：
   - `run`：跑 `ios_app.sh run`，**自动**抓汇总行写记录；**抓不到就不记**（避免把"没跑成"记成"跑过"）；
     同一 commit 重复跑**覆盖**而非堆叠。
   - `check`：检查"自那次通过以来 iOS 相关文件有没有再被改过"。敏感路径**写死在脚本里并注明理由**：
     `apps/ios/**`、`apps/shared/**`（iOS framework 就是它编的——最容易漏的一项）、`apps/shared-core/**`、
     `scripts/ios*.sh`、`scripts/verify_all_ends.sh`。**含未提交改动也算陈旧**
     （"记录之后又改了代码"同样使记录失效）。
   - `show`：只看记录。
3. **可见性** `.github/PULL_REQUEST_TEMPLATE.md`（原先**没有** PR 模板）：把"该跑哪个端"写成清单，
   含"若 SKIP/FAIL 非空必须写清是什么环境限制，不要写'已知问题'"，以及 AGENTS.md 的协作检查项。

### 故意非阻塞（方案 C 的定义）
`check` 默认有问题也只给 ⚠️、退出码 0；`verify_all_ends.sh full` 里调用时加 `|| true`，
并在验收表里注明"⚠️ 已陈旧，不阻塞"。想升级成硬门禁**只需加 `--strict`**（那时它会让该步 FAIL）。

### 自证（用未提交改动做真探针）
```
无改动            → ✅ 记录仍然有效
改 apps/ios/App/TimeFmt.swift → ⚠️ 记录已陈旧：1 个文件；--strict 退出码 1 ✅
提交后再查        → ⚠️ 陈旧（这次是 scripts/verify_all_ends.sh 自己触发的——符合设计：
                    脚本变了，旧结果的判据可能已不同）
用工具刷新记录    → ✅ PASS=42 FAIL=0 SKIP=1 @ b632325，再查 → 有效
```
**记录不是摆设**：它真的会在"改了 iOS 却忘了跑"时把这件事报出来。

### 一条无法绕过的事实（写进文档免得反复讨论）
iOS / Mac / 鸿蒙 三端在 **Linux CI 上永远无法自动测**（需要 Xcode/模拟器）。
CI 能覆盖的端侧只有 **Android 单测 + 共享层编译 + 文档守卫 + 端侧活数字**；
其余三端只能靠"人跑 + 机器判陈旧"。想让它们全自动，唯一的办法是自建 macOS/鸿蒙 runner。
