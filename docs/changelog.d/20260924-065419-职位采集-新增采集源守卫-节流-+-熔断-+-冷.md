## 2026-09-24（职位采集：新增采集源守卫（节流 + 熔断 + 冷却后探测），修复猎聘封禁的结构性原因）

- **背景**：2026-09-23 为 FDE 全量调研连续跑了多轮「22 关键词 × 翻页」扫描，
  把**猎聘的服务器 IP 打进了风控黑名单**（搜索接口恒返回裸拒绝 `{"flag":0}`；
  浏览器 302 到 `safe.liepin.com/.../captchaPage_ip_PC`，`euuid` 解出 `flag10001|ip_ua:<ip>`）。
  复盘出**两个结构性原因**，本次逐一修掉：

  | 原因 | 具体 | 
  |---|---|
  | **没有节流** | ① `fetch_all` 关键词之间**无延迟**；② 更严重：猎聘列表接口不带 JD，`fetcher._fetch_jds` 会为**每条职位**并发抓详情页（`_JD_CONCURRENCY=6`）→ 单关键词 `2 + 40` 次请求，一轮 22 关键词扫描近 **2000 次** |
  | **被拒后还在打** | 猎聘首次 `flag:0` 后只记 warning 并返回空列表，**剩下 21 个关键词照打不误** → 把"临时标记"升级成"持续封禁" |

- **改动**：
  - **新增** `backend/app/agents/job/source_guard.py`：
    · `_IntervalGate`：**预约式**最小间隔闸门——`reserve()` 立刻占用下一个时隙并返回需等待秒数，
      调用方自己 sleep。这样 sync（详情页线程池）与 async（采集编排）两条路径**共用同一份状态**，
      并发调用者自然排队，且 sleep 期间不持锁。另有线程安全用例兜底。
    · `SourceGuard`：按源维护熔断状态。`record_blocked` 累计失败，达阈值即打开熔断；
      冷却期过后 `open_remaining()` 归零 → 放**一次探测**（半开）；`record_success` 复位。
      状态持久化在 `data/source_guard.json`，**容器重启不会重置冷却**（否则重启即等于立刻再打一次）。
    · `SourceBlockedError`：把「源**明确拒绝**我们（风控/验证码）」与「这次正常没有结果」区分开——
      前者触发熔断，后者是正常业务状态。
    · 运维旋钮走环境变量，模块 docstring 列全：`SEKB_JOB_BOARD_INTERVAL_S`(4.0) /
      `SEKB_JOB_OFFICIAL_INTERVAL_S`(0.8) / `SEKB_JOB_DETAIL_INTERVAL_S`(1.0) /
      `SEKB_JOB_BREAKER_THRESHOLD`(2) / `SEKB_JOB_BREAKER_COOLDOWN_S`(1800)。
    · `get_source_guard()` 为**进程内单例**——节流状态必须跨 collector 实例共享，否则等于没节流。
  - `collector.py`：`_safe_fetch` 接入守卫，顺序刻意是「**先查熔断 → 再节流 → 再调用**」：
    冷却期内直接短路返回（**一个网络请求都不发**）；`SourceBlockedError` → `record_blocked`；
    成功 → `record_success`；普通异常只记 warning，**不触发熔断**（避免误伤正常源）。
    所有源都必须经过 `_safe_fetch`，守卫无法被绕过。
  - `fetcher.py`：
    · `_fetch_sync` 的 `flag != 1` 分支由「记 warning 返回 []」改为**抛 `SourceBlockedError`**；
      `LiepinJobFetcher.fetch` 的兜底 `except` 显式**不吞**该异常（其余异常仍降级为空列表）。
    · `_fetch_jds`（请求量放大器）三重克制：并发 `6 → 2`（`SEKB_JOB_JD_CONCURRENCY`）、
      每次请求前过详情页最小间隔（1s）、**单次调用封顶 20 条**（`SEKB_JOB_JD_MAX`），
      超出部分留空、由 `refresh_job_jd` 按需补；并记录 `capped/skipped` 便于观测。
    · `refresh_job_jd`（按需刷新单个 JD）同样遵守熔断与节流——否则它会成为绕过守卫的后门。
  - `docs/ops/10-JOB-SOURCES.md`：猎聘章节补「已修复」小节，把两个原因与对应修复做成对照表，
    并列出仍未做的备选方案（浏览器源人工过验证、22 词拆多轮）。

- **验证**：
  - `ruff check app/ tests/` 通过；`bash scripts/mypy_gate.sh` → 300 ≤ 基线 310，无新增类型错误。
  - 新增 `tests/unit/test_job_source_guard.py`（**22 passed**），覆盖：
    · 闸门：预约时隙**递增**（并发不重复）、零间隔无关断、按 key 隔离、`wait_sync`/`wait_async`
      真的等待、**多线程并发预约无重复时隙**；
    · 熔断：初态关闭、达阈值打开、成功复位、**冷却过期允许探测**、状态**跨实例持久化**
      （重启不重置）、状态文件损坏可容忍、通用平台间隔长于官方站；
    · 集成：熔断期内**源调用次数为 0**（零网络）、`SourceBlockedError` 达阈值后
      **剩余关键词不再打源**、冷却探测成功后恢复、**普通异常不熔断**、节流按源申请时隙；
    · fetcher：`flag=0` 抛 `SourceBlockedError`、`fetch` 不吞该异常、
      详情页**封顶真的生效**（10 条职位只抓 3 条）、熔断期 `refresh_job_jd` 不发请求。
  - job 相关 6 个测试文件合计 **89 passed**。

- **附带修复：默认关闭猎聘 JD 补全（顺带发现的功能性失效）**
  部署后用**单关键词受控探测**验证守卫时，日志里出现
  `猎聘职位 JD 补全完成 total=42, capped=20, skipped=22, filled=0`——
  封顶与节流生效了，但 **`filled=0`**，抓回来的详情页一个 JD 都没解析出来。

  追查到根因：**猎聘详情页已改为纯客户端渲染**。
  `/job/<id>.shtml` 返回的是 **1.3KB 的 JS 跳转壳**（`window.$CONFIG.pcUrl` → `wow.liepin.com/…`），
  手动跟随该跳转得到的仍是 **3KB 空壳**（`<div id="main-container">` + JS bundle）。
  纯 `requests` 不执行 JS，所以旧正则 `<dd data-selector="job-intro-content">` 命中恒为 0。

  影响量化（集内 101 条按来源统计 `jd_text` 非空率）：

  | 来源 | 有 JD |
  |---|---|
  | 字节 / 百度 / 阿里 / 腾讯（官方站） | **100%**（18/18、11/11、10/10、1/1） |
  | 猎聘 | **0%（0/49）** |
  | 智联招聘 | **0%**（0/12，经典页卡片本就不含 JD，实现时的已知边界） |

  即：`_fetch_jds` 在为 **0 收益**消耗「每关键词最多 20 次」的受限请求——**纯浪费且徒增风控风险**，
  与本次要解决的"别再把猎聘打爆"直接冲突。

  处理：`fetcher` 新增 `_JD_FETCH_ENABLED`（环境变量 `SEKB_JOB_JD_FETCH`，**默认 0 = 关闭**），
  `_fetch_jds` 与 `refresh_job_jd` 在关闭时**直接返回并记一条说明日志**
  （避免"为什么 jd_text 是空的"再次变成需要排查的谜题）。代码路径保留，将来猎聘恢复 SSR
  或改用浏览器渲染时设 `SEKB_JOB_JD_FETCH=1` 即可开回。

  测试：新增「默认关闭时零详情页请求」与「`refresh_job_jd` 关闭时不请求」两个用例，
  并把原封顶用例改为显式开启后验证封顶 —— 合计 **24 passed**。
