## 2026-09-25（端侧会话历史持久化：重启 App 不再丢对话）

- **背景**：气泡一直只在内存里，杀掉 App 再打开聊过的内容全没——对聊天应用这是不能接受的。
  网页端有会话列表，端侧连"恢复最近一次"都做不到。

- **改动**（照 `DocumentRegistry` / `VectorStore` 的既有套路：`shared` 定接口 + 内存实现，平台出落盘实现）：
  - 新增 `shared/chat/Conversation.kt`：`Conversation`/`StoredMessage`/`StoredSource` 模型、
    `ConversationCodec`（JSON 编解码，纯逻辑可被 JVM 单测直接跑）、`ConversationStore` 接口、
    `InMemoryConversationStore`。
  - 新增 `ondevice/chat/FileConversationStore.kt`：**每个会话一个 JSON 文件**。
  - `ChatViewModel`：启动恢复最近一次会话、每轮结束落盘、`newConversation()`；
    新增 `conversationTitle` 状态。
  - `ChatScreen`：顶栏显示会话标题（用户才知道自己在聊什么），有对话时给"新对话"入口。

- **四个刻意的选择**：
  1. **一文件一会话**而非一个大 JSON：单文件一次写坏 = 所有历史全没；
  2. **临时文件 + 原子改名**：直接覆写在进程被杀时会留下半截 JSON；
  3. **坏文件跳过而非抛异常**（`lastSkippedCorrupt` 计数），且 `decode` 对**旧数据缺字段取默认值**——
     **宁可丢一个字段，也不能丢整段对话**；
  4. **上限 50 段并裁剪最旧**：端侧存储有限，"无限增长的聊天记录"是隐性磁盘泄漏。
  另：**有意不持久化云端 `conversationId`**——端侧这段（含设备专属的检索来源/执行位置）
  服务端并不知道也不该上传；本地只恢复"用户在本机看到过什么"。

- **验证**：
  - `bash scripts/android.sh test` → **273 用例 / 0 失败**（新增 15 条）。
  - `FileConversationStoreTest` 用**真实文件系统**，核心用例用**新的 store 实例指向同一目录**
    来等价"杀进程重启"；另覆盖坏文件跳过、`.tmp` 不残留、上限裁剪、同 id 覆盖不重复。
  - `doc_guard` 6/6。
  - ⚠️ **未做**：真机上"杀掉 App → 重开 → 历史还在"的端到端目视确认（手机已断开 adb）。
