## 2026-10-15（评测门禁：从假门禁变真门禁（--fail-under/基线/超时）+ 修 LLM 指标两处缺陷）

- **背景**：FDE 岗位 JD 明确要求「构建高性能的**评估管道**和可观测性框架…确保准确性、安全性和延迟要求」。
  盘点时实测发现：评测**早就接进 CI 了，但是假门禁** ——
  `.github/workflows/ci.yml` 里写的是 `python -m app.cli.main eval … || echo "eval non-blocking"`，
  无论通过率多少都 `exit 0`，而 `app/cli/eval.py` 全文件 **0 处 `sys.exit`**。
  同时核对出 LLM 指标层的两处既有缺陷。本次把三者一起修掉。

- **改动**：

  **① 评测门禁（新增 `backend/app/eval/gate.py`）**
  - `GateThresholds` / `GateCheck` / `GateResult` + `evaluate_gate()` + `load_baseline()` /
    `make_baseline()` + `build_fingerprint()`。
  - 三条判据：**绝对阈值**（通过率下限）、**关键指标下限**（取聚合 `mean`）、
    **相对基线**（`pass_rate` 与基线指标不允许下降超过 `max_regression`）。
  - **三条设计原则**（都写进模块 docstring）：
    · **跑不起来 = 失败**：阈值要求的指标在报告里缺失、或基线文件读不出来 → 一律判失败。
      一个"无法执行"的门禁如果算通过，就还是假门禁。
    · **不只看绝对阈值，还看相对基线**：绝对线会掩盖渐进退化（每次掉一点、始终没破线）。
    · **判据可追溯**：指纹 = commit + `prompt/**` md5 + 画像 md5 + 数据集 md5，
      写入报告 —— 否则无法区分「退化来自代码」还是「来自提示词/画像改动」。
  - CLI（`app/cli/main.py`）新增：`--fail-under` / `--baseline` / `--max-regression` /
    `--metric-min name=value`（可重复）/ `--no-fail`（本地调试）/ `--update-baseline`；
    门禁不通过时 `typer.Exit(1)`。未配置任何判据时显式提示"本次评测**不构成门禁**"。

  **② CI 门禁化（`.github/workflows/ci.yml`）**
  - 删除 `|| echo "eval non-blocking"`（这一句就是假门禁的全部原因）；
    改为 `--fail-under` + `--baseline` + `--metric-min`，并给步骤加 `timeout-minutes`。
  - 保留数据集存在性检查，但**不再静默跳过**。

  **③ 修缺陷 A：token / 成本被重复计数约 2×**
  - `record_llm_call`（单次粒度）接入后，`record_chat_metrics` 里的"按请求聚合"写入没有删除，
    两者写**同一个 Prometheus 序列**（聊天路径下同一笔 token/成本记两次）。
  - 已删除该聚合写入（含 `llm_calls_total{role="aggregate"}`、重试/降级的聚合口径），
    唯一事实源 = `record_llm_call`。

  **④ 修缺陷 B：`LLMCallStats.records` 无界增长**
  - 原先无界 `list` + 每次调用 `append`，长期运行只增不减（内存持续增长）。
  - 改为定长 `deque`（`SEKB_LLM_RECORDS_MAXLEN`，默认 2000）；
    **关键**：快照差值原用 `records[snapshot.records_len:]` 下标切片，定长队列淘汰旧元素后会**错位**，
    故改用**单调递增的 `total_calls` 差值**定位（`list(records)[-delta_calls:]`）。
  - `retry_rate` 分母由 `total_calls` 改为**窗口长度** —— 两者口径不同后混用会得到无意义的数。

  **⑤ 指标归因（D1）+ 看板补全（D9）**
  - `llm_tokens_total` / `llm_cost_usd_total` 增加 `role` 标签：回答"哪个 Agent 最烧钱"。
    基数评估：role 是封闭集合共 11 个（`config.yaml` 的 `llm.roles`），不构成高基数。
  - Grafana 看板：新增「LLM 调用延迟（按 Agent，P50/P95）」「LLM 成本累计（按 Agent）」
    「LLM 调用次数（按 Agent）」，Token 面板改为按 Agent；把「日累计成本」换成
    `sum(increase(sekb_llm_cost_usd_total[24h]))` —— 原 `sekb_daily_cost_usd` 是**只 inc、无 reset**
    的 gauge，名不副实，改用计数差值后语义与名称一致。面板 12 → 16。

  **⑥ 单用例硬超时（实测发现的阻塞问题）**
  - 实测评测会在某条用例上**永久挂起**（第 2 条卡死 5 分钟以上、报告永不生成、进程停在 `ep_poll`）。
    没有超时的话这不是"慢"而是"永远不结束"，接进 CI 就是 job 一直挂着。
  - `app/eval/runner.py` 加 `_CASE_TIMEOUT_S`（`SEKB_EVAL_CASE_TIMEOUT_S`，默认 180s），
    超时**降级为"该用例失败"**并给出可读原因，保证评测一定终止。

- **验证**：
  - `ruff check app/ tests/` 通过；`mypy` 303 ≤ 基线 310；新增/相关 4 个测试文件 **79 passed**。
  - 新增 `tests/unit/test_eval_gate.py`（28 用例），重点覆盖**"门禁跑不起来必须失败"**：
    阈值要求的指标缺失 → 失败且提示现有指标；基线缺 `pass_rate` → 失败；基线文件损坏 → 失败；
    渐进退化（0.95→0.90，绝对线仍是 0.90）→ 被基线抓住；`max_regression` 容忍小幅下降；
    以及**"挂住的用例必须变成失败而不是永久挂起"**（monkeypatch 一个 sleep 30 的用例 + 0.05s 超时）。
  - 新增 `tests/unit/test_llm_metrics_fixes.py`（5 用例）钉住重复计数不再回归：
    断言 `record_chat_metrics` **不得**再写 tokens/cost/calls，且不误伤同函数的质量指标；
    断言 `record_llm_call` 的 tokens/cost 确实带 `role`。
  - 新增 `tests/unit/test_llm_stats_bounded.py`（10 用例）：定长上限、保留最近 N 条、
    **快照前有记录且快照后触发淘汰时差值仍只反映快照之后**（原下标切片会错位丢数据）、
    超出窗口的极端情况不抛异常、`retry_rate` 分母口径。
  - **真基线已建立（据实，未编造）**：`backend/eval-baseline.json` 由容器内实测生成
    （`--update-baseline`）。**但实测结果暴露了评测本身不可靠** ——
    10 个用例耗时 **1636s**、**9 个因单用例超时失败**（默认 180s），期间 DeepSeek 返回
    503「Service is too busy」触发重试退避，最终 **pass_rate 只有 0.1（1/10）**。
    这不代表应用质量如此，而是评测依赖的实时外部 LLM 不稳定 + 工具调用挂起。
    · 因此本次门禁定位为**回归门禁**（防"比现状更差"），不是质量下限：
      `--baseline eval-baseline.json --max-regression 0.1 --fail-under 0.1`。
      三者配套才成立 —— 单用 `--max-regression 0.1` 会把下限拉到 0，**退化到 0.0 也算通过**
      （已实测发现并修：补 `--fail-under 0.1` 后 0.0 判失败）。
    · `--max-regression 0.1` 留 1/10 容差是**有意的**：评测依赖实时外部 LLM，
      503 抖动会让个别用例失败，那不是代码退化；评测稳定后应收紧到 0。
    · 基线里带 `_note` 字段记录上述背景（门禁读取时忽略未知键）。
    · **提高门槛的必要前提（下一步）**：① 定位挂起的工具/调用并加超时与快速失败；
      ② LLM 503 用指数退避重试；③ 稳定后 `--update-baseline` 把基线拉回真实水平，
      再叠加 `--fail-under` 的绝对下限。
    · 基线 `fingerprint.commit` 为 `unknown`：容器镜像内没有 `.git`（非缺陷，键仍保留）。
  - 过程记录：清理挂住的评测进程时，我用匹配 `app.cli.main` 的循环**把自己的 shell 也杀了**
    （exit 137）—— 正是 `docs/COORDINATION.md` 冲突记录里记着的同一类坑
    （"不要用匹配自身命令行的模式去杀进程"）。后续改用括号技巧 `ma[i]n` 规避自匹配。
