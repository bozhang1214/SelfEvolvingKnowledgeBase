## 2026-10-08（契约夹具补机械守卫：6 类升级信号必须**逐个**被覆盖）

- **背景**：`apps/contract/signals.json` 从 2026-09-21 起就有"≥13 个 case 才算没被截断"的下界
  （Android `ContractFixturesTest` 与 `scripts/check_edge_facts.py` 各一份）。但**只看总数是不够的**：
  把某一类信号的用例删到只剩别的信号顶上，总数照样 ≥13，而**那一类行为就再没人测**——
  这正是本仓库反复吃的亏（"不能失败的检查等于不存在"的同族问题）。
  6 类升级信号是端云"升级率可比"的语义基础（`PlaneRouter.evaluate` 与服务端 `plane_router` 同口径），
  少覆盖一类意味着该类的漂移**没有任何机械检查能发现**。

- **改动**：`scripts/check_edge_facts.py` 新增第 ⑤ 项检查——`signals.json` 的 `expectSignals` 并集
  必须包含 `json_invalid` / `empty` / `degenerate` / `timeout` / `low_confidence` / `tool_hallucination` 六类。
  - ⚠️ **`context_overflow` 明确不算在内**：它是**事前**不走端侧的预算判据（由 `routing.json` 覆盖，
    见 `docs/ops/16-端云协同协议.md` §6），把它列进来会变成"永远缺一项"的假告警。
  - 该检查同时打印"升级信号覆盖：…"，让"真的覆盖到了哪些"可见（而不是只报 0 错）。

- **验证**：
  - `python3 scripts/check_edge_facts.py` → 覆盖 6 类全齐、37 case、`android_unit_cases=292` ✅；
  - **反向验证**（守卫必须会红）：把 `signals.json` 里所有 `timeout` 期望信号摘掉
    → 立即报「契约夹具 signals.json 没有覆盖这些升级信号：timeout」并退出 1；
    还原后（`git status apps/contract/` 为空，确认夹具未被改动）回绿。
