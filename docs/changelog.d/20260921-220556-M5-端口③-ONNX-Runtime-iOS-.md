## 2026-09-21（M5 端口③：ONNX Runtime iOS 被网络卡死——实测证据与两条可行路径）

- **背景**：端侧真嵌入需要 ONNX Runtime iOS（或 Core ML）。上轮只是"未评估"，本轮把它**测清楚**。

- **实测证据（2026-09-21）**：
  | 路径 | 结果 |
  |---|---|
  | GitHub Release：`onnxruntime-objc-1.20.0.zip` | **HTTP 000（不可达）** |
  | CocoaPods CDN `cdn.cocoapods.org` | 200（可达）——但 podspec 的 `source` 仍指向 GitHub，所以拉不到二进制 |
  | Maven（aliyun 镜像） | 只有 `onnxruntime`（JVM）与 `onnxruntime-android`，**没有 iOS 产物** |
  | 本机 CocoaPods / 本地缓存 | 未安装 `pod`；`~/.cocoapods` 与 `.tooling` 下都没有 ORT 产物 |

- **结论**：端口③ 在**当前网络条件**下无法完成，属于环境阻塞而非实现缺陷。
  两条可行路径（按推荐顺序）：
  1. **在有 GitHub 访问的机器上取回 ORT iOS xcframework**（或给本机配代理），然后按现有
     "swiftc 直编 + 手搓 .app" 的路子链接——共享层的 `EmbeddingProvider` 接口不用改，
     只需在 Swift 侧写一个 `OrtBgeEmbedding` 实现；
  2. **`coremltools` 转 Core ML**：需要 pip 安装（pip 镜像可用性未验证），且**必须重标检索阈值**
     （换空间 → 分数分布变化，这是 M3 已经吃过一次的教训）。

- **影响与对策**：iOS 侧的检索链路**已经跑通**（上一轮：`rag_ingest`/`rag_retrieve`/
  `rag_threshold_refuses`/`rag_device_only_gate`），只是嵌入用的是共享层的确定性桩。
  因此端口③ 的缺口**不阻塞** M6/M7/M8 —— 下一步按计划转入 **M6 鸿蒙 spike**（它只依赖
  本机的 DevEco SDK + OHOS NDK，不受 GitHub 网络影响）。
