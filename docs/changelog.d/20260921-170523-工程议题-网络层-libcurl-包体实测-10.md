## 2026-09-21（工程议题：网络层 libcurl / 包体实测 102MB 与插件化 / 热修复三层；四端方案已确认）

- **背景**：owner 确认四端收敛方案（§9 的 6 条全通过），并追加三条工程建议：
  ① 网络库优先考虑 **libcurl** 统一；② 跨端会增加包体，是否**提前考虑插件化**；③ 是否一起做**热修复**。
  这三件事都不该靠态度回答，所以本轮先查本机事实、再给结论。

- **改动**（**只写文档，未动代码**）：
  - 新增 `docs/多端跨端-工程议题（网络层·包体·热修复）.md`：
    - **网络层**：现状接口已统一（`HttpTransport` + SSE 解析在共享层，平台实现合计仅 ~400 行）。
      **本机实测**：iOS SDK **没有** curl（`iPhoneOS.sdk` 下 `find -iname "*curl*"` 为空，macOS SDK 有）、
      OHOS sysroot **没有** curl / openssl / mbedtls、Android NDK 30 已装但不提供受支持 TLS
      → 全 libcurl 意味着**自建 libcurl+TLS 的 3 条交叉编译链**，且在 iOS 上放弃 ATS/系统代理/后台传输语义。
      结论：**路线 B**——Android + 鸿蒙共用一份 libcurl（C 实现），iOS 保留 NSURLSession，JVM 保留 OkHttp；
      M4 先建 **SSE 一致性夹具**，libcurl 实现放 M5 之后（不阻塞 iOS）。
    - **包体**：实测当前 debug APK **102 MB**（解包 154 MB / 257 项），其中
      `libonnxruntime.so` **四个 ABI 合计 70.4 MB（69%）**、debug dex ~66 MB、BouncyCastle PQC 属性 ~6.7 MB。
      → **跨端增量（KMP 框架）只有 3–5 MB**，真正该做的是与跨端无关的免费瘦身：
      **ABI split / App Bundle（−53 MB）+ 资源排除（−6.7 MB）+ release R8**，建议 **M4 随手做**；
      模型/词表走"首次下载 + sha256 + 空间戳校验"（现在模型本来就不在包里，是 adb push）。
      插件化边界：**iOS 明确禁止下发可执行代码（App Store 3.2.2）** → "插件化"= **资源按需**（`AssetBundlePort`），
      代码插件化只写触发条件（>10 MB 且渠道允许且可回滚，三条同时满足）不实现。
    - **热修复**：分三层——**L1 策略/配置**（阈值/升级信号/提示词/工具白名单，四端都可行，我们已有一半）、
      **L2 资源/模型**（四端可行）、**L3 代码**（Android 自建渠道可评估；**iOS 禁止**；鸿蒙待验）。
      建议 L1+L2 做成正式能力（云端下发 + 本地缓存 + 签名 + 灰度 + 回滚 + 审计 + **可变项白名单**），
      并写死一条硬约束：**策略必须带 `embeddingSpace` 绑定，空间不符即拒绝应用**——
      否则"热修"会变成"远程把检索改坏"的通道（M3 已吃过阈值必须随模型重标定的教训）。
