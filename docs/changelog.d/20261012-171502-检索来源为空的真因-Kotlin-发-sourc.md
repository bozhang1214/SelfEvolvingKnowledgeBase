## 2026-10-26（"检索来源为空"的真因：**字段名不一致** —— Kotlin 发 `source`、ArkTS 读 `sourceId`；`rag_retrieve` 转 PASS）

### 真因（一行字段名，害了几轮）
`SekbApp.retrieve()` 组装命中时写的是：
```kotlin
e.put("source", h.sourceId)      // 发的键是 "source"
```
而 ArkTS 侧的接口声明与取值是：
```ts
interface RawHit { sourceId: string }       // 声明成 sourceId
hits.push(new Source(h.sourceId, ...))      // 取 h.sourceId → 永远 undefined
```
→ `Source.sourceId` 恒为 `''`。症状**极具误导性**：向量检索能给出合理分数（0.696），
只有"来源名"是空的，看起来像"检索没命中/掩码有问题"，于是前几轮一直在查 RAG 的算法与 RDB 层。

**修法**：ArkTS 侧改为**读 `source`（Kotlin 真名）并兼容 `sourceId`**；
同时给命中补上诊断字段 `id`（`<sourceId>#<片号>`）与 `dim`（向量维度），
用来区分"命中错误/遗留的行"与"向量是零向量"——Kotlin 侧也一并发出这两个字段。

### 效果（设备实测）
```
修前: [FAIL] rag_retrieve — 检索 → 1 条，首条=@0.696        ← 来源为空
修后: [PASS] rag_retrieve — 检索 → 1 条，首条=__selftest__@0.696
```
**"检索来源"这条链路在鸿蒙上通了**（自检项 `rag_retrieve` PASS，与 Android 的 0.630 同量级；
本轮 0.696 是自检自己的短文语料）。

### 顺带发现的最短路径（下一轮直接做）
`rag_retrieve` 用的是**上一轮遗留的 `__selftest__` 行**（自检库 `sekb_docs.db` 跨轮保留），
所以"检索能命中"目前有一部分是残留数据撑起来的。**必须让自检库每轮干净**：
- 现有 `rag_selftest_cleanup` 只删文档登记，**不删切片**；
- 而 `rag_ingest` 报"总片段 0 段"（`documents()` 读到 0）与 `dbChunks=1`（`size()` 读到 1）矛盾 ⇒
  写入的切片与登记的文档数量**对不上**，要么登记没写 `chunks` 列，要么 `documents()` 读法不同源。
下一轮顺序：① 让自检每轮用**干净库**（或先 `clear()`）；② 查 `documents()` 的 `chunks` 列为何是 0；
③ 两个都对上之后，才能做 **H5 的检索评测同表**。

### 教训（与上一轮同源，值得合并成一条纪律）
`?: continue`（静默跳过整行）、`?: ""`（静默变成空串）、**字段名两边不一致**，
都会把"读不到"伪装成"没有"。端侧跨语言（Kotlin ↔ ArkTS/Swift）时，
**每个返回值字段都应在两侧各有一条断言**——本轮两处真缺陷（游标长度、字段名）都属这一类。
