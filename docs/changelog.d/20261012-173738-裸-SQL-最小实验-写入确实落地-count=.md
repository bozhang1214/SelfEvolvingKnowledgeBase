## 2026-10-26（裸 SQL 最小实验的结论：**写入落地、读取可用**——所以生产路径的失败不是"C API 不能用"）

### 实验（探针里新加的 `raw_sql_visible`，只用裸 SQL，不经任何封装）
```
fresh_db_is_empty PASS — delete+open 后条数=0 内容=[]
raw_sql_visible  — create=0 insert=0 count=-1 val='hello'
                   轨迹=[v: idx=0 size=6 getText(size)=0/'hello' getText(size+1)=0/'hello']
```
（那一次 `count=-1` 是因为同一次运行里我把 `vs.size()` 与裸 `store` 的查询混在了一起；紧接着的另一次运行
给出 `count=1`。两次合起来才说明问题，**单看一行会误判**——这也是我这几轮反复被绕的原因之一。）

**合并两次运行的结论**：
1. 裸 SQL 的 `CREATE TABLE` / `INSERT OR REPLACE` 返回 `0`（成功），随后 `SELECT COUNT(*)` **= 1** ⇒ **写入确实落地**；
2. `getText` 在 `size` 与 `size+1` 两种长度下都返回 `0`（成功），值正确读出 `'hello'` ⇒ **文本读取本身可用**。

⇒ 因此"生产路径写后读不到"**不是**"`OH_Rdb_Execute`/游标这些 C API 在这个平台上不能用"，
而是**我们这层封装/用法里有状态相关的问题**（同一批断言在相邻两次运行里给出不同结果）。
这反而**支持先修封装**，而不是整体换掉。

### 但本轮的时间预算已经用完，必须做个了断
决断（下一轮第一天执行，不再做新的 C 路径实验）：
1. **把 `RdbVectorStore.upsert` 里的"写后立即回读"当成硬断言**：`begin/before/inTx/commit/after` 五个数
   中 `after` 必须 ≥ `before + records.size`，否则**直接抛错**（不再静默继续）。
   本轮已经把 `lastTx` 带进返回值，这一步只是把"看着不对"升级成"当场失败"。
2. **自检每轮从空库开始**：`fresh_db_is_empty` 已是判据；把它接到自检流程开头（不满足则先 `clear()`）。
3. 只有在 1、2 都做完、且仍有"写后读不到"时，才把这两个端口换到 **ArkTS `relationalStore`**
   （接口不变、共享层零改动）。**不再盲目换实现。**
