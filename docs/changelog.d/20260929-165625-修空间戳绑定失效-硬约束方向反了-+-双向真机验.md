## 2026-09-25（修一处硬约束方向反了：L1 空间戳绑定失效，含真机双向验证）

- **怎么发现的**：§1.8 断网自检时注意到——设备**实际使用**的嵌入空间是 `…-int8@512`，
  而成功应用的策略包空间戳是 `…@512`（不带 int8）**却通过了校验**。

- **根因**：`EdgePolicy.apply` 比的是 `EdgeRuntimeConfig.embeddingSpace`，而该 config 在
  `SekbApp` 第 56 行就构造了——那时还不知道本机跑 fp32 还是 int8（`int8Available` 在第 100 行才算），
  于是一直保留默认值 `…@512`；检索器用的却是 `if (int8Available) …-int8@512 else …@512`。
  **本机 int8 生效 → 两者不一致。** 这道硬约束的目的正是"防止为某空间调的阈值被用到另一空间上
  把检索改坏"，结果方向反了：
  - `…-int8@512`（本机真正需要的）→ **被拒**；
  - `…@512`（fp32）→ **被接受并应用到 int8 检索器**。

- **修法**：嵌入器就绪后把 config 的空间对齐到 `embeddingProvider.space.id`——
  **由构造保证同源**，而不是靠"记得同步"。已加注释说明该坑。

- **真机双向验证（服务端签名的两份策略包）**：
  | 用例 | 修复前 | 修复后 |
  |---|---|---|
  | int8 空间（`minScore=0.62`） | `应用=null`（被拒） | ✅ `阈值 0.5→0.62` + `检索器阈值=0.62` |
  | fp32 空间（`minScore=0.71`） | 被接受（**错**） | ✅ 被拒（`应用=null`） |
  恢复正确策略后自检回 **31 PASS / 0 FAIL / 1 SKIP**。

- **顺带发现（留待下轮）**：自检把"策略被**正确**拒绝"报成 FAIL（`PASS=28 FAIL=3`），
  因为它假定注入的策略一定合法。我自己就先误读了一次。应改为打印拒绝原因，
  并在"预期可拒"（空间/签名不符）时记 SKIP 而非 FAIL。

- 验证：Android 291 用例 / 0 失败；真机自检 31 PASS / 0 FAIL / 1 SKIP；doc_guard 6/6。
