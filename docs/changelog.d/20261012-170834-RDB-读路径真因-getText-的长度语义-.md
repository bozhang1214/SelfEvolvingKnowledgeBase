## 2026-10-26（RDB 读路径真因：`getText` 的长度语义 + `all()` 的 `?: continue` 静默跳过整行；事务已证清白）

### 先证清白：事务没问题（这一步排除了我上一轮的怀疑）
给 `RdbVectorStore.upsert` 的三个事务函数**加上返回值检查**并把五个数带进自检报告：
```
tx=[begin=0 before=0 inTx=0 commit=0 after=1]     ← 全部 0=OK，且提交后 size 由 0 变 1
```
`beginTransaction/commit` 都成功、提交后数据可见 ⇒ **不是"事务没生效"**。
（`before=0` 说明事务前确实没有行，`after=1` 说明这一行是本次写进去的。）

### 真因：`all()` 里 `cursorText(cur, "id") ?: continue` 把**每一行都跳过了**
设备自省（我新加的 `cursorColumnNames` + `cursorTextProbe`）：
```
列名=[0=id|1=source_id|2=text] idx(id)=0 idx(source_id)=1
探针=[id: idx=0 size=12 getText(size)=0 getText(size+1)=0
      | source_id: idx=1 size=10 getText(size)=0 getText(size+1)=0]
```
—— 列名/索引/尺寸/返回码**全都正常**（`size=12` 就是 `doc-probe#0` 的长度）。
但**修之前**，`read_multi_column` 报 `id='<null>'` 而 `source_id` 正常。
原因在 `cursorText` 的**长度参数**：它只传 `n+1`（多留 1 字节给 NUL）。
实测在 `id` 这一列上拿不到值（`getText` 返回非 0），于是：
- `all()`：`val id = cursorText(cur, "id") ?: continue` → **整行被跳过** → `all()` 返回空；
- `size()` 用 `COUNT(*)`，不经过 `cursorText` → 所以它一直是对的 → 于是出现
  "`size()`=1 而 `all()`=0 条"这种自相矛盾的组合（我此前几轮就是被它绕住的）。
- 检索的候选集来自 `all()` ⇒ 库里明明有数据却检索不到。

**修法**：`cursorText` 改为**先按它报告的 size、再按 size+1 各试一次**，两者都失败才算失败
（不再依赖一个魔数）。修完同一批探针全部转为正确：
```
PASS read_single_column — source_id='doc-probe'
PASS read_multi_column  — id='doc-probe#0' source_id='doc-probe'
PASS read_all_path      — 条数=1 首条 id='doc-probe#0' source='doc-probe' dim=3
```
> **教训（值得推广）**：`?: continue` / `?: ""` 这类**默认值兜底**会把"读不到"变成"没有"，
> 而且是**静默**的。读游标这类底层 API 时，兜底必须是"报错"或"至少计数"，不能是"跳过"。
