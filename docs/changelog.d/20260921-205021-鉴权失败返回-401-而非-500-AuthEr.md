## 2026-09-21（鉴权失败返回 401 而非 500（AuthError 未被处理器接住））

- **背景**：在服务器上按手册验证白名单时，`curl -H "Authorization: Bearer <邮箱>"` 打
  `/api/v1/auth/me` 返回的是 **500**：

  ```json
  {"error":"InternalServerError","error_id":"02ccf068c24a","message":"服务内部错误，请稍后重试"}
  ```

  查日志拿到完整堆栈：`verify_jwt` 抛的是 `AuthError("无效的 token")` —— 语义上就是 401，
  却一路冒到 Starlette 的 `ServerErrorMiddleware` 变成「未处理异常」。

- **根因**：`AuthError` 继承的是 `Exception` 而**不是** `SEKBError`
  （`app/core/exceptions.py:122`），所以它穿过了三处已注册的处理器中的前两处
  （`SEKBError`、`HTTPException`），落进兜底的 `Exception` 处理器 → 500。
  而 `_claims_or_401` 的注释早就写着「缺失/无效统一 401」——**「缺失」那半条是好的
  （HTTPBearer 抛 HTTPException），「无效」这半条从来没生效过**。

- **为什么不是小事**：前端**只在 401 时**才判定 token 失效并跳登录页
  （`frontend/src/services/api.ts:68-71`）。于是 token 过期/被吊销/畸形时，
  用户看到的是「服务内部错误」——既不跳登录，也不清 token；同时 500 会污染错误日志与指标。

- **改动**：`app/api/server.py` 新增 `@app.exception_handler(AuthError)`，
  按其自带的 `status_code` 返回，响应体用 `{"detail": ...}`（与 HTTPException 处理器的
  4xx 形状一致，前端无需单开解析路径），并按 `info` 级别记一条「鉴权失败」。

- **验证**：
  - 新增 `tests/unit/test_auth_error_status.py` 4 例：畸形 token / 过期 / 已吊销 / 缺失
    Authorization 头，全部必须 **401**（前三条在修复前是 500）。
  - **A/B 实测**（同一份代码，仅在首请求前撤掉该处理器）：
    `A 有处理器 → 401 {'detail': '无效的 token'}`；`B 撤掉处理器 → 500 ['error','error_id','message']`
    —— B 与线上看到的响应完全一致。
  - `pytest tests/unit` → **978 passed**；ruff 全过；mypy 309 ≤ 基线 310（多出的 1 个在
    协作者的 `bocha_server.py`，与本次无关）。
  - 活数字对齐实测：`backend_unit_cases` 955→978（60→62 文件）、全量 971→994。
