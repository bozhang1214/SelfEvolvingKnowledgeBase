## 2026-10-09（鸿蒙 H3/HR9 探针：libcurl 在设备上不可用（dlopen 权威判据）+ 平台能力清单）

- **背景**：C2 定"网络统一 libcurl（与 Android 共用一份 C 实现）"，HR9 要求先写三个最小探针
  （能编 / HTTPS GET / SSE 逐行），任一不通就回头报告。本轮把探针做成了可复现动作并拿到结论。

- **改动**：
  - `napi_init.cpp` 新增 `LibProbe`：在设备上 **dlopen** 一组候选库并 dlsym
    `curl_easy_*`（变参 `curl_easy_setopt` 用显式函数指针类型调用，常量按 curl 的 ABI 承诺硬编码），
    加载成功则继续做 HTTPS GET + 写回调逐行计数。
  - `module.json5` 加 `ohos.permission.INTERNET` / `GET_NETWORK_INFO`（+ `string.json` 两条 reason）。
  - 新增 `bash scripts/harmony.sh probe [秒数]`：只重打 HAP（不重编 KMP）→ 装 → 起 → 打印 dlopen 结果并断言。

- **验证**（模拟器 127.0.0.1:5555）：
  - `libcurl.so` 及 `libcurl.z.so` / `libcurl_shared.z.so` / `libcurl_ndk.z.so` /
    `/system/lib64/libcurl.so` **全部 dlopen FAIL**（`No such file or directory`），
    且 `libcrypto.so`/`libssl.so` 也没有 → `PROBE1 FAIL`，**H3 无法按 C2 用 libcurl 落地**。
  - 同时确认可用：`libhuks_ndk.z.so` ✅、`libnative_rdb_ndk.z.so` ✅（**RDB 的 NDK C API**）、
    `libohcrypto.so` ✅、`libmindspore_lite_ndk.so` ✅、`libnet_ssl.so` ✅、`libz.so` ✅。
    → H4（凭证）与 H5（向量库/文档登记）可以**纯 Kotlin/Native cinterop** 落地，不需要 ArkTS 桥；
      C3 的 relationalStore 引擎意图保留（RDB 正是其底层）。
  - 记下三条**误判**（都实测过）：`hdc shell test -e` 对已确认在跑的 mindspore 库也报 MISSING；
    host 侧 grep 系统镜像 `libcurl.so` 命中 64 处但库并不存在；sysroot 里连 curl 头都没有。

- **未验 / 待 owner 决策**：H3 的完整 `HttpTransport` 未开工（HR9 出口三选一：
  `@ohos.net.http` / 自写 HTTPS（libnet_ssl+socket）/ 交叉编译 libcurl 静态进包）。
  H4 的 enroll/refresh 自检依赖网络、一并被该决策阻塞；HUKS 往返本身不依赖网络。
