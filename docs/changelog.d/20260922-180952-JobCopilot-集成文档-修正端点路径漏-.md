## 2026-09-22（JobCopilot 集成文档：修正端点路径漏 /jobcopilot 前缀 + 厘清两个鉴权头）

- **背景**：owner 接入扣子（Coze）时 `test_run` 返回
  `{"error": "访问令牌不正确"}`（401，地址 `https://bos-studio.tech/jobcopilot/mcp`）。
  排查结论：**不是代码问题，是集成文档的示例写错了**，且错误在**五篇平台文档 + 索引表**里都有。

- **改动**（`jobcopilot` 子模块，指针同步更新于本提交）：
  - **`url` 漏了子路径前缀**：示例一律写 `https://<你的域名>/mcp`，而本项目公网部署经 nginx
    挂在 `/jobcopilot/` 下（`location /jobcopilot/` + 容器 `JOBCOPILOT_HTTP_BASE_PATH=/jobcopilot`），
    端点是 `/jobcopilot/mcp`。五篇文档 + 索引表全部补上前缀，并说明**只有直接暴露内核、
    无反向代理子路径的自建部署**才是 `https://域名/mcp`。
  - **示例 headers 只写了 `Authorization`，且写成"你的 LLM Key 或访问令牌"**——两者语义完全不同：
    `Authorization: Bearer <x>` 只是**服务访问令牌**（`JOBCOPILOT_HTTP_TOKEN`，门禁中间件最先校验），
    **BYOK 的 LLM Key 必须另放 `X-JobCopilot-Api-Key`**。示例 JSON 已补齐该头。
  - `coze.md` 新增**排障对照表**（三种返回逐字对应，均为 curl 实测）：
    `缺少访问令牌`（没带或忘 `Bearer ` 前缀）/ `访问令牌不正确`（填了 LLM Key 或令牌已轮换）/
    `400 Missing session ID`（✅ 令牌对了）。
  - **新发现的真实限制**：千帆只能把凭据放进查询串，而查询串只认 `token`/`access_token` 两个名字
    且由**门禁**消费；BYOK Key 只能走 `X-JobCopilot-Api-Key` **头**，而千帆的配置结构**没有
    `headers` 字段**。⇒ **公网端点上千帆无法 BYOK**，`analyze_job` / `analyze_jobs_batch`
    这类要调 LLM 的工具会失败（服务端为公网端点刻意不配 LLM Key）。已在 `qianfan.md`
    与索引表显著标注。
  - **未改**：`DEPLOY-HTTP.md` 的 `location /mcp` 自建配方本身正确（根路径部署），
    故其 `https://mcp.example.com/mcp` 保持不变。

- **验证**（全部实测，secret-free）：
  - 对生产端点做了三次**不带任何密钥**的 curl，确认服务健康且能与 owner 的报错逐字对上：
    不带令牌 → `缺少访问令牌`(401)；`Bearer <错令牌>` → **`访问令牌不正确`(401)**；
    `Authorization` 不带 `Bearer ` 前缀 → `缺少访问令牌`(401)。由此反证：owner 的请求**确实带了
    `Bearer <某值>`**，只是该值与服务器 `JOBCOPILOT_HTTP_TOKEN` 不相等。
  - 顺带证明 nginx 未吞头：`deploy/nginx.conf` 的 `/jobcopilot/` 段只设 `Host`/`X-Real-IP`/
    `X-Forwarded-For`/`X-Forwarded-Proto`，没有触碰 `Authorization`。
  - 子模块改动已推送（`7a6f8a7..4d0b262`），SEKB 指针在同一提交内更新。
  - `bash scripts/check_kernel.sh` → 内核状态正常（改前确认无人在动）。
