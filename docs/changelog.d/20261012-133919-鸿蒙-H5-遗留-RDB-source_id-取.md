## 2026-10-26（鸿蒙 H5 遗留：`source_id` 取证探针；并查明 F 的两个动作为何"没输出"）

- **背景**：H8 的自检里出现了**两条互相矛盾**的证据 ——
  ① 向量检索能命中并给出分数（`=@0.696`）；② 同一个命中项的 `sourceId` 读回来是**空串**，
  于是 `deleteBySource("doc-rag")` 删 0 行、检索来源名显示为空。
  两者不可能同时为真：要么"写"错了，要么"读"错了。两个工作流都已收工，故由主线用最小用例把它钉死。

- **改动（主线新增，不改两个工作流的文件）**：
  1. `apps/harmony/spike/knspike/src/ohosMain/kotlin/RdbIdProbe.kt`（新文件）：一条最小、可证伪的往返探针，
     **判据刻意分层**（避免"结论依赖结论"）：
     - 建隔离库 → `upsert` 一条已知记录（`sourceId="doc-probe"`）；
     - `SELECT source_id FROM chunks`（**单列**）→ 直接看库里那一列是什么；
     - `SELECT id, source_id, text`（**多列**）→ 验"按列名取索引"这条路（H8 现象指向它）；
     - `all()`（**生产读法**：四列 + BLOB）→ 验生产路径；
     - `deleteBySource` 是否删到 1 行、`dim_mismatch_refused` 是否报错。
     首行 `RDBID PASS n/N`，与既有自检同格式。
  2. NAPI 入口 `rdbIdProbe(databaseDir, runTag)` 注册在 **`h3h4_napi.cpp`**（`napi_init.cpp` 主线独占、
     不挤进去；这个"各域自己的 `.cpp`"形态正是事故后定下的约定）。
  3. `scripts/harmony.sh` 新增 `rdbid` 动作；`Index.ets` 的探针段接上它。

- **查明的一个重要事实（否则下一个人会以为探针坏了）**：
  H8 把入口页从 `pages/Index` 换成了 `pages/AppShell`（`EntryAbility` 里 `loadContent('pages/AppShell')`），
  而 F 的 `rdbProbe`/`ragSelfTest` 探针是写在 **`Index.ets` 的 `aboutToAppear()`** 里的
  —— 于是 **`harmony.sh rdbprobe` / `rag` 两个动作现在没有输出**（Index 不再被加载，那段代码不执行）。
  实测：`bash scripts/harmony.sh rdbid 40` 得到 `exit=1 没抓到 RDBID 行`，设备 hilog 里
  `SEKB_KN_SPIKE` 只有 H3 那一行 `HTTP run #1 GET .../api/tags → HTTP 200`，**RDB 段一行都没有**。
  → **下一步的落点很明确**：把 `rdbIdProbe`（以及 F 的 `rdbProbe`/`ragSelfTest` 若要复活）
  接进 **`ets/model/SelfTestRunner.ets`** ——那才是现在真正在跑的入口
  （`EntryAbility` 在 `-A SEKB_SELFTEST` 时调它，`SEKB_HARMONY_SELFTEST` 表就是它出的）。
  本轮**没有**替 G 改 `SelfTestRunner.ets`（那是它的文件且刚交付，改动面不小），
  如实记为待办而不是"改完了"。
