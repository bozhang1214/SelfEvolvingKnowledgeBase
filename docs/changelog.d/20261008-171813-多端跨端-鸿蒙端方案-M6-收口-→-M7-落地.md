## 2026-10-08（多端跨端：鸿蒙端方案（M6 收口 → M7 落地，对标 Android 同级））

- **背景**：owner 定了鸿蒙的验收口径——**与 Android 端侧 App 同级（功能完整可用）**，且**没有真机，全部在鸿蒙模拟器上验收**。
  而当时的公开结论（RFC §7 M6/M7、`apps/README.md` 四端状态表）仍写着"运行期/装机等真机、M7 未启动"，
  与实测已经脱节。需要一份能把 M6 收口 + M7 落地讲清、且每一步都可证伪的**整体方案**。

- **依据**：三份只读调研（Android 设计/实现/验收体系；多端收敛口径 + 契约夹具 + iOS 先例；鸿蒙现有资产与缺口）
  + `RFC-多端跨端方案.md`（v1.1.0）+ `apps/README.md`。

- **关键更正（推翻/更新了既有结论，全部带证据）**：
  1. **"唯一阻塞 = 真机 + 签名"已不成立**：模拟器上**未签名 HAP 可装**、能起、NAPI↔KMP 通
     （`ping=42`），且 MindSpore Lite **推理已跑出向量**（`elemNum=262144 firstFloat=173347`，设备持久化 hilog 为证）；
     `build-profile.json5` 其实**已含签名材料**（README 那三处说法过时）。
  2. **模拟器是 arm64 而非 x86_64**（`nova 16 Pro` / HarmonyOS 6.0.2 / `"abi": "arm"`）→ 现行双 ABI 打包有一半体积白费。
  3. **共享层端口实际是 6 个**（`HttpTransport`/`EmbeddingProvider`/`VectorStore`/`DocumentRegistry`/`CredentialStore`/`PolicyStore`），
     而 KMP 方案 §3.2 里规划的 `FileSourcePort` 等 5 个端口**在代码里并不存在**。
  4. **iOS 先例的边界**：iOS 只到"四端口 + 自检页"（**没有**聊天/文档/设置 UI），所以**不能拿它 ≈2 天估鸿蒙**——
     owner 要的是含 UI 的完整可用，UI 规模应参照 Android（25 文件 / 4,785 行）。
  5. **契约夹具实际只有 Android/JVM 在跑**，iOS/Mac 没有 runner（`apps/contract/README.md` 的 ⬜ 标注已过期）。
