## 2026-09-23（职位采集：一条搜索支持多关键词（逗号分隔，逐词采集+去重合并））

- **背景**：`JobCollector.fetch_all(keyword=...)` 只接受**一个**关键词字符串，
  于是一条搜索无法覆盖同义的岗位族。FDE（Forward Deployed Engineer）就是典型：
  北京市场同类岗位散落在 `FDE` / `前沿部署` / `前向部署` / `Forward Deployed` /
  `交付工程师` / `部署工程师` 六个词下，共 205 条原始职位；用户在前端被迫维护 **6~7 条**搜索，
  既重复又难以「看整体」。
  更糟的是：把 6 个词的结果**手工合并**成一条搜索后，那条搜索的 keyword 是个合成标签
  （如 `第四层·企业级AI Agent交付(FDE)`），点「刷新」拿它去采集只会搜出噪声——**看着有、实则不能更新**。

- **改动**：
  - `backend/app/agents/job/collector.py`：
    · 新增 `split_keywords()`——按英文逗号 `,`（兼容中文 `，`）拆分，去空白、**去重且保序**、丢弃空项；
      单关键词输入原样返回单元素列表，**旧调用方行为完全不变**。
    · `fetch_all()` 改为**逐关键词**采集（每个词内部仍是各源并行），跨词结果统一去重合并；
      `per_source` 的 `raw/count` 改为各关键词的累加值（采集量口径），`count` 仍是去重后的总数。
    · 刻意**不用全笛卡尔并发**（词数 × 源数一次性 gather）——避免对招聘站点瞬时压力过大。
    · 模块 docstring 加了显式警告：分隔符**不可用 `|`**，因为
      `job_cache.parse_key()` 用 `|` 切分存储键取 keyword，关键词含 `|` 会把
      keyword/city/薪资全部解析串位（`cache_key` 的格式是 `user|keyword|city|min_salary`）。
  - `backend/tests/unit/test_job_collector.py`（新增，16 个用例）：
    · `split_keywords` 参数化覆盖单/多/中文逗号/空白/空项/去重/`None`；
      并锁死 `a|b` 必须保持字面量（防有人日后错把 `|` 当分隔符）。
    · `fetch_all` 覆盖：单关键词行为不变、多关键词跨词去重、`per_source` 累加口径、
      城市与薪资下限过滤仍生效、空关键词不触发任何采集。
    · 采集源用桩注入（`collector._sources = [stub]`），**不触网**。

- **验证**：
  - `ruff check app/ tests/` 通过；`bash scripts/mypy_gate.sh` → 300 ≤ 基线 310，无新增类型错误。
  - `pytest tests/unit/test_job_collector.py` → **16 passed**。

- **附：线上生效方式**：一条搜索的 `keyword` 直接写成逗号列表即可，例如
  `FDE,前沿部署,前向部署,Forward Deployed`——前端无需改动（keyword 本就是字符串透传）。
  注意 `keyword` 同时是缓存键的一部分（`cache_key`），**改动 keyword 会得到新的 `search_id`**，
  旧搜索条目不会被自动迁移，需要显式清理。
