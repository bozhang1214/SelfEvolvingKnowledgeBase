## 2026-10-25（鸿蒙 H1 开工笔记：先证伪 HR1 的"复合构建"，并给出三种可行形态）

- **只读探路（未改任何构建）**后得到一条会影响 H1 做法的判断：
  `apps/shared` 用 **AGP 9 专属 DSL**（`com.android.kotlin.multiplatform.library` + `androidLibrary {}`），
  而 `apps/harmony/spike` 是**独立构建**、其 OHOS Kotlin fork 配套 **AGP 8.11.2**
  （spike 的 settings 注释写明"故意独立"）。→ HR1 的**选项①`includeBuild` 让共享层用 fork 重编**，
  极可能**在插件应用阶段就失败**（不是"可能撞版本"）。
- **给出三种形态并按代价排序**（推荐第 1 种）：① 抽出**不含 Android 插件**的纯 KMP 模块
  （`apps/shared-core`）供两侧各自依赖——一处源码两侧编译，**不动已全量验证的 Android 基线**；
  ② 共享层加条件开关的 `ohosArm64()` + 另一份 settings 指同一批 `srcDirs`；③ 按 RFC §5.1 统一 wrapper
  （最彻底但动 Android 基线，须单独提交 + 回滚 tag）。
- **H1 下一步**：先花 10 分钟用 `includeBuild` 试一次、**拿到"是否插件阶段失败"这一个事实**再选形态；
  再写 `ohosMain` 的 `Clock`/`Hmac`/`Digests` actual（⚠️ **鸿蒙侧的加密 API 尚未确定**，
  不要照抄 Apple 的 CommonCrypto）；然后接 `:shared`、跑 interop smoke、并给 `harmony.sh` 补 `smoke` 动作。
- **为什么本轮只写判断不写代码**：H1 要动 `apps/shared`（协作共享区），而形态未定前改构建脚本的风险是
  "把已全量验证的 Android 基线弄坏"。故把事实与选项交清，下一轮拿到关键事实后再动手。
