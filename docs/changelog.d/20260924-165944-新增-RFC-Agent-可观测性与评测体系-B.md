## 2026-09-24（新增 RFC：Agent 可观测性与评测体系（B1 方案设计））

- **背景**：FDE（Forward Deployed Engineer）岗位 JD 高频要求「构建高性能的评估管道和可观测性框架」
  「对交付效果负责，构建评测方案并持续迭代直至业务指标达标」。对照 SEKB 现状："能跑"已做到，
  "**能证明效果、能定位退化**"还差一段。本次不实现，只出**交给他人的方案设计**。

  盘点中发现一个反直觉结论：**主要工作不是"接入 LangSmith/LangFuse"，而是"把已接上的接对、并让它成为门禁"**——
  已有的基础设施比预期多得多：

  | 已有 | 证据 |
  |---|---|
  | 23 个 Prometheus 自定义指标（含 LLM 延迟/调用/Token/成本/重试/降级） | `backend/app/core/metrics.py` |
  | 单次调用粒度埋点 `record_llm_call` **已接入** | `backend/app/core/llm_factory.py:944` |
  | LangSmith 接入代码 + trace_id 注入 RunnableConfig | `backend/app/core/tracing.py:21,57` |
  | 完整评测框架 + 2 个 golden 数据集 + CLI | `backend/app/eval/`、`backend/app/cli/eval.py` |
  | Grafana 3 个 LLM 面板 + 完整监控栈 | `deploy/grafana/…/sekb-overview.json`、`docker-compose.monitoring.yml` |

- **改动**：新增 `docs/RFC-Agent可观测性与评测体系.md`（设计 RFC，**不含实现**）。要点：

  **① 缺口清单（带证据）**
  - Token/成本**无法按 Agent 归因**（`llm_tokens_total`:75、`llm_cost_usd_total`:82 缺 `role` 标签）
  - **生产未启用任何链路追踪**（运行时日志 `{"enabled": false, "provider": "langsmith"}`，缺 API Key）
  - **跨容器 MCP 无追踪**（内核跑在独立容器 `docker-compose.prod.yml:268`，自动埋点不跨进程）
  - **CI 评测是"假门禁"**（`.github/workflows/ci.yml:239` 的 `|| echo "eval non-blocking"`；`app/cli/eval.py` 全文件 0 处 `sys.exit`）
  - 三个指标（`conversations_total`/`reflection_pass_rate`/`tool_call_latency_seconds`）**定义后从未埋点**
  - Grafana 缺延迟面板与按 Agent 分解

  **② 顺带核查出两个既有缺陷（P0 必须先修，否则新面板建在错数据上）**
  - **缺陷 A：Token 与成本被重复计数约 2×**——`record_llm_call` 接入后，
    `record_chat_metrics` 里的聚合写入未删除，两者写**同一个 Prometheus 序列**
    （`metrics.py:267-270` vs `:361-365`），聊天路径下同一笔 token/成本记两次。
    影响：现有「LLM Token 用量」「LLM 成本累计」两个面板数字**偏高约一倍**。
  - **缺陷 B：`LLMStats.records` 无界增长**——`llm_factory.py:96` 定义、`:893` 每次调用 append，
    无容量上限；且被当作下标差值快照使用（`:729`/`:744`，依赖"列表只增不减"）。长期运行属**内存泄漏**。

  **③ 方案选型（受两个实测约束驱动）**
  - 约束：服务器磁盘 **59G/已用33G/仅剩25G**（LangFuse v3 需 ClickHouse，风险高）；
    容器内 `openaipublic.blob.core.windows.net` **DNS 解析失败**（境外出网不可靠，LangSmith 端点无法保证）
  - 推荐**分层引入**：P0 复用现有栈（指标归因+修缺陷+评测门禁+看板）零新增基础设施；
    P1 span 日志 → Loki → Grafana（含跨容器 MCP 客户端侧包裹）；P2 才评估外部追踪后端

  **④ 交付形态**：10 个详细设计（D1–D10，含签名/配置/CLI 契约）、分期计划（P0≈6 人日、P0+P1≈9 人日）、
  10 条可验证验收标准（含"故意让用例失败以证明 CI 会红"）、风险与回滚、**逐条证据索引**。

  **⑤ 同时修正了一处文档滞后**：`docs/tech/.facts/T8-observability.md` 记 `record_llm_call`
  「全仓库无调用方」，实测**已过期**（现由 `llm_factory.py:944` 调用）；
  该 RFC 要求在实施完成后同步 T8 与 `docs/tech/09-OBSERVABILITY.md`。
