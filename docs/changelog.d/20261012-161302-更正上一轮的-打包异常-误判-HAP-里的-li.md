## 2026-10-26（更正：上一轮"打包异常"是**误判**；HAP 里的 `libkn.so` 只是被 strip 过的同源产物）

上一轮我写下"HAP 里的 `libkn.so` 与构建产物不一致（打包异常），使设备侧验证不可信"。
**这条结论是错的**，本轮用哈希把它钉死了，先更正，免得下一位按错方向查。

### 实测（`apps/harmony/spike` 下的全部 `libkn.so`）

| 位置 | sha256 前 16 位 | 大小 |
|---|---|---|
| `knspike/build/bin/ohosArm64/debugShared/libkn.so`（KMP 产物） | `ff745a80e420aa14` | 9,604,120 B |
| `hapshell/entry/libs/arm64-v8a/libkn.so`（被 CMake 当 IMPORTED 用的那份） | `ff745a80e420aa14` | 同 |
| `entry/build/.../intermediates/{cmake,libs}/.../libkn.so` | `ff745a80e420aa14` | 同 |
| `entry/build/.../intermediates/stripped_native_libs/.../libkn.so` | `5b9f3b0420868c97` | 4,695,320 B |
| **HAP 内 `libs/arm64-v8a/libkn.so`** | **`5b9f3b0420868c97`** | **4,695,320 B** |

→ **HAP 里那份 = `stripped_native_libs` 那份**（哈希逐字节相同），而 `stripped` 那份来自
`entry/libs` 那份（同为 `ff745a80…`，只是被 hvigor 的 strip 步骤处理过）。
**打包链路是同源的，没有"陈旧库"问题。**

### 我为什么会误判（方法错误，值得记）
我用 `strings <so> | grep dbChunks` 当判据：**未 strip** 的产物里有、**strip 后**没有（`0`），
于是推断"HAP 里的是旧库"。但 `strings` 找的是**字符串字面量**，而 strip 会去掉符号/调试段；
把"某字符串在 stripped 二进制里搜不到"直接当成"这份产物是旧的"，是**判据不成立**。
正确做法就一句：**比对哈希**（上一轮我其实已经拿到 `stripped == HAP` 的哈希，却没据此推翻自己的结论）。

### 附带修正一条同源建议
上一轮我在 changelog 里要求"下一轮先让 HAP 的 libkn.so 与构建产物可验证地同源、写进 verify_link"。
**这条需求本身仍然值得做**（作为 30 秒的机械守卫：`sha256(HAP 内 libkn.so) == sha256(stripped 中间产物)`），
但它的**理由要改**：不是为了修一个不存在的陈旧库，而是为了把"打包是否同源"变成机械可判。

### 那么 `dbChunks=-1` 到底怎么回事？
不是打包问题。本轮把"诊断字段必须出现"单独做成一条断言
（`rag_diag_fields_present`，**故意让它红**），它红了，说明**设备侧那份响应里确实没有 `dbChunks`**。
下一步最省事的判定：给响应加一个**随构建变化的唯一标记**（例如构建号字符串），
在 ArkTS 侧断言它出现——**标记出现 = 产物是新的**，那时若 `dbChunks` 仍缺失，就说明是 Kotlin 侧
那段代码路径没被执行（而不是产物旧）。这条留作下一轮的第一步，附原始报文一起看
（本次已把 `rawJson` 带进返回值，只是那一轮运行没跑到该断言，未取到）。
