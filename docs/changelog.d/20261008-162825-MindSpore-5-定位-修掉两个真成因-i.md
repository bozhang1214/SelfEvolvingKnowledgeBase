## 2026-09-25（MindSpore `-5` 定位：修掉两个真正成因，错误前进到 `-7`）

- **查实并修掉两个成因**：
  1. 探测函数遗留的"**所有输入必须 int64**"判据 —— 模型新增 float32 掩码输入后该判据在设计上即为假；
  2. **不能再按 dtype 判断类型**：`OH_AI_TensorGetDataType(t) == OH_AI_DATATYPE_NUMBERTYPE_INT64`
     在本绑定下**恒为 false**（诊断码 `-1033` = 3 输入 / 0 个 int64 / 3 个"非 int64"，即全被误判）；
     这也是 owner 最初截图 `-5` 的同一个假警报。
  - 修法：① 删掉 `predictTyped` 中基于该 API 的类型断言（类型由 `Feed` 子类显式表达；元素数仍严格校验）；
    ② **改按「元素数」识别角色**（掩码 `1×512×512=262144` vs token `1×512=512`，相差 512 倍，无歧义）。
- **结果：`-5` → `-7`（`NO_OUTPUT`）**：已越过类型判据、`seqLen` 可取，现卡在 `outputElementNum <= 0`。
- **下一步**：区分"没有输出张量"与"输出元素数为 0"（排查方向不同）。办法：加 `outputProbe()` 编码进返回值，
  或用 hilog。本轮试过一次但**`companion object` 插在类体中间把类截断 → 编译失败**，已回退。
- ⚠️ **我自己的过程错误（记录避免重犯）**：中途用窄 grep 过滤构建输出，**滤掉了
  `Compilation finished with errors`**，导致"修完仍 -5"的结论其实来自**旧包**，白绕一轮。
  **教训：构建/测试输出不要用窄模式 grep，必须先确认"构建成功"这一事实。**
