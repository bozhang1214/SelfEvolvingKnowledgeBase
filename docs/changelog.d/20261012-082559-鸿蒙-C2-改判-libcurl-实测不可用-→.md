## 2026-10-12（鸿蒙 C2 改判：libcurl 实测不可用 → 先用 `@ohos.net.http`；owner 二次确认）

- **背景**：C2 原定"鸿蒙与 Android 共用**同一份 libcurl**"，并明确写了失败出口（HR9：
  "任一探针不通就回头找 owner 松口 `@ohos.net.http`"）。本轮把第一个探针做出来，**出口被触发**：

  ```
  bash scripts/harmony.sh probe 22
  LOAD FAIL libcurl.so / libcurl.z.so / libcurl_shared.z.so / libcurl_ndk.z.so / /system/lib64/libcurl.so
  LOAD FAIL libcrypto.so / libssl.so        ← 连 OpenSSL 也没有
  PROBE1 FAIL libcurl.so 加载不了
  ```

  即"libcurl 在鸿蒙上可用"这个前提**不成立**（sysroot 里连 `usr/include/curl` 都没有，
  链接期也没有可用的 libcurl）。owner 据此**二次确认改判**：鸿蒙侧先用 `@ohos.net.http`。

- **改动（文档口径）**：
  - `docs/多端跨端-鸿蒙端方案.md` §4.5 **C2**：由"✅ 与 Android 共用 libcurl"改为
    "⚠️ 已被实测推翻 → 鸿蒙先用 `@ohos.net.http`，统一 libcurl 作为独立议题排后续"，
    并把**触发证据**（5 个变体 dlopen 全失败、无 OpenSSL、无 curl 头）写进决策行本身；
  - 同文件 **HR9**：标注"已按本行的出口处置"，并记下**三条会骗人的判据**——
    ① `hdc shell test -e` 对**已确认在跑**的 `libmindspore_lite_ndk.so` 也报 MISSING（SELinux）；
    ② host 侧 grep 系统镜像得到 **64 处 `libcurl.so` 字符串命中**，但库并不存在；
    ③ `.z.so`/`_shared` 命名习惯要一起试，否则会漏判。
  - **代价写清楚**：鸿蒙侧传输层是 ArkTS 实现，与 Android 的 libcurl「一份 C 实现」暂时分叉；
    但**共享层 `HttpTransport` 接口与 `SseParser`/`SekbApi` 逻辑不变**——各端传输本来就是端口
    （iOS 用 NSURLSession 同理），所以"逻辑一份"这条主线没有被破坏。

- **验证**：`bash docs/tech/.validation/doc_guard.sh --no-warn` → 7 项全过；
  `scripts/check_edge_facts.py` → 端侧活数字与实测一致。

- **同轮采纳的第二条 owner 决策**：**嵌入失败语义保持"降级为零向量"**（不抛）。
  依据：iOS `OrtBgeEmbedding` 早就这么做，且 `KnowledgeIndex.ingest` 按切片数索引、异常会打断导入；
  共享层 `HostOllamaEmbedding` 已对齐，`KnowledgeIndex.ingest` 另加了"条数不符则补零并报 `zeroFilled`"的防御。
