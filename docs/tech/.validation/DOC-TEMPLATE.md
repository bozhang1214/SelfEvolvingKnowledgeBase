## 3. 写作纪律

1. **证据**：每条结论带代码引用；引代码 ≤8 行，超出概括。
   **引用写法（2026-09-16 起，按抗漂移能力排序）**：
   - 首选 `file::symbol`（如 `backend/app/agents/job/mcp_client.py::get_shared_kernel`）——
     **函数/类名不会因为上面增删行而失效**，这是唯一不会被行号漂移打穿的写法；
   - 次选 `file:line`（如 `backend/app/api/routes/chat.py:260`）——只在「引用的是配置项、
     字典键、常量」这类没有符号可锚的地方用；
   - 纯 `file` 路径（如 `backend/app/core/config.py`）用于「证据在这个文件里」。
   三种写法都由 `check-docs.py` 校验：**行号越界、文件不存在、符号找不到**都会报错。
   > 复核教训：这次逮到的最危险错误不是"行号偏了几十行"，而是
   > `state.py:498-519`、`upload.py:494-1006`——<!-- check-docs:ignore 历史错例 -->
   > 引用了**根本不存在的行**，只读文档永远发现不了。
2. **刻意引用历史错例**（写「当时这里写错了」时）：在该行末尾加
   `<!-- check-docs:ignore -->`，否则校验器会把它当成真引用而误报。
3. **活数字**（会随迭代变的数：测试数、覆盖率、mypy 存量债、端点/工具/指标数、
   死配置数、源数量、角色数…）：**同一事实只留一处权威**，其余文档改为链接或不再重复。
   写它的那行必须带事实标记，供 `check-facts.py` 强制全局一致：
   ```markdown
   | 覆盖率 | **54%**（门禁 40%）<!-- fact:coverage_pct=54 --> |
   ```
   同一个 `fact:NAME` 在多处出现**不同值** → 校验直接失败。
   > 复核教训：覆盖率在 10 写 43%、在 CI 注释写 44%（实测 54%）；指标未埋点数 07 写 4、
   > 09 写 3；死配置数 07 写 49、06 算 29；JWT 有效期三处不同。
   > 这些**不会有任何测试失败**，只会让读文档的人按错的数做事。
4. **推断**：标 `【推断·待验证】`。
5. **as-is / to-be 分离**：现状写正文；改进建议归 `07`/`11`，或文中单列「改进项」小节。
6. **脱敏**：密钥/内网 IP → `<REDACTED>`。
7. **表格优先**：接口/参数/配置用表格。
8. **简体中文**：术语首次出现附英文。
9. **不注水**：每节有信息增量与证据。
10. **术语一致**：与 `08-GLOSSARY.md` 严格一致。

**提交前必跑**：`bash docs/tech/.validation/doc_guard.sh`
（= 链接/引用 + 孤儿 + 新鲜度 + 活数字一致性；已接入 pre-commit 与 CI `docs-guard` job）
