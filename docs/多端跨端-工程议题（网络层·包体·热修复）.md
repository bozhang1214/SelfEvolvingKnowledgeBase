# 多端跨端 · 工程议题（网络层 / 包体与插件化 / 热修复）· v1（待确认）

> **本文回应 owner 的三条补充建议**：① 网络库优先考虑 **libcurl** 统一；
> ② 跨端会增加包体，是否**提前考虑插件化**；③ 是否一起考虑**热修复**。
> 结论先给（§0），依据全部是本机可复现的实测或已存证事实；不确定的地方一律标「待实测」。

## 0. 结论（三条，一句话各）

| # | 议题 | 结论 | 做在哪一步 |
|---|---|---|---|
| 1 | **网络层用 libcurl 统一** | **部分采纳**：Android + 鸿蒙共用一份 libcurl 实现（这两端最缺统一）；**iOS 保留 NSURLSession**（ATS/系统代理/后台/证书链语义，libcurl 拿不到）；JVM 保留 OkHttp。收益是"少写两套、SSE 语义一处"；**代价是要自建 libcurl + TLS 的 3 平台编译链**（本机实测：OHOS/iOS SDK **都没有** curl 与 TLS 开发头） | M4 里定接口与夹具；libcurl 实现放 M5 之后（不阻塞 iOS） |
| 2 | **包体 / 插件化** | **先做"免费瘦身"，再谈插件化**。实测当前 debug APK **102 MB**，其中 **ONNX Runtime 四个 ABI 就占 70 MB**（69%），debug dex 44 MB，PDFBox 传递依赖的 BouncyCastle PQC 属性文件 ~6.7 MB —— **这三项与跨端无关，是现在就漏着的**。跨端本身（KMP 框架）预计只加 **3–5 MB**。插件化在 iOS 上**只能下发资源/模型**（禁止下发可执行代码），所以"插件化"应定义成**资源按需**，M4 就定边界 | 瘦身：**M4 随手做**（半天）；资源按需：M4 定设计；代码插件化：**推迟**（有触发条件） |
| 3 | **热修复** | **分三层，采纳前两层**：L1 策略/配置热修（四端都能用，且我们已经有一半：端侧配置档、升级信号、阈值）+ L2 资源/模型热修（四端都能用）。**L3 代码热修**：Android 自建渠道可评估；**iOS 明确禁止**（App Store 3.2.2）；鸿蒙受限（待验）→ 写进文档，**避免以后对外承诺"热修复"** | L1/L2：M4 出设计、M5 iOS 接入（四端同一套）；L3：只登记，不实现 |

## 1. 议题一：网络层统一到 libcurl？

### 1.1 现状：接口已经统一，只有实现在分叉

`shared` 层已有 `HttpTransport` 接口（三个方法：`postJson` / `get` / `postJsonStream`），
四端只是各写一个实现，且 SSE 的**解析已经在共享层**（`SseParser`），平台侧只负责"发请求 + 逐行回调"：

| 端 | 现状实现 | 代码量 | 说明 |
|---|---|---|---|
| Android | `OkHttpTransport`（`net/HttpTransport.kt` 内） | ~120 行 | 已用；`okhttp3` 在**全工程只有这一处**使用（可直接替换） |
| iOS | 待写（NSURLSession） | ~120 行（预估） | — |
| 鸿蒙 | 待写（`@ohos.net.http` 或 libcurl） | ~150 行（预估） | — |
| Mac | 复用 iOS 的 NSURLSession 实现 | 0 行 | — |
| JVM/桌面 | OkHttp 或 `java.net.http` | ~100 行 | 桌面已搁置 |

**所以"分叉成本"上限约 400 行平台代码**，而"统一成本"是下面这些。

### 1.2 本机实测：libcurl 在各端到底有没有现成的（2026-09-21）

| 端 | 系统是否自带 libcurl | 证据（本机实测） | 后果 |
|---|---|---|---|
| **iOS** | ❌ **没有**（连头文件都没有） | `iPhoneOS.sdk` 下 `find -iname "*curl*"` **为空**；对照 macOS SDK **有** `usr/include/curl/curl.h` | 必须自建（curl 支持 `--with-secure-transport`，可不带 OpenSSL） |
| **鸿蒙** | ❌ 没有 | OHOS sysroot `usr/lib/aarch64-linux-ohos` 只有 `libnet_ssl.so`/`libohcrypto.so` 等；`usr/include` **无 curl / openssl / mbedtls** | 必须自建 libcurl **+ TLS**（自建 mbedTLS 或 OpenSSL） |
| **Android** | ❌ NDK 不提供受支持的 TLS | NDK **30.0.14904198 已装**；NDK 无公开 TLS API | 必须自建 libcurl **+ TLS**（mbedTLS ~0.3–0.5 MB 或 OpenSSL ~1.5–2 MB，每 ABI） |
| macOS | ✅ 系统自带 | 同 SDK 证据 | Mac 端可零成本用 |

### 1.3 三条路线

| 路线 | 做法 | 收益 | 代价 | 判断 |
|---|---|---|---|---|
| **A. 全 libcurl（Android/iOS/鸿蒙/Mac 都走它）** | 共享层一份 C 实现（cinterop），各端只编 libcurl | 平台代码最少；超时/重定向/SSE 行为**完全一致**；不被各端网络栈差异咬 | ① 自建并长期维护 **libcurl + TLS 的 3 个交叉编译链**（OHOS/iOS/Android）；② iOS 上放弃 ATS 自动配置、系统代理/VPN/PAC、后台传输与"蜂窝/WiFi 切换"语义；③ 证书链要走自带 CA bundle（系统证书更新的坑）；④ 每端包体 +1.5–3 MB（TLS 库） | ❌ 不建议全量 |
| **B. 混合（推荐）** | **Android + 鸿蒙** 共用一份 libcurl 实现；**iOS 用 NSURLSession**；JVM 用 OkHttp | 拿到"两端一套 C 实现 + 行为一致"的主要收益；iOS 保留系统网络栈的全部语义（对移动端体验更关键） | 两套实现（C 一份 + NSURLSession 一份）；鸿蒙仍需自建 libcurl+TLS | ✅ **推荐** |
| **C. 维持各端原生（OkHttp / NSURLSession / `@ohos.net.http`）** | 各自最省事 | 零自建成本；开发最快 | 四套实现、行为差异靠契约夹具兜；鸿蒙侧 ArkTS 与 Kotlin 之间的流式回调要额外处理 | ⚠️ 可接受，但 owner 已表达偏好统一 |

### 1.4 推荐的落地方式（路线 B）

1. **M4**：把 `HttpTransport` 提到 `shared`，并建 **SSE 一致性夹具**（分块到达、心跳空行、两个 token 间隔 30s、
   中途断线、408/499/500、gzip 关闭、`Content-Type` 缺失）——**夹具先行**，`FakeTransport` 已能跑通一半；
2. **M5**：iOS 用 NSURLSession 实现并跑夹具（不引入 libcurl）；
3. **M5 之后（不阻塞）**：Android 用 libcurl 替换 OkHttp（`okhttp3` 目前只有一处使用）+
   鸿蒙复用同一份 C 实现 → 这时"统一"真正落地：**两端一套 C 代码**；
4. **验收**：① 四端跑同一组 SSE 夹具全绿；② libcurl 版与 OkHttp 版在同一批请求上**逐字节相同的事件序列**；
   ③ 包体增量实测（Android ≤ +3 MB/ABI）；④ 超时/重试语义与现有约定一致（流式**不重试**，见 `OkHttpTransport` 注释）。

> 若 owner 坚持"全 libcurl"（路线 A）：请接受 §1.3 的 ②③，并追加 **1–2 天 spike**：
> 编出 iOS/鸿蒙/Android 三份 libcurl + TLS，各跑一次真实 HTTPS + SSE，测包体与证书链行为。
> 这条 spike 的结论会决定 iOS 是否真的可行（ATS 与系统代理是硬伤）。

## 2. 议题二：包体与插件化

### 2.1 实测：当前 APK 102 MB 里到底是什么（2026-09-21，debug 包）

`apps/android/app/build/outputs/apk/debug/app-debug.apk` = **101,945,162 B（≈102 MB）**，
解包后 154 MB / 257 个条目：

| 条目 | 大小 | 占比 | 归因 | 能不能去掉 |
|---|---|---|---|---|
| `lib/*/libonnxruntime.so` × 4 ABI | **70.4 MB** | **69%** | `onnxruntime-android:1.20.0` AAR 默认带 4 个 ABI | ✅ ABI split / App Bundle（arm64-only）→ 只留 **17.6 MB** |
| `classes*.dex`（debug，未混淆） | 44.5 + 13.0 + 9.0 + … | ~30% | debug 构建 + 无 R8 | ✅ release + R8 大幅压缩（实测后记数） |
| BouncyCastle PQC 属性（`picnic`/`sike`） | ~**6.7 MB** | ~6% | PDFBox-Android 的传递依赖 | ✅ `packaging.resources.excludes` 排除 |
| Compose / OkHttp / 其它 | 余量 | — | — | 部分可由 R8 收 |

**关键结论**：**现在最该做的包体工作与"跨端"无关**——是 ABI 与 debug 构建的漏。
跨端引入的增量（KMP 框架 + SwiftUI/ArkUI 各自的语言运行时）预计 **3–5 MB（Android）**、
**5–8 MB（iOS，含 Kotlin/Native 运行时）**，量级远小于上面那 70 MB。

### 2.2 建议的优先级（先免费、后付费）

| 优先级 | 动作 | 预期收益 | 成本 | 放哪 |
|---|---|---|---|---|
| **P0** | **ABI split / App Bundle**（只发 arm64-v8a） | APK −53 MB | 半天（`splits` 或 bundle） | **M4 随手做** |
| **P0** | `packaging.resources.excludes` 排除 BouncyCastle PQC 属性 | −6.7 MB | 1 小时 | M4 顺手 |
| **P0** | release 构建开 R8 + 资源压缩 | dex 大幅下降（待实测） | 半天（需要 keep 规则 + 回归） | M4 |
| **P1** | **模型/词表/评测集走"首次启动下载 + sha256 + 空间戳校验"** | 保证将来打进包也不会发生；**iOS 早晚必须这么做** | 1–2 天 | **本期只做一半**：iOS 首版先把 **int8 嵌入模型（23.9 MB）打进包**，先保"功能可用"（离线也能用）；下载通道随 L2 资源热修一起做（非本期重点） |
| **P2** | **代码插件化**（Android dynamic feature / 鸿蒙 HSP） | 只在"功能模块很大且用户只用一部分"时才划算 | 见 §2.3 | **推迟**（触发条件见下） |

### 2.3 插件化：各端"到底能下发什么"（这决定了可行边界）

| 端 | 能下发**资源**（模型/词表/配置/规则） | 能下发**代码** | 机制 | 备注 |
|---|---|---|---|---|
| Android | ✅ | ✅（技术可行） | Play Feature Delivery / 自研 dex 插件 | ⚠️ 本项目主力是**国内渠道**（华为/小米/应用宝），Play Feature Delivery 用不上；自研 dex 插件风险高（Android 9+ 限制、厂商加固冲突） |
| iOS | ✅ | ❌ **明确禁止** | App Store 审核 **3.2.2 / 2.5.2** 禁止下载可执行代码 | 所以 iOS 上"插件化"= **资源按需** |
| 鸿蒙 | ✅ | ⚠️ 待验（HSP/HAR 动态共享包的能力边界要查） | HAP/HSP/HAR 模块化 | spike 里顺带确认一句 |
| Mac | ✅ | ✅（自签名分发） | 应用内更新 | 我们不发布 Mac App Store 的话自由度高 |

**我的建议**：
1. **把"插件化"定义为"资源按需"**（跨端统一、iOS 也能用），M4 就定接口：
   `AssetBundlePort`（清单 + 下载 + sha256 + 版本/空间戳 + 落盘位置 + 断点续传）；
2. **代码级插件化写触发条件**（不是现在）：① release APK 里"非首屏功能代码" > 10 MB；
   ② 且渠道允许动态分发；③ 且有独立的测试/回滚手段。三条同时满足才启动；
3. **包体预算进 CI**：M4 起在 CI 里记录 release APK/IPA 体积（**回归看趋势，不设死线**），
   避免"每加一个端涨一点"没人发现。

## 3. 议题三：热修复

### 3.1 分三层看，四端可行性完全不同

| 层 | 内容 | Android | iOS | 鸿蒙 | Mac | 我们的现状 |
|---|---|---|---|---|---|---|
| **L1 策略/配置** | 阈值、升级信号开关、前缀守卫长度、提示词/模板、工具白名单、模型档位、路由偏好 | ✅ | ✅ | ✅ | ✅ | **已有雏形**：端侧配置档、`escalate_on`、`stream_guard_chars`、`EdgeConfig` |
| **L2 资源/模型** | 嵌入模型、词表、规则 JSON、评测集 | ✅ | ✅ | ✅ | ✅ | 模型已是"外部文件"（不进包） |
| **L3 代码** | 修 bug / 改逻辑 | ⚠️ 自建渠道可评估（Tinker 类，高风险） | ❌ **禁止** | ⚠️ 待验 | ✅（自签名分发） | 无 |

### 3.2 L1（策略/配置）本期**正常实现**——口径与验收

> **owner 2026-09-21 定**：**L1 正常实现**；其中**「设备适配」类策略（机型/SoC/内存档位映射、
> 按 ROM 的差异开关）只预留字段，本期不实现**。

**L1 本期实现范围**（通用策略，四端同一套）：

| 可变项（白名单） | 说明 | 为什么需要热修 |
|---|---|---|
| `streamGuardChars` | 流式前缀守卫长度（默认 60） | 端侧延迟/退化检测的取舍，实测后可能要调 |
| `escalateOn` | 6 类升级信号开关 | 过敏→多走云（贵/慢）；过钝→端侧答烂 |
| `maxInputTokens` / `maxOutputTokens` / `maxTtftMs` | 端侧硬预算 | 随机型/模型变化 |
| `preferPlane` | 路由偏好（edge/cloud） | 灰度期临时切云 |
| `modelTier`（short/default/quality → 模型名） | 端侧档位映射 | 换模型不发版 |
| `promptPacks`（提示词/模板 ID → 文本） | 意图分类/工具调用模板 | 改错别字与措辞最高频 |
| `toolWhitelist` | 允许暴露给模型的工具集 | 出问题可一键收窄 |
| `retrievalMinScore` | 检索阈值 | ⚠️ **必须与空间戳绑定**（见下） |

**服务端：✅ 已实现（2026-09-21）**——`backend/app/core/edge_policy.py`（生成/签名/校验/灰度/白名单）+ `GET /api/v1/edge/policy`（设备 token 鉴权，返回体**服务端自校验**后再下发）；`backend/tests/unit/test_edge_policy.py` **19 条**（未知键整包拒绝、越界值、签名不符、改空间戳破坏签名、灰度确定性与分桶比例、端点自校验）。

**端侧：✅ 已实现（2026-09-21）**——`apps/shared/.../policy/EdgePolicy.kt`：验签（HMAC-SHA256，规范化 JSON 与服务端逐字节一致，有**跨语言向量测试**）→ 有效期 → 空间戳 → 白名单（未知键整包拒绝；`deviceProfiles` 预留但**不读取**）→ 灰度 → 合并进 `EdgeRuntimeConfig`。**如实区分「已应用」与「仅识别」**：`retrievalMinScore` 不在 `EdgeRuntimeConfig` 里（属 Retriever 构造参数），放进 `ignoredKeys` 并提供专用读取口；`promptPacks` 本期后置（owner 已确认）。仍待做：拉取时机（启动 + 每 6h + 自检手动）、双槽持久化（`PolicyStore` 端口 + 各端实现）、审计落盘。

契约（`GET /edge/policy` 返回体）：
- 返回 `{ version, issuedAt, expiresAt, embeddingSpace, rollout: {...}, policy: {…}, signature }`；
- **签名**：用服务端密钥对 `policy+version+embeddingSpace` 签名，端侧校验失败即**整包丢弃**（用旧版）；
- **灰度**：`rollout = { percent, salt }`，端侧按 `hash(deviceId + salt) % 100 < percent` 决定是否应用；
- **回滚**：服务端发新版本号即回滚；端侧保留**上一份可用策略**（双槽），失败自动回退；
- **审计**：端侧每次应用写一条本地日志（`policyId / from → to / 应用或拒绝的原因`），与路由日志同源。

**端侧（共享层，四端同一份）**：
- 启动时拉一次 + 每 N 小时刷新（N 也属于白名单）；拉不到就用缓存；首装内置一份默认（`shared/constants`）；
- **应用前三道校验**：① 签名；② `embeddingSpace` 与本地一致（**不一致 → 拒绝应用**，留痕
  `policy_rejected:space_mismatch`）；③ 键必须在白名单内（**多一个键也拒绝整包**，不放行"未知键"）。
- **硬约束（写死，别改）**：策略**不得**包含"设备型号/ROM/SoC → 行为"的差异化规则——那属于
  §3.3 的预留子集，本期不实现。

**验收（可证伪）**：① 单测：非法签名 / 过期 / 空间不符 / 含白名单外键 → **全部被拒且留痕**；
② 灰度：同版本按设备分桶，能一键回滚；③ 端到端：改一次阈值 → **不发版、不重启**即生效（日志可证）；
④ 后端全量测试不回归（基线 **966**）。

### 3.3 预留（本期**不实现**）：设备适配类策略

为什么要留：Android 机型/ROM 差异大（内存档位、热降频、后台被杀、厂商省电策略），
将来很可能需要"按设备档位选模型/调预算"。**但本期不做**——因为：
① 我们没有真机矩阵，现在写规则全是猜；② 真机到货后要按实测数据定档，规则会全改。

**预留方式（只是占位，代码里不读取）**：策略包 schema 里保留一个**空对象**字段，
并写明它将来承载什么、以及"读取方尚未实现"：

```jsonc
{
  "version": 7,
  "embeddingSpace": "BAAI/bge-small-zh-v1.5-int8@512",
  "rollout": { "percent": 100, "salt": "2026w39" },
  "policy": {
    "streamGuardChars": 60,
    "escalateOn": ["json_invalid", "empty", "degenerate", "timeout", "low_confidence", "tool_hallucination"],
    "maxInputTokens": 2048,
    "maxOutputTokens": 512,
    "modelTier": { "short": "qwen3.5-2b", "default": "qwen3.5-4b" },
    "toolWhitelist": ["kb_search", "device_time"],
    "retrievalMinScore": 0.5
  },
  // ⬇️ 预留：本期不实现，端侧不得读取（键不在白名单 = 整包拒绝）
  "deviceProfiles": {}
}
```

> 落地时把 `deviceProfiles` 放进"已登记但未启用"的清单里，并在端侧白名单校验时**明确跳过**它——
> 这样将来启用它时，改动点是**收敛的**（一处 schema + 一处读取），不是散在各端判断里。

### 3.4 L2（资源/模型）——本期**只做一半**

L2 = 嵌入模型、词表、规则 JSON、评测集的**按需更新**。本期：
- iOS 首版**把 int8 嵌入模型（23.9 MB）打进包**，先保"四端功能可用"（离线也能用）；
- **下载通道（清单 + sha256 + 空间戳校验 + 断点续传）随 `AssetBundlePort` 一起后置**——
  它与 §2 的包体议题是同一件事，等包体真成问题时再做。

### 3.5 L3（代码热修）的结论

| 端 | 结论 | 理由 |
|---|---|---|
| iOS | **不做，且写进文档** | App Store 禁止下发可执行代码；承诺"iOS 可热修"是不成立的 |
| 鸿蒙 | 待验，默认**不做** | 应用市场审核限制；HSP 是"共享包"不是"热补丁" |
| Android | **登记为可选**（自建渠道） | 国内渠道常见（Tinker 类），但风险高：dex 加载、厂商加固、崩溃不可预期；只有在"发版周期很长且线上事故频发"时才值得 |
| Mac | 可做（应用内更新） | 非商店分发 |

## 4. 汇总：三条建议分别落在哪一步

| 事项 | M4（共享层） | M5（iOS） | 之后 |
|---|---|---|---|
| **网络层** | 定接口 + **SSE 一致性夹具**（JVM 上先跑通） | NSURLSession 实现 + 跑夹具 | Android/鸿蒙切 **libcurl 一份 C 实现**（含 TLS 自建） |
| **包体** | **ABI split + 资源排除 + release R8**（半天~1 天）；CI 记体积 | iOS 侧内嵌 int8 模型（23.9 MB）保功能可用 | 代码插件化（三条触发条件全中才做）；模型改按需下载 |
| **热修复** | **L1 正常实现**（`GET /edge/policy` + 缓存/签名/灰度/回滚/审计/白名单/空间戳绑定，见 §3.2，排期 **M4.5**）；**设备适配子集只预留**（§3.3） | 沿用同一份策略客户端 | L2 资源下载通道（`AssetBundlePort`）后置；L3 只在 Android 自建渠道登记 |

> **本期一句话**：**先把四端功能跑通**（[`RFC-多端跨端方案.md`](RFC-多端跨端方案.md) §2.3 清单），
> 网络层按 S1 落地、包体做 P0 免费瘦身、**L1 策略热修正常实现（设备适配子集只预留）**。
