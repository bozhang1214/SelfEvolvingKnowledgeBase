## 1. 目标与背景

### 1.1 要解决的断点（as-is）
当前 SEKB 开发-运维闭环在这些环节断裂：
1. 告警只「通知」不闭环——没有 诊断→提案→授权→执行→验证 的链路；
2. 发布依赖人工 bundle+scp，无 staging/灰度/健康门禁/自动回滚的系统化支撑；
3. 线上指标/反馈没有回流成迭代输入；
4. GitHub 连接不稳定，remote 还带明文 PAT（安全红线）。

### 1.2 目标形态（to-be）
把闭环组织成一个 **agentic 平台**：感知 → 提案（agent 只读）→ 授权（HIL 人工）→ 执行 → 回流，六层闭环见 §2。

---

## 2. 总体架构（六层闭环）

```mermaid
flowchart LR
    subgraph 感知层
      A1[告警/指标] --> A2[用户反馈/客服]
      A2 --> A3[日志/成本]
    end
    subgraph 提案层 agent只读
      B1[根因分析] --> B2[修复/优化提案+PR]
    end
    subgraph 授权层 HIL
      C1[人工 Review/确认闸门 G1-G6]
    end
    subgraph 执行层
      D1[staging 验证] --> D2[灰度发布+健康门禁] --> D3[自动回滚兜底]
    end
    subgraph 回流层
      E1[发布后监控对比] --> E2[复盘→BACKLOG]
    end
    感知层 --> 提案层 --> 授权层 --> 执行层 --> 回流层 --> 感知层
```

## 3. Human-In-Loop 闸门（固定检查点）

| 闸门 | 内容 | 可自动？ | 备注 |
|------|------|---------|------|
| **G1** | 生产部署前人工确认 | 否 | 保守策略核心 |
| **G2** | 版本切换（快照式发布）人工确认 | 否 | 人定切换时机 |
| **G3** | 代码变更进生产前 PR review 确认 | 否 | agent 只出 PR |
| **G4** | 生产数据/凭据/破坏性操作确认 | 否 | 永不自动（单人 HIL 见 D-16） |
| **G5** | 自动回滚阈值/白名单由人批准 | 触发可自动；策略人定 | 回滚目标=上一稳定版 |
| **G6** | 降级/熔断/预算策略变更确认 | 否 | — |
| 通用 | agent 动作全程审计日志 | — | 谁/何时/改什么/关联提案号 |

## 4. Git 平台与流水线（M1 载体，按 D-02）

### 4.1 为什么 Gitea + 自建流水线
- 国内访问稳定；凭据不出本机；CI/CD 环节都落在自己的服务器上，闭环最短；
- 与现状 bundle+scp 兼容升级（把「手工步骤」固化为脚本/流水线步骤）；
- GitHub 降级为只读归档镜像（若需保留远端副本）。

### 4.2 目标拓扑（待细化）
```mermaid
flowchart LR
    G[Gitea :3000 内网/Tailscale]
    R[自建 runner/脚本流水线]
    S[staging compose]
    P[prod compose]
    G -->|webhook/poll| R
    R -->|门禁:测试/静态/冒烟| S
    R -->|HIL 确认后| P
    P -->|回滚预案| P
```

### 4.3 待讨论细节
- Gitea 部署：容器（docker compose）挂什么卷、HTTPS 入口（见 §6 域名方案）；
- 流水线载体：Gitea Actions（内置，需启用）vs 自建 runner 脚本（bash 流水线，贴近现状）——倾向自建 runner 脚本 + 门禁函数库；
- 触发：PR/推送 hook 自动跑 staging；prod 发布由「HIL 确认」步骤触发。

## 6. staging/平台入口域名方案（已确认 A+C）

背景：云服务器域名 `bos-studio.tech`，当前 nginx 已托管 `/sekb/` 应用与 HTTPS。staging 与 Gitea 需独立入口。候选：

### 方案 A：子域名 + 独立 nginx server（推荐）
- `staging.bos-studio.tech` → staging 应用；
- `git.bos-studio.tech` → Gitea；
- 需在 DNS 添加两条 A 记录指向同一服务器 IP；
- nginx 增加两个 server_name 段（各自 TLS，可用同一证书通配或分别签）。
- 优点：隔离清晰、无路径冲突、SPA base 简单；缺点：需 DNS 与证书操作。

### 方案 B：子路径（`bos-studio.tech/staging/`、`/git/`）
- 不加 DNS；nginx location 分流。
- 优点：零 DNS 改动；缺点：SPA/vite base 需带前缀、易与现 /sekb 混、隔离弱。

### 方案 C：仅内网 + Tailscale（最安全）
- staging 与 Gitea 只经 Tailscale 访问（不公网暴露），手机/办公网经 Tailscale；
- 优点：安全第一，符合 M0；缺点：外出无 Tailscale 时不可访问。
- 可与 A 结合：staging 走 Tailscale，正式流水线由服务器内部触发即可。

**已确认：A+C（子域名 + Tailscale 兜底）**——git.bos-studio.tech → Gitea、staging.bos-studio.tech → staging；正式流水线全内网；可先 C 后 A（先 Tailscale 内网，公网子域名后置）。

**关于"是否要新域名"的澄清**：
- 子域名属于已有域名 `bos-studio.tech`，**无需新申请**；
- 实际成本 = ① 域名服务商 DNS 加 2 条 A 记录指向服务器 IP；② 证书扩 SAN（certbot 同命令加 `-d`）或签通配 `*.bos-studio.tech`（DNS challenge）；
- 也可先纯 C（Tailscale 自带 TLS，零 DNS/证书），公网子域名后置。

## 7. M4 BugFix 半自动循环（首批，按 D-06）

### 7.1 一条 BugFix 的完整旅程（按 D-12 蓝绿/快照式）
```mermaid
flowchart LR
    S[信号:告警/巡检] --> C1[agent 只读诊断]
    C1 --> R1[根因假设+影响面+复现建议+处置类型]
    R1 -->|Owner确认根因| P[agent 出修复提案:改码+补测]
    P --> CI[CI:ruff/mypy/单测/eval门禁]
    CI -->|绿| D[部署 staging]
    D -->|冒烟过| R2[上线请求+回滚预案]
    R2 -->|G3 PR review + G1确认| REL[停服快照→起新tag容器→健康门禁]
    REL -->|过| FULL[确认切换=新版本上线]
    REL -->|败| RB[回退上一稳定tag(必要时恢复快照)]
    FULL/RB --> V[验证+指标对比] --> W[复盘→写回 docs+关闭 Issue]
```

> 说明：D-12 下不做并行灰度；「发布」= 快照 + 起不可变 tag 新容器 + 健康门禁 + 人确认切换；「回滚」= 回退 tag + 必要时恢复快照。

### 7.2 首批 runbook（按 D-06/4 建议）
| # | 故障 | 诊断要点 | 处置 |
|---|------|---------|------|
| R-01 | 告警阈值误报/疲劳 | 指标口径缺陷（daily_cost 只增、groundedness 只留最近、死指标） | 修口径/埋点，HIL 后上 |
| R-02 | 首 token 慢 | planner reasoner 时长、RAG 冷启动、TTFT | 优化/降级/缓存（涉 ADR） |
| R-03 | ChromaDB 段损坏/检索空 | 备份、原始文件、重嵌入脚本 | **严格人工** 停服→备份→重建 |
| R-04 | embedding 冷加载慢 | HF 缓存、etag | 预热/离线缓存 |

### 7.3 运行方式（按 D-11 混合 + D-17）
- 内置「感知/诊断/提案 Agent」：事件驱动（告警/webhook）与定期巡检触发，只读诊断、出 PR、汇报（标状态，无需确认）；
- 执行：staging 可自动；prod 部署/切换/回滚/数据/凭据一律 HIL（G1-G6）；
- 外部助手：复杂问题深度协作、开发期与 Owner 交互；
- 提案状态机落 Gitea Issue（D-15）：proposed→diagnosed→pr_ready→approved→staging_ok→deploy_approved→released→verified→closed（含 rejected 分支）。

## 8. 自迭代范围与问题分流（按 D-17）

### 8.1 触发范围收紧（核心约束）
| 来源 | 是否自动自迭代 | 条件 |
|------|--------------|------|
| **线上告警** | 是 | 仅「影响较大」的告警（critical 级 + 持续/高频 warning，阈值见 8.2） |
| **定期巡检发现** | 是 | 仅「影响较大」的问题（指标劣化超阈值、死配置引起的事故隐患等） |
| **用户反馈** | **否（暂）** | 先人工筛选确认；待有一套合理筛选标准后，再放开自动迭代 |

- **所有问题一律汇报给 Owner，并标注状态**（如「待处理/诊断中/提案就绪/待确认/已修复/已忽略+原因」）；**汇报本身无需 Owner 确认**。
- 执行层仍遵守 G1-G6 HIL 闸门（即：自动的是「感知+诊断+提案+汇报」，生产执行/发布仍需人工确认）。

### 8.2 「影响较大」的判定口径（建议，待细化）
- 告警：critical 一律纳入；warning 需「持续 >2 个评估周期 或 24h 内复发 ≥3 次」。
- 巡检：错误率 P95>15s、P99>60s、成本日超预算 80%、磁盘/向量库增长异常、文档过期 >90 天等命中即纳入。
- 明确排除：一次性瞬时抖动、未达阈值的 noise、仅影响 0 次请求的死路径。

### 8.3 问题三分类（避免「都改代码」）
| 类型 | 例 | 归宿 |
|------|-----|------|
| 代码缺陷 | 接口 500、并发丢数据 | M4 BugFix 闭环 |
| 知识缺失 | 用户常问某问题、锚定度低 | 知识库入库 / 补文档，不改码 |
| 运营/配置 | 阈值误报、采集源失效 | 改配置 / runbook，不改码 |

- Agent 诊断时须显式输出「处置类型建议」，供 Owner 分流。

## 9. 安全红线（写入规约）

1. 生产写操作默认人工（G1-G6 之外一律人工）；
2. 只读诊断 agent 不持有写凭据；Agent 有独立成本预算帽（D-13）；
3. staging 先于 prod；prod 发布前自动快照（D-12）；
4. 回滚目标=上一稳定 tag；数据类变更回滚走人工恢复；
5. agent 动作全程审计；所有问题汇报并标状态（D-17）；
6. 敏感操作（凭据/数据）永不自动；单人 HIL 高危操作加冷却期+影响预览（D-16）；
7. 新模块先在 staging 全量测试+冒烟；
8. eval 门禁阻断，提案重试达上限即停并升级给人（D-14）。

## 10. 风险与开放问题（待讨论）

| 项 | 问题 | 倾向 |
|----|------|------|
| O-01 | Gitea 与自建流水线的运维负担 vs 收益 | 可接受（个人单机） |
