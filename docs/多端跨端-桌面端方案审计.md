## 0. 审计结论（一屏）

**对 owner 原始问题的直接回答：桌面的"端侧"值得做，但价值集中在一件事上——算力宿主；而不是"多一个客户端"。**

| # | 结论 | 我的判断 | 与原方案的差异 |
|---|---|---|---|
| C1 | **headless 边缘宿主：做**，但必须先定义清楚是"给谁供算力" | ✅ 做（拓扑 B 优先） | 原估 **2–3 人日** → 修正为 **4.5–6.5 人日**（差价在：鉴权默认、资源上限、Windows 服务化、卸载） |
| C2 | **桌面 GUI：后置**，且在拿到 Windows/Linux 验证能力之前**不开工**；若总体 UI 选原生 → 桌面**不做 GUI** | ⏸️ 后置到 M4 共享层之后 | 原为"建议做（5–7 天）" → 加两条**前置条件**（M4 完成 + 有目标 OS 验证手段），并给出"选原生则不做"的分支 |
| C3 | **过渡形态：宿主 + 浏览器入口**（不做 GUI 也能交付） | ✅ 作为阶段 A 交付物 | 原方案没写这条；这是"桌面经验不足"约束下的关键降价手段 |
| C4 | **一个必须先修的定义漏洞**：`DEVICE_ONLY` 现在的语义是"端侧"，一旦"端侧"可以是**局域网里的另一台机器**，隐私硬边界就被绕开了 | 🔴 必须在写宿主之前改契约 | 原方案未提及（见 §2.6 F-1） |

**三句话结论**：

1. **桌面宿主的真实用户是"手机端"和"桌面自用"，不是"桌面用户"**——它不是第五个客户端，而是给已有端加一块算力；
2. **CMP GUI 的成本被低估的地方不在写 UI，而在"打包与验收"**：官方文档明写**不支持交叉编译**，`.msi` 只能在 Windows 上打、`.deb` 只能在 Linux 上打，我们本机是 macOS；
3. **AI 之外的最大风险是"这不是我们的机器"**：桌面是用户的工作机，装一个常驻进程 + 常驻显存如果不设资源上限，第一次用户体验就是"电脑变卡了"。

## 1. 口径确认：桌面端的"端侧"到底指什么

### 1.1 目标平台（我按这个口径审计，若要改请说）

| 项 | 纳入 | 说明 |
|---|---|---|
| Windows | **10 22H2 / 11，x64** | Ollama 官方要求 Win10 22H2+（外部事实，见 §8 E-D1） |
| Ubuntu | **22.04 / 24.04 LTS，x64** | 只承诺 LTS；非 LTS 与 ARM 桌面"能跑不保证" |
| Windows ARM64 | ⚠️ 仅"能跑不保证" | 本机是 Apple Silicon，本地 VM 只能验 ARM；与用户实际（多为 x64）不一致 → 见 §4.3 |
| macOS | ✅ 但**只作为开发机** | 本机唯一能跑的目标；不单列交付 |
| WSL2 里的 Ubuntu | ❌ 不算独立端 | 是 Windows 上的一个进程环境，别当第三个平台维护 |

### 1.2 "端侧"在桌面上的四个具体含义（可验证的口径）

| 含义 | 具体是什么 | 与手机端的差异 |
|---|---|---|
| **算力宿主** | 一个常驻的 OpenAI 兼容端点（`http://<host>:11434/v1`），跑 2B/4B/9B 档 | 手机只能跑小模型或调宿主；桌面可以跑 9B+，且能当别人的"边缘云" |
| **文件主场** | PDF/Word/Excel 批量导入与索引、目录监听 | 手机受 SAF 选择器限制（M3 已踩坑），桌面本来就是文档主场 |
| **隐私边界** | 桌面**同时**是"端"和"宿主"：它的本机文件算不算 `DEVICE_ONLY`？它代手机推理时能不能落盘？ | 语义与手机**不同**，必须显式定义（§2.6 F-1） |
| **凭证托管** | 桌面 GUI 若做完整端，会持有云端用户 token（与手机同级） | 桌面被多人共用/被远控的概率远高于手机 |

### 1.3 明确不在范围内

- ❌ **不做第二个服务端**（Linux 服务器版）：云端已有 REST/SSE，重复实现无收益（沿用 `docs/RFC-多端跨端方案.md` §2.2）；
- ❌ **不做 Windows 原生 UI**（WinUI3/.NET）：第三套 UI，一人维护不动；
- ❌ **不承诺桌面端侧嵌入模型**：嵌入在手机端已 19ms（int8），桌面宿主首版**只提供 LLM chat completions**，不提供 embeddings（少一个空间戳一致性风险面）；
- ❌ **不做桌面车机/服务器变体**：等鸿蒙（OHOS 系）打通后另议。

## 2. headless 边缘宿主设计（审计主体）

### 2.1 先纠正一个混淆：三种拓扑，原方案把它们混成了一件

| 拓扑 | 谁在跑 | 路由决策在哪 | 现状 | 审计意见 |
|---|---|---|---|---|
| **A 本机自用** | 桌面跑 SEKB 后端 + 本机 Ollama | 服务端 `plane_router.py` | **已实测**（M0/M1，Mac） | 已完成，只需脚本化 |
| **B 给手机供算力** | 桌面只跑推理宿主；手机 `edgeBaseUrl` 指向它 | **手机端**（`apps/android/app/src/main/kotlin/com/sekb/ondevice/route/PlaneRouter.kt`） | **不存在** | ✅ 本次审计的重点 |
| **C 桌面完整端** | 桌面跑后端 + 推理 + GUI | 服务端 + 桌面客户端 | 不存在 | ⏸️ 后置（依赖 CMP） |

> **审计意见（关键）**：`docs/RFC-多端跨端方案.md` §4 D3 的 ① 写的是"起 Ollama + **复用 M0 的端云 profile**"。
> 但 M0 的 profile 里 `planes.edge.base_url` 是 **127.0.0.1**（见 `backend/config.edge-cloud.yaml`，由 `scripts/make_local_profile.py` 生成）——
> 对桌面**自己**够用，**对手机毫无用处**（手机连的是 `BuildConfig.DEFAULT_EDGE_BASE_URL`，见 `apps/android/app/build.gradle.kts`）。
> 拓扑 A 的产物 ≠ 拓扑 B 的交付物，这是原估算 2–3 天低估的第一个原因。

### 2.2 它到底是什么进程/服务：**Ollama 还是 llama.cpp server**

| 维度 | Ollama | llama.cpp `llama-server` | 审计意见 |
|---|---|---|---|
| 模型管理 | `ollama create` 导 GGUF、`ollama ps` 看占用、`keep_alive` | 手工管 GGUF 路径与参数 | **Ollama 胜**（`scripts/edge_m0_setup.sh` 已在用 `ollama create`） |
| 鉴权 | ❌ 无 API key（OpenAI 兼容端点默认裸奔） | ✅ 有 `--api-key`（外部事实 E-D4，待验） | llama.cpp 胜；首版用网络隔离替代（§2.5） |
| 可复现性 | ⚠️ Windows/macOS **自动更新**（E-D1）→ 用户机器上行为会悄悄变 | 固定二进制，不自动变 | llama.cpp 胜；或用"固定版本 + 显式升级"约束 Ollama |
| 跨平台安装 | ✅ 官方安装包（Win/Ubuntu），Ubuntu 装 systemd 服务 | 预编译包需选后端（CUDA/Vulkan/ROCm/CPU） | Ollama 胜（首版快） |
| 控制粒度 | 中（`OLLAMA_*` 环境变量） | 高（`-ngl`、`--ctx-size`、`--parallel`、`--no-mmap`） | 需要精细控制时切 llama.cpp |

**结论**：**首版用 Ollama**（M0/M1 的全部实测数字都建立在它上面，沿用才可复现），
但宿主脚本必须做成**运行时可选**（`--runtime ollama|llamacpp`），且**把"要 token"作为切换 llama.cpp 的触发器**——
这样"要不要鉴权"从一个架构争论变成一个开关。

### 2.3 与其他两端的关系（拓扑 B 的数据流）

```
手机 App（Android）                              桌面宿主（Win/Ubuntu）
┌──────────────────────────┐                  ┌───────────────────────────┐
│ ChatOrchestrator         │                  │  ollama serve             │
│  └ PlaneRouter（决策）    │  OpenAI 兼容 SSE │   ├ 127.0.0.1:11434 (默认) │
│      ├ edge → 宿主 ───────┼─────────────────▶│   └ 0.0.0.0:11434（--lan） │
│      └ cloud → SEKB 云端  │                  │  sekb-edge-host（薄网关）  │
│ EdgeRouteStore → 上报 ────┼──▶ SEKB 云端 ◀───┼── 心跳/能力上报（可选）    │
└──────────────────────────┘  /api/v1/edge/   └───────────────────────────┘
                                 route-events
```

- **宿主不决策**：它只提供推理；决策仍在手机端（`PlaneRouter`）与服务端（`plane_router.py`）。
  这是对的——把决策放进宿主会让"三端语义一致"变成四端；
- **但宿主必须能被发现**：手机端得知道"这个宿主有哪些模型、多大上下文、能不能关思考"。
  现在没有这个端点 → 需要新增宿主能力端点（**/sekb/capabilities**，计划），并纳入契约夹具；
- **上报链路复用现成的**：`POST /api/v1/edge/route-events`（设备 token）、`GET /api/v1/edge/routes/stats`（见 `docs/ops/16-端云协同协议.md` §4/§5），
  不需要新协议；但需要**加一个 `host` 维度**，否则"手机端侧完成率"会和"桌面宿主完成率"混成一张表（§6 R-10）。

### 2.4 配置面（要落成什么）

| 配置项 | 现状 | 宿主版要变成 | 证据 |
|---|---|---|---|
| 双平面 profile | ✅ `backend/config.edge-cloud.yaml`（生成物，`scripts/make_local_profile.py` + `--check`） | 增加"edge base_url 可指向远端宿主"的档 | `scripts/make_local_profile.py` |
| 档位映射 | ✅ short=2b / default=4b / quality=9b | 宿主侧声明"我装了哪几档"，手机端按声明选档 | 同上 |
| 输入/输出/首字预算 | 服务端 300/2048/800ms（profile）；手机端 512/2048/800ms（`PlaneRouter.kt`） | **两边不一致**，跨端前必须统一到契约常量 | `apps/android/app/src/main/kotlin/com/sekb/ondevice/route/PlaneRouter.kt` |
| 关思考 | ✅ `disable_thinking: true`（实测 25×） | 宿主侧默认保持；**不能**依赖手机端记得传 | `scripts/make_local_profile.py` |
| 流式前缀守卫 | ✅ 60 字符（`stream_guard_chars`） | 不变（在手机端执行） | `docs/ops/16-端云协同协议.md` §6 |

| 凭证 | ✅ 设备 token（`POST /api/v1/device/enroll`）；BYOK 仅 MCP 端点有（`X-JobCopilot-Api-Key`） | 宿主首版**不持云 key**（只做本地推理）；若要代付，另议 | `docs/ops/15-MCP-ENDPOINT.md`、`docs/ops/16-端云协同协议.md` §2 |
| 宿主鉴权 | ❌ 不存在 | ⚠️ 三选一（§2.5） | — |
| 资源上限 | ❌ 不存在 | 必做（§2.7） | — |

### 2.5 鉴权与现实约束（我认为这是最容易被做错的一处）

**事实**：Ollama 的 OpenAI 兼容端点**没有 API key 机制**；一旦 `OLLAMA_HOST=0.0.0.0:11434`（外部事实 E-D2，待本地验证），
同一局域网内任何人可以：白嫖你的 GPU、拉取你的模型列表、读取模型输出。这在"桌面宿主"场景是**默认危险**，不是理论风险。

| 方案 | 做法 | 成本 | 审计意见 |
|---|---|---|---|
| **① 网络隔离（推荐首版）** | 默认只绑 127.0.0.1；显式 `--lan` 时才绑 `0.0.0.0`，且**同时**要求：Tailscale 在线 + 只允许 `100.64.0.0/10`（用防火墙/`New-NetFirewallRule`，E-D10） | 0.5 人日 | ✅ 首版 |
| ② 切 llama.cpp `--api-key` | 换运行时，带 token | 1–1.5 人日 | 备选（"必须 token"时启用） |
| ③ 薄网关(token) | 宿主前面加一层极薄代理（反代 + static token + 资源上限 + 模型白名单） | 1.5–2 人日 | 与 §2.7 资源上限合并做时更划算 |
| ④ Tailscale Serve | 用 `tailscale serve` 把本机端口以 HTTPS 暴露到 tailnet（E-D9） | 0.5 人日 | ✅ 与 ① 组合 |

**硬性默认值（要写成脚本里的断言，而不是文档里的建议）**：
未开 `--lan` → 绑 127.0.0.1；开了 `--lan` 但没检测到 tailnet 且没写 `--i-know` → **拒绝启动并打印两种正确做法**。
理由：文档里的安全建议一定会被跳过，能拒绝启动的默认值不会。

### 2.6 T-1 拓扑下的隐私边界（F-1：必须先修的定义漏洞）

现在的硬边界（M1 实现）：`DEVICE_ONLY` 数据**永不升云**，`escalation_allowed=false`，失败留痕 `escalation_blocked:device_only`。
**但它的隐含前提是"端侧 = 本机"。** 一旦手机把"端侧"当成桌面宿主，手机上标记 `DEVICE_ONLY` 的内容就会走局域网到另一台机器——
这台机器**同样不是云，但也不是本设备**。

| 问题 | 现状 | 必须改成 |
|---|---|---|
| `DEVICE_ONLY` 允许去哪 | 隐式 = "端侧平面" | 显式 = "**本设备上的本地运行时**"（on-device ONNX / 本地 llama.cpp），**排除远端宿主** |
| 宿主收到 `DEVICE_ONLY` 请求 | 无定义 | 契约里定义为**非法请求**（拒绝 + 留痕），而不是"能跑就跑" |
| 宿主日志 | 无定义 | 代理手机请求时**不得落盘 prompt 正文**（只落 token 数/耗时/模型名） |
| 桌面本机文件 | 无定义 | 建议默认 `NORMAL`（可上云），只有显式标记才 `DEVICE_ONLY`；**这一条要 owner 拍板**（§7 Q7） |

这不是"加个测试"能解决的，是**契约要先改**：`apps/contract/` 的隐私用例（`docs/RFC-多端跨端方案.md` §6 计划新增）
里加一组"跨机器 DEVICE_ONLY 必须被拒"的夹具，两侧（手机端 + 宿主）各跑一遍。**建议：这条排在宿主功能之前做。**

### 2.7 运行时事实：后端矩阵与门槛（Windows / Ubuntu）

| 平台 | 官方路径 | 坑（外部事实，全部标「待本地验证」） | 审计意见 |
|---|---|---|---|
| Windows + NVIDIA | Ollama 原生（含 CUDA） | 驱动要求 NVIDIA **551.61+**（E-D1）；服务会话（session 0）下 GPU 是否可用**必须实测** | ✅ 主推 |
| Windows + AMD | ROCm v7/HIP7 驱动栈 **或** Vulkan | RDNA2 / RX 6000 系（含 6800 级）在当前驱动上可能没有 ROCm v7 → **Vulkan 是官方推荐兜底**；混合 iGPU+dGPU 需 `GGML_VK_VISIBLE_DEVICES` 指定独显 | ⚠️ 需实机验，别承诺 |
| Windows CPU | 有 | 慢（内存带宽受限，见下表） | 兜底可用 |
| Ubuntu + NVIDIA | Ollama 官方 tar/install.sh（含 CUDA） | install.sh 需 sudo 且装**系统级** systemd 服务（E-D3，待验）→ 与"用户级安装"路线冲突 | ✅ 主推 |
| Ubuntu + AMD | ROCm 需额外包；ROCm 按 GPU 型号 + 发行版受限（E-D8） | 老卡/集显基本没戏 | ⚠️ 需实机验 |
| Ubuntu + Intel/AMD 集显 | Vulkan（llama.cpp 有 Vulkan 后端） | Ollama 侧走 Vulkan 的成熟度低于 llama.cpp | ⚠️ 备选 |

**性能与门槛估算**（依据本仓库 Mac 实测 + 解码带宽公式，**标注为估算**）：

解码速度 ≈ 内存/显存带宽 ÷ 权重字节数 × 0.6–0.7。本机（M5 Pro，350 GB/s）实测：
8B/4bit **61 tok/s**、32B/4bit **16 tok/s**、2B **86–116 tok/s**、TTFT 427ms @923 token
（见 `docs/RFC-端云协同-实施记录.md`；云端 deepseek-flash 对照 158–218 tok/s、TTFT 845–1306ms）。

| 档 | GGUF Q4_K_M 体积（实测） | 全 GPU 建议 VRAM | 纯 CPU 建议可用内存 | 估算 decode（DDR5 双通道 ~90GB/s / RTX 4060 ~272GB/s） |
|---|---|---|---|---|
| 2B | **1.3 GB** | ≥ 4 GB | ≥ 4 GB | ~35–50 tok/s / ~110 tok/s |
| 4B | **2.7 GB** | ≥ 6 GB | ≥ 8 GB | ~20–28 tok/s / ~60 tok/s |
| 9B | **5.7 GB** | ≥ 10 GB | ≥ 12 GB | ~10–14 tok/s / ~30 tok/s |
| 32B | ~19–20 GB（未在本仓库出现，Mac 上跑过 16 tok/s） | ≥ 24 GB | ⚠️ 不建议 | ~4–5 tok/s / ~12 tok/s |

> KV 缓存随上下文线性增长（8B 级约 144 KB/token → 8K 约 1.15 GB；2B/4B/9B 更小）。
> **这些是估算，不是实测**——桌面宿主的真实数字必须在目标机上量（§4.4 V5）。

**下载 UX（有本仓库实测证据，别重蹈）**：HuggingFace 官方 0 B/s、GitHub raw 仅 **27 KB/s**，
而同机国内链路 **6.3 MB/s**、ModelScope **16.8–20 MB/s**（见 `docs/RFC-端云协同-实施记录.md`）。
三档合计 **9.2 GB**：走 ModelScope ≈ **9–10 分钟**，走 GitHub raw ≈ **95 小时**。
→ 宿主必须复用 `scripts/edge_m0_setup.sh` 的 ModelScope + 断点续传路径，**不要**让用户 `ollama pull`；
并补两件它现在没有的：**磁盘空间预检** 与 **SHA256 校验**。

### 2.8 工程化清单（Windows / Ubuntu 各一条主路径）

| 关注点 | Windows | Ubuntu | 审计意见 |
|---|---|---|---|
| 进程形态 | Ollama 用户级安装后后台运行（不进服务）；**服务化**另做 | install.sh 装系统级 systemd 服务 | 首版 Windows 用**计划任务**（登录时启动，`schtasks`），不引入服务包装器 |
| 服务化备选 | 计划任务 / WinSW（E-D5）/ Servy（E-D5）/ ❌ NSSM（上游停更）/ ❌ 直接用 `sc.exe` 包非服务程序（会 1053） | systemd **user** unit + `loginctl enable-linger`（E-D3 待验）；或系统 unit | 服务化只在"GPU 在服务会话可用"实测通过后才给 |
| 监听与防火墙 | 默认 127.0.0.1；`--lan` 时加 `New-NetFirewallRule` 限定 tailnet 网段 | 默认 127.0.0.1；`--lan` 时用 `ufw allow from 100.64.0.0/10` | 与 §2.5 的"拒绝启动"断言绑定 |
| 远端接入 | Tailscale（已用于访问云端服务器，沿用）+ 可选 `tailscale serve`（E-D9） | 同 | ✅ 一致 |
| 日志与指标 | 宿主本地日志 + 可选上报 `route-events` | 同 | 复用 `docs/ops/16-端云协同协议.md` §4 |
| 升级 | ⚠️ Ollama 自动更新（E-D1）→ 宿主模式应**关闭自动更新**或固定版本 | 手动重跑 install.sh（E-D3） | 写进宿主脚本：`--pin-version` 默认开 |
| 卸载 | 官方卸载器 + `OLLAMA_MODELS` 目录按提示保留/删 | 删 unit + 目录 | 验收项 V8：卸载后无服务/无端口/无开机项 |
| 崩溃恢复 | 计划任务可配重启；手动模式打印诊断 | systemd `Restart=on-failure` | 验收项 V7 |
| **资源上限** | `OLLAMA_KEEP_ALIVE` / `OLLAMA_NUM_PARALLEL=1` / `OLLAMA_MAX_LOADED_MODELS=1`（E-D2 待验）；进程优先级 BelowNormal；一键"暂停宿主" | 同 + cgroup 限额 | 🔴 **必做**：这是"别人的工作机"，不是机房 |
| 磁盘占用 | 9.2GB（三档）/ 1.3GB（仅 short） | 同 | 安装时给"最小安装"选项（§7 Q6） |

## 3. GUI 审计（四选一，含成本/收益/风险）

> **范围声明（避免与同批文档打架）**：**"CMP 还是原生"的总体决策由同批产出的《多端跨端 · CMP 方案评估》负责**
> （owner 已表示倾向原生）。本文只回答一个更窄的问题：**桌面这一端值不值得为它单独写一套 UI**。
> 因此下表的结论是**条件式**的——无论总体选 CMP 还是原生，桌面的推荐都不变（见 §3.2）。

### 3.1 候选摊开对比

| 方案 | 复用 | 增量成本 | 主要风险 | 在"owner 桌面经验不足"约束下 |
|---|---|---|---|---|
| ① **CMP 桌面** | L3 逻辑（KMP）+ L5 UI（CMP）+ JVM 端口（JDBC/ONNX Java/PdfBox） | 5–8 人日（共享层已就绪）；共享层未就绪则 **+8–12** | 打包**不能交叉编译**（E-D6）：`.msi` 要 Windows、`.deb` 要 Linux；JVM 体积大；jlink 模块漏配 → `ClassNotFoundException` | 一套代码四端跑，**长期最省**；但短期需要目标 OS 机器才能出包 |
| ② **Tauri + 复用 `frontend/`** | 只复用 React UI（antd，68 用例） | 4–6 人日 | 端侧能力（本地 RAG/推理/凭证）全在 Kotlin 侧，Web UI 拿不到 → 要么做 sidecar/HTTP，要么桌面端变成"纯云端客户端"，**丢了端侧叙事**；Windows 依赖 WebView2（E-D7）；Rust 工具链新增一门语言 | 引入第二种语言 + 两套能力边界，owner 难排查 |
| ③ **原生（WinUI3 / Qt / GTK）** | 0 | 15+ 人日 | 即便总体选原生，桌面这端也是**第三个** UI 代码库（Android/鸿蒙之外），每加功能多改一处 | ⚠️ 只在前三端都原生且桌面是演示主力时才考虑 |
| ④ **只给浏览器入口** | 现有 `frontend/` 一行不改（桌面只是"打开网页"） | 0–0.5 人日 | 端侧价值无法体现；但**在阶段 A（只有宿主）时是完全够用的** | ✅ 阶段 A 交付物 |

### 3.2 我的推荐（条件式，分三段 + 止损线）

**先给结论：桌面 GUI 是"最不该为原生付钱"的一端。** 理由：桌面的差异化价值是**算力与文件**（都不需要新 UI），
而"原生体验"的收益在桌面最小（用户对桌面软件的宽容度高于手机）。所以：

| 总体 UI 决策 | 桌面 GUI 推荐 | 增量成本 |
|---|---|---|
| 总体选 **CMP** | 直接复用共享 UI（阶段 B） | 5–8 人日 |
| 总体选 **原生** | **不要**为桌面再写一套原生 UI → 桌面用 **浏览器入口 + 宿主状态页**（阶段 A） | 0.5–1 人日 |

| 阶段 | 做什么 | 触发条件 | 止损线 |
|---|---|---|---|
| **A（现在）** | 宿主 + **浏览器入口**（桌面用现有 Web 前端；宿主自带一个极简本地状态页：模型/显存/最近请求/暂停按钮） | 无（可立即做） | 若本地状态页超 1 人日 → 砍掉，只留命令行 `--status` |
| **B（M4 之后）** | **若总体选 CMP** → CMP 桌面：先 macOS 跑通（验证共享层与 JVM 端口），再出 Windows/Linux 包；**若总体选原生** → 阶段 A 就是桌面 GUI 的终点，省下的 5–8 人日投到 iOS/鸿蒙 | M4 共享层完成 + 有目标 OS 验证手段（§4.3） | 若某平台打包在 2 人日内不通 → 该平台只交付"绿色包 + 命令行"，不做安装器 |
| **C（可选）** | Tauri 版（唯一价值是复用 React UI；但拿不到 Kotlin 端侧能力） | ❌ 不推荐 | — |

**为什么把 GUI 后置是"省"不是"拖"**：CMP 桌面 GUI 的边际成本确实低，**前提是共享层已经在**。
现在共享层还没抽（M4 未开工），此时做桌面 GUI 等于**提前承担 M4 的成本**，而且是在一个没有验证机器的平台上承担。
**若 owner 最终选原生**（如《多端跨端 · CMP 方案评估》所述倾向），桌面这端就更没有必要写第三套 UI——
把"桌面 GUI"降级为浏览器入口，是这套方案里**唯一一个"不做反而更好"的决策点**。

### 4.1 本机现在就能验（不需要任何 Windows/Linux 机器）

## 9. 不做什么 / 已知代价（诚实清单）

- **不做**：第二个服务端、Windows 原生 UI、WSL2 作为独立端、桌面端侧 embeddings（首版）、NPU 加速；
- **已知代价 1**：桌面宿主首版**没有真 token**（靠网络隔离）——这在"家里局域网 + Tailscale"场景够用，
  但**不是**可以放在咖啡厅 Wi-Fi 上的东西。文档与脚本都必须把这条写清楚，不能只在设计文档里说；
- **已知代价 2**：CMP 桌面 GUI 会把端侧维护面从 3 端变 4 端，`doc_guard`、契约夹具、评测、自检都要跟着扩（Q8 的"端税"）；
- **已知代价 3**：本机 macOS 只能验"逻辑与链路"，**平台特有的东西（服务、防火墙、安装器、GPU 后端）一律无法在本机证明**——
  在拿到 Windows/Linux 验证手段之前，M8.1/M8.4 的进度只能算"写完了，未验证"；
- **已知代价 4**：桌面 GUI 的体验会**不如原生**（CMP 的窗口/托盘/输入法细节需要 interop 补），这是"一套 UI 四端跑"的必然取舍。
