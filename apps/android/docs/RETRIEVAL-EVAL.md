# 端侧检索评测（M3 第一批 · 验收数字 ④）

> 复现：`bash scripts/emulator.sh --background && bash scripts/android.sh push-model`
> 然后 `adb shell am start -n com.sekb.ondevice/.MainActivity --ez evalrag true`，
> 结果输出在 `adb logcat -s SEKB_RAG_EVAL`。
> 标注集在 `app/src/main/kotlin/com/sekb/ondevice/eval/RetrievalEvalSet.kt`。

## 1. 这套评测回答什么问题

不是"跑一个分数"，而是回答三个具体问题：

1. **端侧嵌入够不够用**：给定自然语言提问，正确的知识片段能不能被排到前面；
2. **阈值该定多少**：`Retriever.minScore` 决定"召回"与"误召回"的取舍，
   而这个区间完全取决于嵌入模型——必须标定，不能拍；
3. **延迟够不够低**：嵌入与检索分开测（前者是模型推理，后者是向量扫描）。

设计上刻意做了三件事：文档短且**主题互不重叠**（12 篇）、提问尽量**不复用文档原句**、
以及留 **3 条"库里没有答案"的问题**——只测"有答案时能否命中"会掩盖另一类错误：
把不相关内容硬塞给模型（幻觉的温床）。

## 2. 实测结果（模拟器 + ONNX `bge-small-zh-v1.5`，33 条问题）

```
语料 12 篇 / 问题 33 条（有答案 30，无答案 3）
阈值=0.20  Hit@1=26/30( 87%)  Hit@3=30/30  MRR=0.928  误召回=3/3(100%)  嵌入均 41ms(p95 58ms)  检索均 0.5ms
阈值=0.30  Hit@1=26/30( 87%)  Hit@3=30/30  MRR=0.928  误召回=2/3( 67%)  嵌入均 38ms(p95 56ms)  检索均 0.7ms
阈值=0.40  Hit@1=26/30( 87%)  Hit@3=30/30  MRR=0.928  误召回=0/3(  0%)  嵌入均 38ms(p95 57ms)  检索均 0.5ms
阈值=0.50  Hit@1=26/30( 87%)  Hit@3=29/30  MRR=0.911  误召回=0/3(  0%)  嵌入均 37ms(p95 55ms)  检索均 0.9ms
阈值=0.60  Hit@1=24/30( 80%)  Hit@3=24/30  MRR=0.800  误召回=0/3(  0%)  嵌入均 38ms(p95 57ms)  检索均 0.3ms
推荐阈值：0.40
```

| 结论 | 依据 |
|---|---|
| **默认阈值定为 0.4** | 0.2 时 3 条"库里没有答案"的问题**全部被强行回答**（100% 误召回，正是幻觉源）；0.4 时误召回归零、而 Hit@1/Hit@3 **一点没降**；再往上（0.6）开始伤召回 |
| 端侧嵌入"够用" | Hit@1 **87%**、Hit@3 **100%**、MRR **0.928**（同一批问题在真实模型上全部能排进前三） |
| 延迟 | 嵌入 **38ms**（p95 57ms，模拟器 CPU）、检索 **0.5ms**（12 篇；暴力余弦在万条量级前都够） |

```

```

前三条是**语义上合理的混淆**（"向量空间 vs 量化"都关于嵌入模型；"路由 vs 升级"都关于端云决策），
说明嵌入确实抓到了语义而不是词面。第 2 条（联系人权限 vs 端侧检索隐私）不太合理，
值得在下一批里看看是不是文档表述问题。

## 3.5 fp32 vs int8 量化模型（同一套标注集）

量化：`onnxruntime.quantization.quantize_dynamic`（QInt8，只量化权重）。
对比脚本：`python3 scripts/eval_embedding_quantization.py`（主机侧，直接解析端侧的标注集，
保证评测集只有一份）。

| 模型 | 体积 | Hit@1 | Hit@3 | MRR | 误召回 @0.4 | 误召回 @0.5 | 嵌入延迟（设备） |
|---|---|---|---|---|---|---|---|
| fp32 | 94.9 MB | 26/30 (87%) | 30/30 | 0.928 | 0/3 | 0/3 | 33–38 ms（p95 43–57） |
| **int8** | **23.9 MB（1/4）** | **26/30 (87%)** | **30/30** | **0.928** | 1–2/3 ⚠️ | **0/3** | **19 ms（p95 38）** |

三条结论：

1. **排序完全不变**（Hit@1/Hit@3/MRR 与 fp32 一致）——量化动的只是向量的绝对位置，
   而检索只关心**相对顺序**。跨模型逐条余弦 0.96–0.97。
2. **分数分布整体上移 → 阈值必须重标**：int8 在 0.4 下会把"库里没有答案"的问题答出来
   （误召回 1–2/3），**0.5 才干净**（0/3）。所以默认阈值定为 **0.5**（对 fp32 与 int8 都成立）。
3. **int8 的空间戳必须不同**（`…-int8@512`），因此**不能与云端向量融合**——
   这是量化的代价，切换时端侧会**原地重算**索引（已验证：3 块原地重算、文本不丢）。

设备延迟：**19 ms vs 33–38 ms（约 1.7× 快）**，而这还是**没有 `i8mm` 的模拟器**；
真机（有 dotprod/i8mm）预期更好。**建议默认用 int8**（体积 1/4、排序不变、更快），
代价是放弃与云端检索结果的融合——而融合目前还没实现，所以现在没有实际损失。

## 4. 这套评测的边界（别过度解读）

- **12 篇语料、33 条问题**：能筛出"阈值定错"这种量级的问题，不足以支撑"准确率 87%"这种结论；
- 语料是我写的**短文档**：真实用户文档（长、含表格、跨主题）会更难，命中率必然下降；
- 性能数字来自**模拟器**（Mac CPU），不能当作真机数字（见 SEKB RFC §9.1）；
- 阈值与命中率都是**模型相关**的：换嵌入模型（或做 int8 量化）必须重跑这套评测重新标定。
