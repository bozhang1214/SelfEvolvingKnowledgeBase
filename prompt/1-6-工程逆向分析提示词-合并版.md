# 工程逆向分析与技术文档生成提示词（完整版）


## 使用说明

本文档是一份**可直接复用**的提示词工程模板，用于对存量软件项目（特别是 Agent/LLM 应用类项目）进行全量代码逆向分析，并生成体系化的技术文档工程。

**适用场景**：
- 接手遗留系统，需要快速建立技术认知
- 为开源项目补充完整的技术文档体系
- 技术债务评估与架构重构前的现状摸底
- 团队知识沉淀与新人 onboarding 材料准备

**使用方式**：
1. 将本文档作为系统提示（System Prompt）提供给大语言模型
2. **严格按「执行工作流」分阶段推进**，逐批提供代码文件
3. 根据项目规模选择文档清单（完整版 12 篇 / 核心版 7 篇）

**⚠️ 重要约束**：
- 本提示词采用**只读分析**原则，不修改任何业务代码/配置
- 所有结论必须有代码证据支撑，标注 `文件:行号`
- 推断内容须显式标记「【推断·待验证】」
- 密钥/凭证/内网 IP 一律脱敏为 `<REDACTED>`

## 三、核心原则与纪律

### 3.1 事实纪律

| 原则 | 说明 |
|------|------|
| **禁止臆造** | 没读到的代码不许写结论；读到的必须给行号 |
| **区分事实与推断** | 推断必须显式标注「【推断·待验证】」 |
| **as-is / to-be 分离** | 现状与改进建议分章节，不得把设想写成现状 |
| **禁止复制既有文档** | 所有内容以代码为准，既有文档仅作交叉校验输入 |
| **禁止输出密钥原文** | 任何凭证信息必须脱敏 |

### 3.2 图示规范

- 所有图表使用 **Mermaid** 语法（可在 Markdown 直接渲染）
- 每张图必须配有文字解释，图文互相印证
- 架构图至少包含：系统上下文（C4-L1）、容器视图（L2）、组件视图（L3）

### 3.3 引用规范

- 代码引用格式：`path/to/file.py:L42-L68`
- 每段引用代码 ≤8 行，超过部分用自然语言概括
- 交叉引用用相对链接，每篇文档末尾附「相关文档」

### 3.4 写作规范

| 要求 | 说明 |
|------|------|
| **语言** | 简体中文；技术术语首次出现附英文原词 |
| **表格优先** | 接口/参数/配置信息用表格，避免长段落 |
| **编号体系** | 全局唯一编号（如 `API-07`、`CFG-12`） |
| **文档元信息** | 每篇文档顶部含：title / layer / owner / status / version / last-updated / related |
| **信息增量** | 每节都应有信息增量与代码证据，不注水 |

### 3.5 术语一致性

- 先产出术语表（Glossary），全文强制统一引用
- 禁止同义词混用（例如："反思"与"重规划"必须区分定义）
- 禁止同一个概念在文档中用不同名称指代

### 阶段 1：事实抽取（强制先产出，作为单一事实源 SSOT）

在撰写任何文档之前，**必须先产出以下 8 张事实表**。这是后续所有文档的数据源头。

| 编号 | 表名 | 必须字段 |

| **T3** | LLM 调用点清单 | 角色名、模型、temperature/max_tokens/response_format、超时/重试策略、调用位置（文件:行号）、是否走统一统计入口、每请求调用次数上界 |

### 阶段 2：关键路径精读（分批喂代码）

按**逻辑顺序**分批提供代码文件，每批 3-5 个强相关文件。

**推荐喂食顺序**（「倒着喂」原则）：
1. **数据实体优先**：`models/`、`schemas/`、`types/` → 理解数据长什么样
2. **配置与工厂**：`config.py`、`llm_factory.py`、`embedding/` → 理解如何装配
3. **无状态工具**：`tools/`、`utils/` → 理解有哪些能力
4. **有状态核心**：`memory/`、`storage/` → 理解状态如何管理
5. **编排调度**：`graph/`、`agents/`、`orchestrator/` → 理解如何调度
6. **接入层最后**：`api/`、`routers/`、`middleware/` → 理解如何对外暴露

**每批代码使用的分析提示词**：

> 请对当前这批次代码执行「逆向序列图抽取」和「状态机还原」：
>
> ### 1. 核心类/函数职责摘要（去注释版）
> - 提取每个核心类的真实副作用（例如：这个类不仅仅是调 API，它还负责维护 global_session_id 并写入 Redis）
> - 列出本批次代码中最复杂的 3 个函数，用自然语言简述其内部的决策树逻辑
>
> ### 2. 隐式数据流与对象生命周期
> - 追踪关键数据对象在本批代码中的流转路径：创建 → 被哪个修饰器增强 → 最终被哪个序列化器吐出
> - 重点识别：哪个地方发生了「对象突变（Mutation）」？
>
> ### 3. 外部依赖调用图谱（I/O Clustering）
> - 汇总本批代码中所有调用的外部接口（数据库 SQL、Redis Key 模式、外部 REST API 端点、LLM API 端点）
> - 标出其中没有设置超时时间或没有重试机制的危险调用点
>
> ### 4. 配置项溯源
> - 提取本批代码中读取的所有环境变量，生成《待补充配置项字典》

## 九、补充视角与发散建议

以下视角在原五份提示词中未充分覆盖，但具有重要价值，**建议根据项目情况选择性纳入**：

### 9.1 安全与合规视角

| 检查项 | 说明 |
|--------|------|
| **敏感数据暴露** | 日志中是否打印了 token/密码/用户隐私？代码中是否硬编码了密钥？ |
| **输入注入风险** | Prompt Injection 防护措施？SQL 注入防护？ |
| **鉴权与权限** | 是否所有敏感接口都有鉴权？权限模型是否合理？ |
| **数据留存与删除** | 用户数据删除时是否真的物理删除了？向量库中的 embedding 如何删除？ |
| **审计日志** | 关键操作是否有审计日志？日志是否防篡改？ |

### 9.2 性能与可扩展性视角

| 检查项 | 说明 |
|--------|------|
| **并发瓶颈** | 是否存在单点瓶颈？数据库连接池大小？线程池/协程池配置？ |
| **缓存策略** | 哪些数据可缓存？缓存失效策略？缓存穿透/雪崩防护？ |
| **LLM 调用优化** | 是否使用流式输出？是否使用前缀缓存（Prefix Caching）？Prompt 压缩策略？ |
| **向量检索性能** | 索引类型选择是否合理？数据量增长后的扩展方案？ |
| **水平扩展能力** | 无状态设计程度？共享存储方案？分布式锁实现？ |

### 9.3 知识图谱与关系抽取（如项目涉及）

- Agent 之间的依赖关系图（调用链、事件流）
- 工具与 Agent 的绑定关系矩阵
- 配置项与代码模块的依赖热度图

### 9.4 多语言/国际化（如适用）

- i18n 资源文件结构
- 语言切换机制
- 日期/数字/货币的本地化格式

### 9.5 前端专项深度

| 检查项 | 说明 |
|--------|------|
| **组件层级** | 组件树深度、复用率、重复组件 |
| **状态管理** | Store 结构是否合理？是否存在 prop drilling？ |
| **SSE 流式处理** | 前端如何处理流式数据？错误处理与重连机制？ |
| **性能** | 首屏加载时间、打包体积、懒加载策略 |

### 9.6 依赖治理视角

- **依赖冗余**：是否引入了未使用的依赖包？
- **版本锁定**：依赖版本是否固定？还是使用范围版本（如 `^` / `~`）？
- **安全漏洞**：是否存在已知 CVE 的依赖版本？
- **License 合规**：是否存在冲突的开源协议？

### 9.7 代码健康度自动检查清单

可纳入文档工程的可量化指标：

| 指标 | 检查方式 | 可接受阈值 |
|------|---------|-----------|
| 平均函数行数 | 静态扫描 | <50 行 |
| 最大函数行数 | 静态扫描 | <200 行 |
| 循环复杂度（Cyclomatic Complexity） | 静态扫描 | <15 |
| 重复代码率 | 静态扫描 | <5% |
| 测试覆盖率 | 测试报告 | >70% |
| 注释率 | 静态扫描 | >20%（核心模块） |
| 死代码/未使用的导入 | 静态扫描 | 0 |

### 9.8 文档体系自维护机制

为确保文档不过期，建议在文档工程中附带：

1. **CI 校验脚本**：
   - 检查所有内部链接是否可达
   - 检查是否有孤儿文档（不在索引中）
   - 检查配置项是否与代码一致（可做 diff）
   - 检查文档最后更新是否超过 6 个月（新鲜度告警）

2. **文档版本管理策略**：
   - 文档随代码一起版本管理
   - 重大架构变更时触发文档同步更新
   - 每季度文档全面审阅一次

3. **贡献指南**：
   - 如何更新文档
   - 文档规范如何执行
   - 谁负责审批文档变更
